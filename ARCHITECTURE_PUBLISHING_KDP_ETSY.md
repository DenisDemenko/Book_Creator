# Модуль публікації та експорту: Amazon KDP + Etsy

**Реалізація ТЗ v1.1 від 20.08.2026 (Fusion Lab).** Нижче — не пропозиція, а
опис того, що вже написано, підключено до застосунку й покрито тестами.
Посилання на файли — з робочого репозиторію NOVA STUDIO.

Запуск тестів: `npm run test:publishing` (164 тести) і
`npm run test:publishing-routes` (84 тести). Обидва входять у `npm test`.

---

## 1. Головне архітектурне рішення: дві гілки, а не одна

ТЗ (розділ 2) фіксує різницю платформ, і саме вона визначає форму всього
модуля:

| Платформа | Публічний API | Де закінчується наш код |
|---|---|---|
| **Amazon KDP** | немає | на готових файлах і **листі метаданих**, який автор копіює вручну |
| **Etsy** | Open API v3, OAuth2 | на **опублікованому лістингу** |

Тому в коді немає спільного «публікатора» з полем `platform`, який всередині
розгалужувався б на два зовсім різні сценарії. Натомість:

- `server/kdpSpec.ts` — специфікація KDP: трим-розміри, корінець, макет
  обкладинки, валідація рукопису, лист метаданих. **Жодного мережевого
  виклику в цьому файлі немає й не буде** — автоматизація завантаження в KDP
  порушує умови Amazon (ТЗ 9);
- `server/etsy/*` — повний конвеєр до живого лістингу.

Спільним лишається тільки те, що справді спільне: сутність товару, журнал
публікацій і файли, підготовлені до відправки.

## 2. Модель даних

Шість таблиць (схема — `server/db.ts`, доступ — `server/publishingStore.ts`).

**`products`** — товар: книга, курс, методика або набір. Окрема сутність від
книги навмисно: одна книга дає різні товари (рукопис під KDP і компактний zip
під Etsy), і в кожного свої заголовок, ціна й теги майданчика.

**`publications`** — публікація товару на майданчику. Ключове:

```sql
UNIQUE (product_id, platform)
```

Це і є ключ ідемпотентності з ТЗ 4.5: скільки б разів автор не натиснув
«Опублікувати», другого лістингу в крамниці не з'явиться — база просто не
дасть створити другий рядок.

**`publication_jobs`** — черга. Живе в базі, а не в пам'яті процесу, тому що
ТЗ 8 вимагає пережити рестарт сервера без втрати статусу задачі. Поля `step`
(де зупинились) і `progress` (що вже завантажено) — контрольні точки.

**`etsy_accounts`** — підключена крамниця. Токени зберігаються **тільки
зашифрованими** (див. §5).

**`etsy_oauth_states`** — транзитний стан PKCE: `state → code_verifier`.
Рядок живе хвилини й видаляється одразу після обміну коду на токен.

**`etsy_research_snapshots`** — зрізи дослідження тем. Одна таблиця обслуговує
одразу дві вимоги ТЗ 6: кеш на 24 години (останній рядок за темою) та
історизація для графіка динаміки (усі рядки за темою). Це не «остання
відповідь», а журнал — саме тому й можлива динаміка.

Шар доступу винесено в окремий модуль, а не дописано в `server/store.ts`:
той файл уже перевалив за тисячу рядків, а публікація — закінчена підсистема
з власним життєвим циклом. Контракт лишився проєктним: **той самий API поверх
SQLite і поверх JSON-файлів**, тож середовище без `node:sqlite` поводиться
однаково. Обидва бекенди ганяються по одному й тому самому набору тестів.

## 3. REST-ендпоінти

Шляхи повторюють структуру ТЗ — це полегшує звірку.

| Метод | Шлях | Призначення |
|---|---|---|
| `GET` | `/api/publishing/kdp/spec` | трим-розміри, ліміти, dpi |
| `POST` | `/api/publishing/kdp/cover-spec` | корінець + розгорнутий макет обкладинки |
| `POST` | `/api/publishing/kdp/validate` | перевірка рукопису перед експортом |
| `POST` | `/api/publishing/kdp/metadata` | лист метаданих для кабінету KDP |
| `GET/POST` | `/api/publishing/products` | список / створення товару |
| `GET/PUT/DELETE` | `/api/publishing/products/:id` | товар |
| `GET/POST/DELETE` | `/api/publishing/products/:id/files[/:name]` | файли товару |
| `POST` | `/api/publishing/products/:id/bundle/analyze` | оцінка набору + сценарій А/Б |
| `POST` | `/api/publishing/products/:id/bundle/package` | збірка `.zip` |
| `POST` | `/api/publishing/products/:id/publish/etsy/validate` | передпольотна перевірка |
| `POST` | `/api/publishing/products/:id/publish/etsy` | → `202` і задача в черзі |
| `GET` | `/api/publishing/jobs/:id` | стан задачі публікації |
| `GET` | `/api/publishing/publications` | журнал публікацій автора |
| `GET` | `/api/etsy/status` | чи налаштована інтеграція, чи підключена крамниця, ліміти |
| `POST` | `/api/etsy/oauth/start` | посилання авторизації (PKCE) |
| `GET` | `/api/etsy/oauth/callback` | обмін коду на токен |
| `DELETE` | `/api/etsy/connection` | відключити крамницю |
| `POST` | `/api/etsy/research` | дослідження теми (кеш 24 год) |
| `GET` | `/api/etsy/research/trend` | часовий ряд по темі |

Два рішення, які варто пояснити:

**Файли — вкладений ресурс** (`/products/:id/files`), а не пласкі `/files` з
`productId` у тілі. Приналежність перевіряється одним і тим самим кодом для
всіх операцій, і неможливо створити «сирітський» файл.

**Публікація повертає `202`, а не `200`.** Це не косметика: публікація — це
1 + до 10 + до 5 + 1 звернень до Etsy, кожне з яких може впертися в 429.
Тримати HTTP-з'єднання відкритим хвилинами й губити всю роботу від обриву —
неприйнятно. Роут ставить задачу в чергу й одразу віддає її id; інтерфейс
опитує `/jobs/:id`.

## 4. Підсистема 1 — генератор KDP-сумісних файлів

**Що вже було в проєкті.** Експорт EPUB/DOCX (`src/utils/fileExporters.ts`),
верстка з полями та трим-розмірами (`LayoutView`, `PdfEditorView`), клієнтська
валідація під KDP (`src/utils/kdpHelpers.ts`), форматування рукопису через
Claude (`server/claudeManuscript.ts`). Ці частини ТЗ вже закриті, і переписувати
їх заради «сервісу kdp-export-service» я не став — це була б заміна робочого
коду на інший робочий код без виграшу для автора.

**Що додано.** Те, чого бракувало саме конвеєру публікації:

- **розрахунок розгорнутого макета обкладинки** за формулою KDP:
  `ширина = 2 × (сторінка + виліт) + корінець`, з окремо винесеною товщиною
  корінця (`0.002252″`/`0.0025″`/`0.002347″` на сторінку для white/cream/color),
  результатом у мм і в пікселях за 300 dpi, з явним зазначенням CMYK для друку
  та RGB для електронної версії;
- **валідація перед експортом**: мінімум 24 і максимум 828 сторінок, наявність
  змісту, цілісність ієрархії заголовків (пропуск рівня ламає навігацію в
  Kindle), порожні глави;
- **лист метаданих**: назва, підзаголовок, опис (ліміт 4000 символів), рівно
  7 полів ключових слів, до 3 категорій BISAC, плюс розраховані корінець і
  макет обкладинки — усе готове до копіювання поле за полем.

Числа живуть **тільки на сервері** й віддаються через `/api/publishing/kdp/spec`.
Коли Amazon змінить вимоги, правити треба буде один файл, а не кожен екран.

## 5. Підсистема 2 — інтеграція з Etsy Open API v3

### 5.1. Авторизація

OAuth 2.0 Authorization Code + PKCE (`server/etsy/etsyOAuth.ts`). `code_verifier`
ніколи не покидає сервер: у браузер іде лише `state` і `code_challenge`. Стан
зберігається в базі й читається **один раз** — повторне відтворення того самого
callback-у не спрацює (перевірено тестом).

Скоупи рівно ті, що потрібні: `listings_r listings_w listings_d shops_r shops_w`.
Зайвий скоуп — зайва причина для автора не натиснути «Дозволити».

### 5.2. Токени зберігаються зашифрованими

`server/etsy/tokenCrypto.ts` — **AES-256-GCM**, ключ виводиться з
`ETSY_TOKEN_SECRET` через `scrypt`, формат `v1:<iv>:<tag>:<ciphertext>`.

Три рішення тут неочевидні:

1. **GCM, а не CBC** — GCM автентифікує: підмінений шифротекст не
   розшифрується, а чесно кине помилку (є тест на підміну).
2. **Префікс версії** лишає місце для зміни алгоритму без міграції таблиці.
3. **Якщо секрет не заданий, модуль відмовляється підключати крамницю.**
   Краще не підключити, ніж покласти ключ від крамниці автора в базу
   відкритим текстом — навіть у dev-середовищі.

Назовні токен не йде ніколи: ані в API-відповідь, ані в лог. У журналі — лише
відбиток `sha256:xxxxxxxx`.

### 5.3. Транспорт: ліміт швидкості й повтори

`server/etsy/etsyClient.ts` + `server/etsy/rateLimiter.ts`.

- **Токен-бакет** на 8 запитів/сек при стелі Etsy у 10 (ТЗ 4.1) — запас на
  кількох одночасних авторів.
- **Бакетів два — публікаційний і дослідницький.** Це пряма вимога ТЗ 6.4:
  дослідження теми робить десятки запитів поспіль, і в спільному бакеті автор,
  що тисне «Опублікувати», чекав би, поки догорить фонова аналітика.
- **429 і 5xx** повторюються з експоненційним backoff (база 1 с, максимум 5
  спроб, з джитером ±25%). Джитер обов'язковий: без нього всі задачі, що впали
  під час хвилинного збою Etsy, повернулися б одночасно й поклали його знову.
- **4xx, окрім 429, не повторюються ніколи** — «поле обов'язкове» саме не
  виправиться, скільки не чекай.
- **401** запускає рівно одне оновлення токена по `refresh_token` і один
  повтор. Якщо свіжий токен теж дає 401 — проблема не в терміні дії.
- **Мережевий обрив** повторюється так само, як 503: обрив TCP нічим не гірший
  і трапляється частіше.

### 5.4. Потік публікації: чому черга з контрольними точками

`server/etsy/publishQueue.ts` виконує потік ТЗ 4.3 покроково:

```
create_listing → upload_images → upload_files → activate → done
```

Стан фіксується в базі **після кожного кроку, а всередині завантажень — після
кожного файлу**. Наслідки:

- падіння процесу коштує щонайбільше одного файлу, а не всієї публікації;
- після рестарту `requeueStuckJobs()` повертає задачі зі стану `running` у
  чергу, і робота продовжується з місця обриву;
- **повтор ніколи не створює другий лістинг**: крок `create_listing`
  пропускається, якщо в публікації вже є `external_id`.

Часткова невдача (ТЗ 4.5) обробляється так, як просить ТЗ: якщо лістинг уже
створено, а файли не долилися, публікація лишається в статусі `draft`, автор
бачить конкретну помилку й може долити файли руками. Робота не зникає.

### 5.5. Усі ліміти перевіряються ДО звернення до API

`server/etsy/etsyListingRules.ts` — чисті функції: 5 файлів, 20 МБ кожен,
перелік дозволених розширень, 13 тегів по 20 символів, до 10 зображень,
заборона варіацій для цифрового товару.

Це критерій приймання 4.6, і причина не формальна: якби ці помилки ловилися
відповіддю Etsy, автор дізнавався б про них після п'яти хвилин завантаження, а
половина файлів уже висіла б у чернетці.

## 6. Підсистема 3 — пакувальник курсових компонентів

`server/etsy/coursePackager.ts` + `server/etsy/zipWriter.ts`.

**Оцінка передує пакуванню.** `analyzeComponents()` — окрема чиста функція:
спакувати 300 МБ відео, щоб потім сказати «не влізло в 20 МБ», означало б
змарнувати час автора й пам'ять сервера.

**Вибір сценарію А/Б (ТЗ 4.4)** автоматичний, з порогом **нижчим за 20 МБ**:
від 90% ліміту рекомендується сценарій А. Набір на 19,5 МБ формально влазить,
але будь-яке доповнення матеріалів наступного місяця вимагатиме перепаковувати
товар — і система чесно пояснює це автору текстом, а не просто вмикає інший
режим.

**ZIP пишеться власним кодом** (`node:zlib`, ~120 рядків) замість наявного в
залежностях `jszip`: jszip писався для браузера й у серверний бандл заходить
помітно важчим, ніж потрібно, щоб скласти 3–5 файлів. Формат перевіряється
тестом, який розпаковує архів і звіряє вміст байт у байт, а також звіряє CRC32
з еталонним значенням.

**Про README.pdf — свідоме відхилення від ТЗ.** ТЗ просить `README.pdf`.
Стандартні шрифти PDF не підтримують кирилиці, а Unicode-шрифт репозиторій не
возить. Рішення: якщо доступні `pdf-lib` і шрифт (`ETSY_README_FONT_PATH`,
кеш у `DATA_DIR/fonts` або одноразове завантаження з `ETSY_README_FONT_URL`) —
кладемо `README.pdf`; якщо ні — кладемо `README.txt` і **явно повідомляємо про
це попередженням**. Набір не повинен ставати неопублікованим через відсутній
шрифт. Якщо потрібен саме PDF без винятків — скажіть, і ми покладемо ліцензійно
чистий шрифт (DejaVu Sans, Bitstream Vera license) у репозиторій; це ~700 КБ.

## 7. Підсистема 4 — дослідження попиту та SEO

`server/etsy/etsyResearch.ts` (аналіз) + `server/etsy/researchService.ts`
(кеш, історизація, розклад).

**Найважливіше в цій підсистемі — чесність формулювань.** Etsy Open API v3 не
віддає ані продажів чужого товару, ані позицій у видачі, ані готового підбору
слів (ТЗ 6.1). Тому:

- жодне число не називається «продажами» чи «бестселером» — тільки «оцінний
  показник»; текст застереження живе в коді константою `RESEARCH_DISCLAIMER_UK`
  і **виводиться в інтерфейсі перед цифрами**, а не під ними;
- похибка завжди в бік «недооцінити»: якщо поля немає, вважаємо нуль, а не
  домальовуємо середнє.

**Індекс популярності** = `0.65 × нормалізовані «улюблені» + 0.35 × позиція у
видачі`. Вага на користь «улюблених» навмисна: позиція відображає ще й рекламу
та свіжість, тобто шумніша за пряме вподобання. «Улюблені» нормалізуються до
максимуму по вибірці — абсолютні числа в різних нішах непорівнянні.

**Частотний аналіз** рахує не «скільки разів слово трапилось», а **у скількох
різних лістингах воно є**: один продавець, що напхав слово вісім разів у назву,
інакше перекошував би всю вибірку. Слово-тег важить утричі більше за слово в
назві — тег є усвідомленим вибором продавця для пошуку, назва часто містить
описове сміття. На виході — до 13 кандидатів, кожен уже обрізаний до 20
символів **по межі слова** (обрубок «watercolor journ» гірший за коротший, але
цілий тег).

**Кеш і історія — одна таблиця.** Повторний запит теми впродовж 24 годин не
витрачає жодного виклику Etsy (перевірено тестом). Кожен свіжий збір **додає**
зріз, а не перезаписує — саме тому можлива динаміка попиту за тижні.
Планове оновлення (`ETSY_RESEARCH_REFRESH_MINUTES`) типово вимкнене; без нього
графік показуватиме лише ті дні, коли автор шукав вручну.

## 8. Обробка помилок

| Ситуація | Код | Рішення |
|---|---|---|
| Некоректний вхід (порожня назва, ціна ≤ 0, тема > 120 символів) | `400` | валідація до будь-яких записів і викликів |
| Не автентифікований | `401` | `requireAuth` |
| **Чужий товар / задача** | `404`, не `403` | навмисно: `403` підтвердив би, що такий id існує |
| Лістинг не пройшов правила Etsy | `400` + список `issues` | усе перевірено до звернення до API |
| Крамницю не підключено | `409` + `kind: 'etsy_not_connected'` | машинний код, щоб UI показав кнопку підключення |
| Товар уже опубліковано | `409` + `kind: 'already_published'` | захист від подвійної публікації |
| Ключів Etsy немає | `503` з поясненням, якої змінної бракує | **стан конфігурації, а не збій** |
| Помилка Etsy | `502`/статус Etsy | збій зовнішньої системи |
| Непередбачене | `500` | деталі — у лог, назовні загальне повідомлення |

Три моменти, які вважаю найважливішими:

**Відсутність ключа — це конфігурація, а не помилка.** Без `ETSY_API_KEY`
модуль не падає: KDP-гілка й пакувальник працюють повністю, а Etsy-вкладка
пише, чого саме бракує. Це та сама філософія, що вже діє в проєкті для
AI-ключів.

**Сирі відповіді Etsy не течуть назовні.** Назовні йде людське пояснення,
`err.message` і обрізане тіло лишаються в серверному лозі. Перевіряється
окремим тестом (відповідь `invalid_grant` не має з'явитись у повідомленні
клієнту).

**Робота автора не зникає.** Файли зберігаються на сервері до публікації;
репліка «створити лістинг» ідемпотентна; часткова невдача лишає чернетку.

## 9. Тестування

`npm run test:publishing` — **164 тести**, `npm run test:publishing-routes` —
**84 тести**. Разом 248, усі проходять. Ані мережі, ані ключів Etsy тести не
потребують: `fetch`, клієнт Etsy та час підставляються.

Покриття за рівнями:

- **Чисті правила** — корінець і макет обкладинки (звірка з формулою KDP),
  валідація рукопису, правила лістингу (6-й файл, файл > 20 МБ, недозволений
  формат, варіації, нульова ціна), нормалізація тегів, вибір сценарію А/Б.
- **Криптографія** — round-trip, різні шифротексти для того самого токена,
  виявлення підміни, відмова на чужому форматі.
- **Транспорт** — 503 повторюється й минає; 400 не повторюється; 401 запускає
  рівно одне оновлення токена; вичерпаний дослідницький бакет не впливає на
  публікаційний.
- **Аналітика** — токенізація, стоп-слова, біграми, індекс популярності,
  розкладання ціни Etsy `{amount, divisor}`, відсутність слів самої теми серед
  «нових» тегів.
- **Пакувальник** — архів має сигнатуру `PK\x03\x04`, коректний EOCD, і його
  вміст розпаковується байт у байт; CRC32 звірено з еталоном.
- **Сховище** — CRUD, ізоляція чужих товарів, унікальність пари
  (товар, майданчик), черга задач, одноразовість OAuth-стану. **Той самий набір
  перевірок проганяється і на SQLite, і на JSON-фолбеку.**
- **Конвеєр** — повний happy path (чернетка → зображення → файли → активація),
  ідемпотентність повторного натискання, часткова невдача (5 спроб → `failed`,
  лістинг лишається чернеткою, причина збережена), відновлення після рестарту
  (лістинг НЕ створюється заново, зображення НЕ завантажується вдруге).
- **HTTP** — на кожен ендпоінт позитивний і негативний сценарій:
  `200/201/202` проти `400/401/404/409/503`, включно зі спробою вийти за теку
  товару через ім'я файлу `../../evil.txt`.

## 10. Припущення і питання до уточнення

**Припущення, які я зробив:**

1. Один автор — одна крамниця Etsy. Кілька крамниць на акаунт не передбачені.
2. Товар публікується на майданчик один раз; оновлення вже опублікованого
   лістингу (зміна ціни, заміна файлу) — окремий сценарій, у цьому етапі не
   реалізований.
3. Категорія Etsy (`taxonomy_id`) передається запитом; окремого довідника
   категорій з підказками поки немає — за замовчуванням Digital Prints/Books.
4. Ціни в USD; конвертації немає (як і в наявному модулі підписки).
5. Файли товару лежать на диску сервера поруч із базою. На ефемерному
   хостингу під них потрібен той самий постійний том, що й під `DATA_DIR`.

**Питання, на які хотів би відповідь до наступного етапу:**

1. **README.pdf**: класти шрифт DejaVu Sans (~700 КБ) у репозиторій, щоб PDF
   формувався завжди, чи лишити нинішню деградацію в `.txt`?
2. **Оновлення опублікованого лістингу** — потрібне в цьому релізі? Це
   змінює контракт: з'явиться `PUT /publications/:id` і крок `update` у черзі.
3. **Довідник категорій Etsy** — тягнути `taxonomy` з API й показувати автору
   дерево, чи достатньо ручного введення `taxonomy_id`?
4. **Планове оновлення тем** типово вимкнене. Вмикати за замовчуванням
   (наприклад, раз на добу), і якщо так — скільки тем на прогін?
5. **Квоти на публікацію за тарифами.** Зараз модуль доступний усім ролям з
   правом публікації без обмежень по кількості. Чи прив'язувати його до
   тарифів Pro/Ultra, як зроблено для форматування під KDP?

## 11. Терміни та ризики

**Чи змінився початковий дедлайн:** ні.

**Стан:** описане вище реалізовано, підключено до застосунку (вкладка
«Публікація та експорт») і покрито 248 тестами. На доведення під відповіді на
питання вище закладаю **6–9 годин**:

- оновлення опублікованого лістингу — ~2 год;
- довідник категорій Etsy з пошуком — ~2 год;
- шрифт і гарантований README.pdf — ~0,5 год;
- квоти за тарифами — ~1 год;
- решта — на уточнення після демонстрації.

**Ризики, які бачу зараз:**

1. **Ревʼю застосунку в Etsy.** Personal-доступ до API видається одразу, але
   для роботи від імені інших продавців застосунок проходить перевірку Etsy.
   Це організаційний строк, не технічний, і він поза нашим контролем — варто
   подати заявку заздалегідь.
2. **Ліміт 20 МБ проти реальних курсів.** Сценарій А (лінк на власну
   платформу) знімає проблему, але вимагає, щоб та платформа існувала й
   видавала лінки доступу. Якщо її немає, «компактний курс» лишається єдиним
   робочим варіантом.
3. **Оцінність показників дослідження.** Ми будуємо аналітику на непрямих
   сигналах. Якщо бізнес очікує «показати бестселери» — цього не зможе жоден
   інструмент, що працює через офіційний API; варто узгодити очікування до
   демонстрації, а не після.
4. **Файли на локальному диску.** На ефемерному хостингу підготовлені файли
   зникнуть при рестарті разом із теками. Черга це переживе (стан у базі), але
   задача впаде з «файл не знайдено». Потрібен постійний том або перехід на
   об'єктне сховище — та сама вимога, що вже є для згенерованих зображень.
5. **Зміни в Etsy API.** Версія v3 стабільна, але поля на кшталт `num_favorers`
   не мають гарантії незмінності. Аналітика деградує м'яко (нуль замість
   помилки), проте якість оцінок у такому разі мовчки впаде — варто раз на
   квартал звіряти реальні відповіді API з очікуваними полями.
