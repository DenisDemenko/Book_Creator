# Т5.3 — Story Core API для графів і Story Graph у Graph Studio

Продовження `task.md` (етап 5, Т5.3), `PLAN_GRAPH_STUDIO.md` (Т5.2),
`PLAN_ACCESS.md` (Т6.2) і `PLAN_ROADMAP.md` §8. Формат — як попередні плани:
що вже є, рішення, етапи В1…Вn, кожен окремим записом журналу.

Джерела: ТЗ Graph Studio v3.0 §23 (Story Graph — представлення справжніх
даних ядра, не копія канону), §24 (стани пропозиції DETECTED → … → CANON,
REJECTED, SUPERSEDED; AI → PROPOSAL), §25 (походження), §33 (операції Story
Core API; графи не отримують довільного SQL), §34 (ревізії сутностей і
зв'язків), §37 (`CANON_WRITE`), §39 №13, 14, 15, 16, 18.

**Готово (task.md):** операції §33 (get_schema … write_canon, publish_schema,
rollback_schema) над наявним ядром — графи не отримують довільного SQL. Story
Graph — представлення справжніх entities / entity_relations /
entity_mentions … з фільтрами, походженням і ручними пропозиціями. Готово:
№13, 18.

## 1. Що вже є

- **Ядро твору** (Т0.3–Т0.4): `entities` (статус suggested / confirmed /
  rejected, версії в `entity_versions`), `entity_relations` (докази-абзаци;
  AI-зв'язок без доказу база не приймає), `entity_mentions`,
  `analysis_runs` (модель, версія промпту), `analysis_findings`
  (пропозиції AI-1 `mention_suggestion` / `relation_suggestion`). AI лише
  пропонує, статус змінює людина.
- **Граф історії книги** (Т1.4): `buildStoryGraph` — огляд і фокус із
  глибиною, типи, лише підтверджені, зв'язки з тегів, докази з уривками;
  сторінка «Граф» у Студії й `/api/projects/:id/story-graph`.
- **Реєстр схем** (Т5.1): активна версія онтології `fusion-story` — типи
  сутностей із властивостями, типи зв'язків із дозволеними кінцями
  (`from` / `to`), правила перевірки; публікація й відкат.
- **Наданий доступ** (Т6.2): рівні view … approve, manage на книгу, розділ,
  сцену, персонажа, локацію; обмежений доступ закриває граф і пошук.
- **Graph Studio** (Т5.2): `/admin/graph-studio/<вкладка>`, право
  `canPublishSchema`, вкладка «Граф твору» — поки посилання.

## 2. Рішення власника (01.10.2026)

1. **`CANON_WRITE` — на рівні книги:** записати в канон може власник книги,
   адміністратор або учасник із наданим доступом «схвалення» (approve) чи
   вищим на книгу (механізм Т6.2). Окремого права ролі немає.
2. **Новий реєстр пропозицій** сутностей і зв'язків зі станами §24 і
   походженням §25. Наявні пропозиції AI-1 (`analysis_findings`, suggested
   зв'язки) лишаються як є й показуються поруч.
3. **Вкладка «Граф твору» — вибір книги:** адмін бачить усі книги,
   синхронізовані з ядром; інші — ті, до яких мають доступ (обмежений
   доступ Т6.2 граф не відкриває).
4. **Story Core API — внутрішній сервіс** для процесів (виконання — Т5.4) і
   HTTP для Graph Studio; зовнішнє API — пізніше.

## 3. Задум

**Пропозиція** (`story_proposals`, міграція 0023): книга, вид (`entity` /
`relation`), стан §24 (`detected` → `proposed` → `validated` → `approved` →
`canon`; `rejected`, `superseded`), зміст (сутність: тип, назва, канонічні
поля, за бажанням — наявна сутність, яку уточнює; зв'язок: тип, початок,
кінець, примітка), ключ дубля, докази-абзаци, впевненість, походження §25
(`source`, процес і його версія, вузол, версія онтології, модель, версія
промпту, прогін, рішення Jev), результат перевірки, правка автора (що було →
що стало), посилання на запис канону, хто вирішив і чому. Журнал
`story_proposal_events` — лише дописується.

**Правила** (і в базі, і в обох сховищах): AI створює лише `detected` /
`proposed` і лише з доказом; стан змінює людина чи система, не AI; `canon`
— лише з посиланням на запис; `superseded` — лише з посиланням на новішу;
кінцеві стани (`canon`, `rejected`, `superseded`) незмінні; одна відкрита
пропозиція на ключ дубля.

**Перевірка** щодо АКТИВНОЇ версії онтології: тип є й не застарілий,
властивості й переліки, обов'язкові властивості, кінці зв'язку (`from` /
`to` типу і правило `relation_endpoints`), сутності існують і не
відхилені, докази — живі абзаци книги, дублі в каноні й серед відкритих
пропозицій.

**Запис у канон** (`write_canon`): схвалена пропозиція → підтверджена
сутність (нова або правка наявної — нова ревізія) чи зв'язок від імені
людини, що схвалила; пропозиція — `canon` з посиланням; подія в журналі з
походженням (№16).

**Story Core API** (`server/core/storyCore/api.ts`): реєстр операцій §33 з
описом, видом (читання / пропозиція / рішення / схема) і перевіркою прав —
читання за доступом до книги, пропозиції — редагування книги, схвалення й
запис у канон — approve+ / власник / адмін, публікація й відкат схеми —
`canPublishSchema`. Внутрішній виклик `callStoryCore(op, ctx, args)` для
процесів і HTTP `/api/core/story-core/…` для Graph Studio. Довільного SQL
немає — лише ці операції (№13).

**Вкладка «Граф твору»**: вибір книги; граф справжніх сутностей і зв'язків
(№18) з фільтрами (групи / типи, стан, джерело: автор, тег, AI-1,
пропозиція); картка вузла чи ребра з походженням (ревізії, докази, хто
створив, модель і промпт прогону); панель пропозицій (новий реєстр поруч із
пропозиціями AI-1) з перевіркою, схваленням із правкою, відхиленням і
записом у канон; форма ручної пропозиції.

**Критерії ТЗ §39.** №13 (Query читає Story Core через API) — реєстр
операцій і `callStoryCore`, довільної операції немає; №18 (Story Graph зі

самі записи (живий прогін (2)). Також №14 (вихід AI — пропозиція) — AI лише
detected / proposed і лише з доказом, і в базі; №15 (Accept / Edit / Reject)
— схвалення з правкою автора й відхилення; №16 (запис у канон — ревізія,
походження, аудит) — підтверджений запис ядра від імені людини, журнал із
походженням (живий прогін (3)).

**Чого ще немає — і чому.** Процеси, що пишуть пропозиції, — Т5.4;
пропозиції згадок — на старому шляху AI-1 (тег ставиться в редакторі);
зовнішнє API — пізніше (§2 п.4); Continuity Gate перед записом у канон
(№17) — вузлом процесу в Т5.4–Т5.5.
