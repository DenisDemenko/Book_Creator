# Т6.5 — внески та граф співпраці

Джерело: Graph Studio v3.0 §47, §51, §55–56, критерії №35, 41–42, 45–47, 50.

Реалізовано 07.10.2026, журнал #391.

## Поведінка

- Співавтор із правом редагування сцени надсилає Change Proposal. Сервер
  визначає користувача, участь і ролі; клієнт не призначає автора чи схвалювача.
- Власник або адміністратор читає правку, схвалює та зливає або відхиляє.
  Перевіряються актуальні права автора й точна ревізія книги. Застаріла
  пропозиція лишається pending: потрібно перечитати джерело й подати нову.
- Книга, ревізія, merged-пропозиція, Contribution і доменні події записуються
  атомарно в SQLite. Збій відкочує все; повторне злиття дає 409.
- Співавторський прямий PATCH повертає `proposal_required`. Realtime-квиток
  співавтора не дозволяє запис; під час повідомлень роль перечитується.
  Звичайний редактор із явним edit-доступом зберігає пряме редагування сцени,
  яке також записує внесок. Роль не розширює наданий доступ.
- У «Спільній роботі → Пропозиції та внески» доступні подання, порівняння з
  початковою ревізією, розгляд і журнал. Обмежений учасник бачить тільки
  дозволені сцени. Внески не є юридичним визначенням авторських прав.
- Graph Studio → «Граф співпраці»: Participant / Role / Contribution /
  Access / Production. Граф доступний лише з повним доступом книги;
  production-представлення показує реальний розгляд і злиття scene proposals.
  PERSON — обліковий запис людини, не CHARACTER семантичного ядра.

## Походження

Запис містить projectId, participantId, userId, знімок roleIds, actionType,
resourceType/resourceId/chapterId, sourceRevision/resultRevision, timestamp,
approvalStatus/approvedBy та provenance. taskId/deliverableId зараз null:
їхні об'єкти реалізуються в етапі 7. Немає ретроспективного приписування
внесків старим ревізіям або автоматичного оголошення юридичних співавторів.

Зберігаються підтверджені правки сцен через серверний source API та
Change Proposal; довільне повне збереження авторської книги, локальний
IndexedDB, історичні realtime-правки й завантаження дизайнів не видаються
за вже повний реєстр внесків. Для нових ресурсів етапу 7 потрібні їхні
фактичні інтеграції, а не клієнтське самодекларування внеску.

## Події та процеси

Зберігаються CHANGE_PROPOSED / CHANGE_REJECTED / CHANGE_APPROVED /
CONTRIBUTION_RECORDED. Каталог також читає справжні події участі, ролей і
доступу з Core та CANON_CHANGE_PROPOSED / CANON_CHANGE_APPROVED із журналу
Story Core. Метадані подій не містять тексту книги чи приватного контексту.

START має JSON-параметр `collaboration_events`, наприклад:

```json
["CONTRIBUTION_RECORDED", "CANON_CHANGE_APPROVED"]
```

Після перевірки та публікації процесу людина з правами керування Graph
Studio може запустити його за подією з графа. Сервер перевіряє доступ до
книги, походження події та підписку поточної production-версії; відкидає
додатковий клієнтський input і draft versionId. У запуску `trigger=manual`,
а перевірене джерело зберігається в `input.collaborationEvent`.

Автоматичної фонової підписки або автоматичних платних запусків немає.
TASK/DELIVERABLE-події етапу 7 не імітуються. Доступ і канон залишаються
під поточними серверними перевірками workflow.

## Сховище та межі

SQLite серверної книги є обов'язковим для нового журналу та proposals;
без нього API відповідає 503. Три додаткові таблиці створюються повторювано
при першому зверненні; вони належать книзі й видаляються з нею. Учасники,
ролі та доступ залишаються в Core (Memory або PostgreSQL). Міграція Core
не потрібна. Списки журналу обмежені 1000 записами, core events — 500,
Story Core proposals для каталогу — 200 з останніми 100 подіями кожної.

Перевірка: `npm run test:collaboration-contributions`; PostgreSQL — окрема
нова база через CORE_TEST_DATABASE_URL; браузер після `npm run build`:
`npm run live:collaboration-contributions`.
Ручне приймання: [T6.5](docs/acceptance/T6.5.md).
