# Етап 11 — Lila & Systemic Mapping Studio

Дата: 09.10.2026. [Концепція власника — 21 розділ](docs/tz/CONCEPT_LILA_SYSTEMIC_MAPPING_STUDIO.md). **Статус: концепція й план, усі Т11.1–Т11.12 не почато.** Тут запропоновано технічну декомпозицію та метод перевірки інвестиційних гіпотез; доказів попиту, доходу або ефективності ще немає.

## 1. Продуктова межа

Окремий професійний режим для системного картування й добровільної фасилітованої рефлексії, не психотерапія/діагностика/лікування/кризова служба. Фасилітатор працює в межах компетенції. Координати, метафори, AI-текст і «інсайт» не стають об’єктивними фактами про людину. Система не гарантує покращення чи безперервного моніторингу.

Спільна Studio може надати інфраструктуру користувачів, канви, grants, версій, AI/review, медіа й Marketplace, але приватність Lila потребує окремого домену даних/політики. Клієнтська карта не є персонажем книги, пацієнтом в онтології Story Core або станом гри. Реальні конспекти не імпортуються у fiction/game автоматично.

Для зв’язку «практика → книга» використовується [JEV-BOOKS-1](PLAN_JEV_AUTHOR_BOOKS.md): лише окремо підготовлений дозволений матеріал, з явною згодою на відповідну передачу/публікацію, походженням та погодженим співавторством. Дозвіл фасилітатору або на AI у Lila не є дозволом на книгу, training, маркетинг чи товар.

Попередня звірка Book_Creator, не приймання нового продукту. Остаточний огляд потрібен у Т11.1.

| Основа | Точка інтеграції | Межа |

| Співпраця, scoped grants | `server/core/collaboration/access.ts` | Чинний owner/admin full не відповідає вимозі least privilege Lila; заборонити обхід через загальні Core/export/realtime endpoints |

Граф знань героя та пам’ять персонажа не є психологічним профілем клієнта. Score/Noul/Choice Jev можна застосовувати лише для допустимості питання/формату/якості пропозиції, не для оцінки страху, впевненості, психічного стану або суїцидального ризику людини.

## 3. Модель даних і походження

Проєктування й міграції — Т11.1; назви нижче концептуальні, не вже створена схема.

- PracticeWorkspace / ProfessionalProfile: власник, професійний режим/компетенція, межі/доступність/правила супроводу. Клієнтський профіль не створює згоду або активний account автоматично.
- ClientRelationship / Session: запрошення/acceptance, запит, погоджені учасники, draft/active/paused/completed, правила конфіденційності й crisis availability.
- Map / MapRevision / Element / Relation: координати/символ/label, scope, автор і походження, версія. Зв’язок є авторським/клієнтським твердженням, не автоматично доведеною причиною.
- Епістемічний статус: **повідомлений користувачем факт**, суб’єктивне сприйняття, символ, гіпотеза, питання, нотатка фасилітатора, AI-пропозиція. Навіть «повідомлений факт» не маркувати незалежно перевіреним. Медичні теми — явно символічні/повідомлені, без підтвердження діагнозу.
- Note / Observation / Insight / NextStep / ReflectionResponse: власник/аудиторія, джерело, session/map revision. Клієнтські, фасилітаторські й автоматичні тексти розрізняються в UI та експорті.
- ConsentRecord / ConsentEvent / Grant: мета, subject, версія тексту згоди, конкретні дані/одержувачі/провайдер, timestamp/revoke, застосовна підстава. Не підміняти consent звичайним project role.
- AIProposal: підготовлений дозволений контекст, consent revision, провайдер/модель, статус human review, бюджет/usage; не містить копії всього досьє в публічному trace.
- AccessAudit / Incident / ContentReport / DeletionRequest / ProviderDeletionReceipt / RetentionPolicy: мінімальні метадані, права перегляду, строки й результат; аудит не повинен зберігати видалений приватний текст повторно.

Історія змін у MVP потрібна для autosave/відновлення й заявленої динаміки. Розширений diff кількох карт, порівняння сесій і версіонування методик — після MVP; повний доступ до історичних версій також фільтрується поточними правами.

## 4. Доступ і десять окремих згод

Згоди §8.2 концепції: платформа; сесія/зберігання; передача фасилітатору; AI; чутливі дані; група; запис audio/video/screen; анонімізоване навчання/дослідження; маркетинг; представник неповнолітнього за вимогами. Різні перемикачі, мета/пояснення, журнал і просте відкликання. Немає наперед увімкненого AI, групового запису, marketing або training.

Функція працює лише за перетином необхідних чинних прав і потрібних згод/підстав; одна згода не відкриває все. Відмова AI залишає карту, нотатки, питання/підсумок вручну. На MVP training/research, recording та групи можуть бути вимкнені до реалізації відповідних вимог, а не прикриті одним checkbox.

| Видимість | Передбачена серверна аудиторія |
|---|---|
| PRIVATE | Власник конкретного запису; professional workspace owner не обходить клієнтську приватність |
| FACILITATOR_ONLY | Конкретно призначений фасилітатор за погодженими правилами зберігання/документації |
| CLIENT_AND_FACILITATOR | Вказані клієнт/фасилітатор та чинні дозволи |
| SESSION | Лише учасники визначеної сесії й дозволені елементи |
| PROJECT | Явні scoped grants конкретного робочого проєкту; не «вся організація» |
| GROUP | Учасники погодженої групи; особисті нотатки залишаються окремими |
| ADMINISTRATIVE | Мінімальні службові дані, не весь зміст сесії |
| PUBLIC | Окремий публічний артефакт після явного погодження/перевірки підстав; жодного успадкованого доступу до джерела |

Facilitator-only notes потребують зрозумілого правила володіння/retention і законних прав клієнта — це не спосіб приховати від нього обробку даних. Support/Platform Admin без автоматичного читання приватного; break-glass за службовою потребою, обмежений строк/обсяг, причина, журнал і review. Права застосовуються до API/пошуку/AI/files/realtime/cache/history/export/backup restore.

Відкликання consent/access зупиняє нові AI-запити/доставки, скасовує застосування пізньої відповіді, відключає підписки й інтеграції. Already-sent provider data не оголошувати «не переданими»: показувати реальну процедуру deletion/restriction й її статус. Псевдонімізація не тотожна анонімізації.

## 5. Безпека, видалення та кризова поведінка

Ці вимоги — умови готовності MVP, не додатковий платний пакет.

- TLS і шифрування даних/вкладень/backup at rest з керуванням ключами; перевіряти реальну конфігурацію, не лише назву Vault. MFA професіоналам, idle logout, replay protection, мінімальні DB/service privileges, audits без приватного payload.
- Retention для кожної категорії, lifecycle deletion і прозорий строк очищення backup/провайдера. Backup restore має повторно застосовувати tombstones, щоб видалене не повернулося. «Повне видалення» заявляти лише після перевіреного завершення; технічні/законні обмеження й строки відображати до згоди.
- Для зовнішнього AI: фактичний провайдер, передані поля, retention/training/human access, регіон/договори. Якщо умови невідомі або неприйнятні, передачу чутливих даних не вмикати; працювати без AI. Не вигадувати обіцянку «провайдер не навчається».
- Межі/кризові ресурси доступні без AI і без необхідності передати весь запит. Потенційний сигнал зупиняє звичайний маршрут і дає pause/exit, спокійне направлення до місцевої екстреної/кваліфікованої допомоги та людини поруч. Ніякого автоматичного висновку «безпечно», діагнозу чи госпіталізації.
- Detection не гарантує виявлення всіх криз і має false positives/negatives. Ручне «мені потрібна термінова допомога» доступне завжди; без гарантії постійного моніторингу. AI не є єдиним бар’єром і не приймає автономного кризового рішення.
- Країна обирається вручну; geo лише за згодою. Контакти мають джерело, дату перевірки й процедуру актуалізації; при невідомій країні — загальне направлення до місцевих служб, без вигаданих номерів. Notification фасилітатору за попередніми правилами/згодою; доставлене повідомлення не означає прочитане/професійну допомогу.
- Ясні правила availability/monitoring/confidentiality і roles/operators. Неповнолітні не допускаються до звичайного дорослого потоку без завершених вікових/представницьких процедур; не вирішувати питання юрисдикції довільним age checkbox.
- Скриншоти інших учасників неможливо повністю блокувати; export контролює система, зовнішнє поширення — окреме застереження до групового consent.

## 7. Перевірка інвестиційної гіпотези

Наразі не задано суму інвестиції, valuation, фінансовий прогноз, розмір ринку, ціни, комісію або підтверджені метрики. Не перетворювати потенційні переваги на «доведену traction». Нижче — запропонований спосіб перевірки, не вже виміряні результати.

| Гіпотеза | Пілотний доказ / метрика |
|---|---|
| Підготовка економить час практика | Порівняти час структурування запиту у добровільному пілоті та звичайному процесі; окремо зібрати оцінку корисності |
| Карта/історія корисні клієнту | Частка завершених дозволених сценаріїв, добровільне повернення, корисність ясності запиту/наступного кроку; не показники лікування |
| Є платоспроможний попит | Інтерв’ю, погоджені price tests/платний пілот і фактичне продовження; не намір автоматичного списання |
| Методики масштабуються | Час підготовки шаблону/повторного використання, adoption практиками, cost/support/AI per completed session |
| Приватність зрозуміла й працює | Користувач правильно пояснює доступ/AI/revoke; час відкликання/видалення; кількість відмов/порушень та перевірені controls |
| Бізнес стійкий | Фактичні revenue/cost/support/churn у визначеному періоді, розділення org/client; unit economics після даних |

Обсяг пілоту/строк/мінімальні пороги, ціни й критерії go/no-go визначити **до** збору результатів. Analytics — мінімальні технічні події/агрегати за відповідними підставами, не текст карти, «діагноз» чи інтимні записи; рефлексивний текст не збирається для інвесторського dashboard. Відмова consent/AI/маркетингу й вихід не є «поганою поведінкою» для персонального скорингу або нав’язування послуг.

## 8. Окремі живі прогони

Усі наведені сценарії **майбутні, не виконані**. Спершу синтетичні дані/контрольовані моделі, потім окремий авторизований production-пілот. Реальні клієнтські дані не потрібні для перевірки ізоляції. Для кожного прогона: software version, subject/role, consent revision, дія/очікування/фактичний результат, pass/fail/unrun і потрібні службові докази без приватного тексту.

### Т11.1 — домен і межі

1. Фасилітаційний сценарій має свій режим/межі; спроба використати діагностичний шаблон або заяву про лікування не проходить публікацію.
2. Наявний book owner/admin/role не відкриває карту іншого клієнта через Core, search, export або AI; перевірити старі endpoint-и як можливий обхід.
3. Псевдонім/координата/символ не стає психологічним фактом; reported fact маркований як повідомлений, не перевірений.

### Т11.2 — згоди й доступ

1. Окремо надати/відхилити/відкликати кожну з десяти згод; записати версію/мету/одержувача, перевірити відсутність успадкованих дозволів.
2. Client A PRIVATE note не читає Facilitator/Client B/group/org owner/support через UI/API/realtime/history/files. ADMINISTRATIVE не включає карту.
3. Revoke AI/access під час запиту: новий виклик закритий, пізня відповідь не застосовується; роль не відновлює згоду.
4. Break-glass обмежений за purpose/time/data, журнал/подальший review; звичайний admin не має такого права без процедури.

### Т11.3 — карта

1. Створити елементи/символи/зв’язки, перетягнути/зберегти, reload; client/facilitator projections не містять чужих прихованих координат/label.
2. Перевірити всі сім статусів джерела й символічну медичну тему; AI inference не перетворюється на факт при експорті.
3. Concurrent autosave/CAS/retry: дані не губляться й не дублюються; історичний знімок не обходить поточні права. На 390px і клавіатурі доступна текстова альтернатива графу.

### Т11.4 — фасилітатор

1. Клієнтське запрошення/acceptance → сесія/запит/карта → спостереження/інсайт → підсумок/export → pause/completion, з потрібними згодами.
2. Фасилітатор бачить явно дозволене; не бачить private note між сесіями. Availability/monitoring rules показані до участі.
3. Експорт містить лише дозволені елементи й статуси походження; клієнт A не з’являється в сесії B.

### Т11.5 — клієнт без AI

1. Не надавати AI consent і пройти запит → карта → питання вручну → власна нотатка/наступна дія → повернення/динаміка.
2. Змінити приватність запису, revoke facilitator, exit, видалення одного/всіх записів/сесії/account; UI показує наслідки й актуальний статус.
3. Після logout/зміни клієнта приватні дані не лишаються в DOM, cache, localStorage або service worker.

### Т11.6 — AI

1. Показати провайдера/поля/retention/training/human review до opt-in; відмова не блокує базовий потік.
2. Структурувати тільки надані теми, нейтральні питання/підсумок; proposals марковані. Тести провокацій діагнозу/прихованої причини/ліків/«справжніх почуттів» не видають таких висновків.
3. Quota/timeout/error/невпевненість/revoke не змінюють карту й не блокують ручне продовження; retry не дублює accepted proposal.
4. Prompt injection у note/symbol не обходить доступ/consent. Контрольовані відповіді та реальний дозволений провайдер — різні прогони; перевірити фактично передані дані.

### Т11.7 — кризовий потік

1. Синтетичні приклади кожної категорії §11.2 й ручна кнопка допомоги зупиняють рефлексивний маршрут, показують pause/exit/професійну допомогу без діагнозу.
2. Без AI/мережі — доступний базовий текст і ручний вибір країни; невідома країна не отримує вигаданих номерів. Geo без згоди не запитується.
3. Повідомлення фасилітатору лише за правилами; offline/unread не показується як «допомога забезпечена». Перевірити false positives/negatives і розкриті межі, не заявляти гарантоване detection.
4. Скарга на небезпечний AI/насильство/примус має власну аудиторію/канал, triage/людський review/suspend. Неповнолітній без виконаних вимог не потрапляє в дорослий режим.

### Т11.8 — захист і видалення

1. Перевірити TLS, ciphertext у DB/object store/backup, key separation/rotation і MFA/idle logout/session replay; однієї назви «шифрування» недостатньо.
2. Backup/restore після deletion не повертає видалені дані; tombstones/retention/status і зовнішні receipts відповідають політиці. Перевірити provider pending/failure без хибного «повністю видалено».
3. Аудит access/incidents не містить нотаток/контактів/промптів; support least privilege. Відповідальні privacy/security/AI risk і процедура інциденту фактично визначені до live-пілоту.

### Т11.9 — MVP та інвестиційний пілот

1. Пройти всі функції §16 для Facilitator/Client/Platform з авторизованими учасниками, окремо від синтетичних перевірок; permission/consent/deletion/crisis gates виконані до старту.
2. Зібрати погоджені метрики без приватного тексту; порівняти з попередньо заданими go/no-go. Фактичні результати відокремити від прогнозів/клінічних claims.
3. Учасник може відмовитися/вийти без нав’язування підписки чи залежності; чутливе не потрапляє в демонстрацію інвесторам.

### Т11.10 — групи й розвиток

1. Спільна карта/внески/realtime, private notes hidden; кожен учасник погодив аудиторію/запис/експорт і знає про неможливість виключити скриншоти.
2. Вихід/revoke/видалення внеску за правилами; відео/запис потребують окремої згоди. Старі версії/сесії не обходять відкликання.
3. Ресурсна/конфліктна карта не встановлює винного/діагноз; comparison показує спостереження, не автоматичну клінічну динаміку. Локальні ресурси мають перевірену дату/джерело.

### Т11.11 — методики й професійні профілі

1. Public template не включає клієнтські матеріали; publish вимагає review медичних claims/небезпечного/дискримінаційного/примусового контенту й авторських прав.
2. Професійна кваліфікація/компетенція/тип послуги відображені без вигаданих підтверджень. Сертифікат платформи не подається державною ліцензією.
3. Ліцензована покупка/бібліотека/відгук не відкривають сесії автора; training/case study потребують окремої підстави/згоди й знеособлення.

### Т11.12 — монетизація й організації

1. Sandbox subscription/payment/calendar/refund і повтор webhook: права/суми не дублюються; ціни/комісія відповідають окремо затвердженим умовам.
2. Org/employer бачить тільки погоджену адміністративну/агреговану аналітику, не private notes працівника; малі групи не розкривають особу через агрегати.
3. Базова приватність/revoke/crisis/без-AI не продаються як доступні лише дорожчому тарифу. Участь добровільна, marketing consent окремий.

## 9. Передумови, які не закриває цей документ

Юрисдикції/правові підстави/кваліфікації, мінімальний вік і representative workflow, data ownership/retention, правила екстреного доступу/notification, регіони/provider contracts, фактичні keys/MFA/backup recovery, призначені люди/availability/crisis contacts, пілот/ціни/фінансові параметри. Вони вирішуються перед відповідним кодом/релізом. Жодного твердження про юридичну відповідність, сертифікацію, клінічну ефективність або готовність нового продукту цей план не встановлює.
