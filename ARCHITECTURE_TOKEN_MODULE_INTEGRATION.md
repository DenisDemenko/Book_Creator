# Інтеграція модуля обрахунку токенів (Modul_token) у Book_Creality

**Статус:** план на затвердження, за підсумками grill-me сесії 2026-08-22.
Нижче — рішення, до яких дійшли по кожній розвилці, і що саме буде зроблено.
Джерела фактів: `Book_Creality/ARCHITECTURE_CHAT_SESSIONS.md`, `server/chatRoutes.ts`,
`server/pricing.ts`, `server/subscriptions.ts`, `server/store.ts`,
`Modul_token/server.js`, `Modul_token/src/services/*`, `Modul_token/src/components/*`.

---

## 1. Ключове рішення: розширюємо наявний чат, а не будуємо новий

У Book_Creality вже є протестована фіча "Чат-сесії з LLM" (`server/chatRoutes.ts`,
таблиці `chat_sessions`/`chat_messages`, 71 тест у `npm run test:chat`). Її єдине
обмеження — рушій (`engine: 'gemini' | 'gpt' | 'claude'`) один, фіксований на
рівні сервера при старті (`registerChatRoutes(app, deps)` викликається один раз
у `server.ts` з одним `deps.generate`); користувач модель не обирає.

**Замість** перенесення окремого UI/сесій/сховища Modul_token як паралельної
фічі — розширюємо `engine`/`generate` цієї фічі до 6 провайдерів і додаємо вибір
моделі. Схема БД, роути, existing 71 тест лишаються; додається лише нове.

Це напряму закриває питання, яке автор фічі сам залишив відкритим у розділі 9
`ARCHITECTURE_CHAT_SESSIONS.md`: *"Мультимодельність: користувач обирає модель
сам, чи вона фіксована на рівні сервісу?"* — відповідь: **обирає сам**.

## 2. Що НЕ входить у цей етап

- Окремий UI/сесії/дизайн Modul_token як самостійний розділ — відхилено.
- Статичний калькулятор-довідник цін без прив'язки до реального акаунту — відхилено.
- Доступ для Free/Start — фіча лишається Pro/Ultra (+ адмін).
- Стрімінг відповіді (SSE), сумаризація витісненого контексту, retention-політика
  історії — не чіпаємо, це окремі відкриті питання з розділу 9 наявного документа,
  не пов'язані з підключенням нових провайдерів.
- Виправлення адмінської вкладки "Витрати на API" — **не є частиною цього плану**.
  За вашим уточненням, вона спроектована в Google AI Studio й ще не тестувалась
  вами; статично код виглядає підключеним коректно (роут `/api/admin/usage`
  зареєстрований, `registerAdminRoutes(app)` викликається). Перед тим як щось
  у ній міняти — окремий крок: **ви тестуєте її як є**, і лише за наявності
  конкретного бага заводимо його окремо. Новий трафік від чату однаково піде
  в той самий `usage_log`, який ця вкладка читає, — тож розширення чату
  автоматично дасть їй більше реальних даних для перевірки.

## 3. Провайдер-рівень: що переноситься з Modul_token

`Modul_token/server.js` вже має робочі, реальні (не симуляційні) проксі-роути
до 3 провайдерів, яких немає в Book_Creality:

| Провайдер | Апстрім | Автентифікація |
|---|---|---|
| DeepSeek | `https://api.deepseek.com/chat/completions` | `DEEPSEEK_API_KEY` (env) або ключ користувача |
| Groq (Llama) | `https://api.groq.com/openai/v1/chat/completions` | `GROQ_API_KEY` (env) або ключ користувача |
| Mistral | `https://api.mistral.ai/v1/chat/completions` | `MISTRAL_API_KEY` (env) або ключ користувача |

Переносимо саме цю **серверну** логіку (не клієнтські `src/services/*Service.ts`
з Modul_token — ті лише звертаються до його ж проксі з браузера, нам потрібен
безпосередньо серверний виклик). У Book_Creality це стає новим модулем
`server/chatProviders.ts`: по одній функції на провайдера з єдиною сигнатурою

```ts
type Generate = (prompt: string, systemInstruction: string, modelId: string)
  => Promise<{ text: string; inputTokens: number; outputTokens: number }>;
```

`chatRoutes.ts` замість одного зашитого `deps.generate` отримує **вибір
генератора за `modelId` сесії** — `chat_sessions.model_id` вже існує в схемі,
просто досі завжди дорівнював фіксованій серверній моделі. Нове поле в БД не
потрібне: `model_id` починає відображати реальний вибір користувача
(`gemini-3.7-flash`, `gpt-4o`, `claude-sonnet-5`, `deepseek-chat`,
`llama-3.3-70b-versatile`, `mistral-large-latest` тощо), а провайдер
визначається по ньому через невелику мапу `MODEL_TO_ENGINE`.

## 4. Ключі API

Патерн з `Modul_token/server.js` (`clientKey || process.env.X_API_KEY`)
переноситься як є — узгоджується з вашим рішенням лишити можливість вставити
власний ключ:

- **Основний шлях**: `DEEPSEEK_API_KEY`, `GROQ_API_KEY`, `MISTRAL_API_KEY` в
  `.env` сервера (як зараз `OPENAI_API_KEY`/`GEMINI_API_KEY`/`ANTHROPIC_*`) —
  спільні для всіх Pro/Ultra користувачів.
- **Опційний override**: поле в налаштуваннях користувача (аналогічно
  `Settings → DeepSeek API Key` в Modul_token) — якщо заповнене, йде в запит
  замість серверного ключа.

## 5. Тарифи (`server/pricing.ts`)

Додаються таблиці для DeepSeek/Groq/Mistral за тим самим принципом, що вже є
для Gemini/GPT/Claude (`inputPerMillionUsd`/`outputPerMillionUsd`, override
через env, `updatedAt`). Орієнтир для DeepSeek (звірено на офіційному
`api-docs.deepseek.com` у поточній сесії, серпень 2026):

| Модель | Вхід (off-peak / peak) | Вихід (off-peak / peak) |
|---|---|---|
| DeepSeek-V4-Flash | $0.22 / $0.44 за млн | $0.66 / $1.32 за млн |
| DeepSeek-V4-Pro | $0.66 / $1.32 за млн | $1.98 / $3.96 за млн |

Тарифи Groq і Mistral я в цій сесії не звіряв з їхніх офіційних сторінок —
перед впровадженням це окремий крок звірки (аналогічно до того, як вже
задокументовано в `server/pricing.ts` для GPT: "якщо модель інша — перевірте
ціну вручну").

`priceForTextEngine` розширюється відповідними гілками; решта пайплайна
(`priceForTextEngine` → `chat_messages.cost_usd` → `chat_sessions.total_cost_usd`
→ `usage_log`) не змінюється — саме так вартість чату й далі бачить адмінська
вкладка "Витрати на API".

## 6. Квоти (нове)

За зразком наявного `checkImageQuota()` у `server/subscriptions.ts` (той самий
принцип: адмін без лімітів, ліміт по плану, скидання на початок періоду
підписки) — нова `checkChatQuota()`, але **по $, не по кількості**, бо вартість
повідомлення сильно залежить від моделі.

Нове поле в `PlanDefinition`:

```ts
chatQuotaUsd: number | null; // null = без ліміту (адмін)
```

| План | Ліміт/міс |
|---|---|
| Pro | $5 |
| Ultra | $20 |
| Адмін | без ліміту (як і зараз для `imageQuota`) |

При вичерпанні — **жорсткий ліміт**: `POST /api/chat/sessions/:id/messages`
повертає `403` з поясненням (як зараз `requirePlanAtLeast` пояснює брак плану),
до оновлення ліміту в наступному періоді або підвищення плану.

## 7. UI-зміни

**а) Наявний чат-інтерфейс** (компонент(и) за скріншотами
`screenshots_chat/01_chat_full_window.png`, `02_chat_modal.png` — точний файл
компонента визначається на етапі реалізації, у наданих файлах він не
зустрівся під очевидною назвою): додається селектор моделі/провайдера з 6
варіантів. Дизайн лишається нативним Book_Creality — це узгоджується з вашим
уточненням, що дизайн Modul_token важливий саме для тарифів/аналітики, не для
вікна чату.

**б) Нова вкладка в адмінці — "Тарифи та аналітика ШІ"**: переносяться
`Modul_token/src/components/ModelPricingView.tsx`, `EditPricingModal.tsx`,
`AnalyticsView.tsx` у дерево Book_Creality **як є**, з дизайном без змін.
Ізоляція стилів — CSS-неймспейс: кореневий клас (напр. `.token-module-scope`)
навколо перенесеного піддерева, під яким живуть стилі й змінні з
`Modul_token/src/index.css` (там уже своя система CSS-змінних — `--surface`,
`--primary` тощо — без конфлікту з `Book_Creality/src/index.css`, доки обидва
не потрапляють в один без-скоуповий шар). `AnalyticsView` перепідключається на
реальні дані з `usage_log`/`chat_sessions` Book_Creality замість власного
сховища Modul_token.

## 8. Послідовність робіт

1. `server/chatProviders.ts` — перенесені й адаптовані під Node/Express
   виклики DeepSeek/Groq/Mistral (+ рефактор наявних Gemini/GPT/Claude
   генераторів під єдину сигнатуру `Generate`).
2. `server/pricing.ts` — нові тарифні таблиці (DeepSeek готовий, Groq/Mistral
   — звірити).
3. `server/chatRoutes.ts` — `deps.generate` стає вибором за `model_id` сесії
   замість одного фіксованого генератора; `POST /sessions` приймає бажану
   модель.
4. `server/subscriptions.ts` — `chatQuotaUsd` у `PlanDefinition`,
   `checkChatQuota()`, підключення як перевірка перед викликом моделі в
   `POST /messages`.
5. Клієнт: селектор моделі в наявному чаті.
6. Перенесення `ModelPricingView`/`EditPricingModal`/`AnalyticsView` з
   CSS-неймспейсом, перепідключення на реальні дані Book_Creality.
7. Розширення `scripts/test-chatSessions.mts` новими провайдерами (позитивний
   і негативний сценарій на кожен, за зразком наявних 71 тесту) + нові тести
   на `checkChatQuota`.
8. **Ви тестуєте вкладку "Витрати на API"** окремим кроком — за результатом
   вирішуємо, чи потрібен окремий баг-фікс поза цим планом.

## 9. Ризики

- **Groq/Mistral тарифи не звірені** в цій сесії — до впровадження звірити на
  офіційних сторінках, як зроблено для DeepSeek.
- **$-квота, а не квота повідомлень** — точність залежить від точності
  тарифів; якщо тариф застарів, ліміт спрацює неточно (за прикладом наявного
  коментаря в `pricing.ts`: краще недооцінити вартість, ніж завищити).
- **Немає єдиного UI-компонента чату**, знайденого статично — перший крок
  реалізації включає його ідентифікацію (скріншоти є, файл — ні).
- Успадковані ризики з `ARCHITECTURE_CHAT_SESSIONS.md` (вартість контексту,
  точність usage-даних від провайдера, ручна звірка тарифів) поширюються і на
  нові провайдери без змін.
