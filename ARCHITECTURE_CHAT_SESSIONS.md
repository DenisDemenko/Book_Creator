# Чат-сесії з LLM: архітектура та план реалізації

**Крок 2 — технічний план.** Backend-сервіс, через який користувач веде окремі
чат-сесії з моделлю: сервіс пам'ятає історію діалогу, зберігає її в БД і показує
використання токенів та накопичену вартість сесії.

Нижче — не абстрактна пропозиція: план описує рішення, які я вже реалізував і
перевірив тестами. Посилання на файли — з робочого репозиторію.

---

## 1. Сутності та схема даних

Дві таблиці. Розділення на сесію й повідомлення — тому що лічильники сесії
читаються на кожен показ списку розмов, а повідомлення — лише при відкритті
конкретної сесії.

**`chat_sessions`**

| Поле | Тип | Призначення |
|---|---|---|
| `id` | TEXT PK | ідентифікатор сесії |
| `user_id` | TEXT NOT NULL | власник; усі запити фільтруються по ньому |
| `title` | TEXT NOT NULL | автозаголовок з першої репліки користувача |
| `model_id` | TEXT NOT NULL | яка модель обслуговує сесію |
| `total_input_tokens` | INTEGER | накопичено вхідних токенів |
| `total_output_tokens` | INTEGER | накопичено вихідних |
| `total_cost_usd` | REAL | накопичена вартість сесії |
| `message_count` | INTEGER | скільки реплік у сесії |
| `created_at` / `updated_at` | TEXT | ISO-час |

Індекс: `(user_id, updated_at DESC)` — саме цим запитом малюється список розмов.

**`chat_messages`**

| Поле | Тип | Призначення |
|---|---|---|
| `id` | TEXT PK | |
| `session_id` | TEXT NOT NULL FK → `chat_sessions(id)` | |
| `role` | TEXT | `user` \| `assistant` |
| `content` | TEXT | текст репліки |
| `input_tokens` / `output_tokens` | INTEGER | заповнені лише для реплік асистента |
| `cost_usd` | REAL | вартість саме цієї відповіді |
| `created_at` | TEXT | |

Індекс: `(session_id, created_at)` — вибірка історії по порядку.

**Чому вартість зберігається двічі** (у `chat_messages.cost_usd` і в
`chat_sessions.total_cost_usd`). Це свідома денормалізація: лічильник у сесії
дає O(1) на список розмов, а порядкові записи лишаються джерелом правди —
`total_cost_usd` завжди має дорівнювати `SUM(chat_messages.cost_usd)`. Ця
рівність перевіряється тестом, тож розходження лічильника не проскочить тихо.

## 2. REST endpoints

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/api/chat/sessions` | створити сесію → `201 {session}` |
| `GET` | `/api/chat/sessions` | список сесій користувача (свіжі перші) |
| `GET` | `/api/chat/sessions/:id` | сесія + повна історія реплік |
| `POST` | `/api/chat/sessions/:id/messages` | надіслати повідомлення → відповідь моделі |
| `DELETE` | `/api/chat/sessions/:id` | видалити сесію разом з репліками |

Ключове рішення — **повідомлення є вкладеним ресурсом сесії**
(`/sessions/:id/messages`), а не пласким `/messages` з `sessionId` у тілі. Так
приналежність перевіряється одним і тим самим middleware для всіх операцій, і
неможливо випадково створити «сирітське» повідомлення.

`POST /messages` — єдиний роут, що звертається до моделі. Він атомарний з точки
зору користувача: приймає текст, зберігає його, викликає модель з контекстом,
зберігає відповідь, оновлює лічильники й повертає `{session, userMessage,
assistantMessage}` — клієнту не треба робити другий запит, щоб дізнатися нову
вартість.

## 3. Як нове повідомлення отримує контекст історії

Стратегія — **ковзне вікно останніх N реплік** (`CONTEXT_WINDOW_MESSAGES = 20`),
а не вся історія.

Причина суто економічна: вартість запиту росте лінійно з довжиною контексту.
Сесія на 200 реплік, надіслана цілком, означала б платити за всі 200 щоразу.
20 реплік покривають практичну глибину посилань у розмові («а що ти казав про
Олену?»), і при цьому тримають вартість передбачуваною.

Збирання контексту винесене в чисту функцію `buildPromptContext(history,
newMessage)` — без Express, без БД, без мережі. Тому вона тестується напряму, і
її можна замінити, не чіпаючи роути.

**Наступний крок, коли знадобиться довша пам'ять:** підсумовувати витіснений
«хвіст» окремим дешевим викликом і підкладати саммарі системним повідомленням.
Це вміщається всередину тієї ж функції — сигнатура не змінюється.

## 4. Usage-дані та розрахунок вартості

Після кожного виклику з відповіді провайдера беруться `promptTokenCount` і
`candidatesTokenCount`. Далі:

1. `cost_usd` рахується і пишеться в саму репліку асистента;
2. лічильники сесії інкрементуються;
3. та сама витрата дублюється в **загальний журнал `usage_log`** — щоб
   адміністративні графіки витрат бачили чат нарівні з рештою AI-викликів
   системи, а не окремим «сліпим» каналом.

Невдалий виклик теж потрапляє в журнал — з нульовою вартістю й `success=false`.
Без цього статистика показувала б лише успішні спроби і приховувала б проблеми
з провайдером.

## 5. Model-specific pricing (щоб формула не була «зашита» в контролер)

Усі числа тарифів живуть **виключно** в одному модулі — `server/pricing.ts`.
Контролер не знає жодної ціни; він викликає:

```ts
priceForTextEngine(engine /* 'gemini' | 'gpt' | 'claude' */, inputTokens, outputTokens)
```

Усередині — таблиця «долари за мільйон токенів» на кожен двигун, з
перевизначенням через env (`OPENAI_INPUT_PRICE`, `GEMINI_OUTPUT_PRICE` тощо) і
полем `PRICING_UPDATED_AT`, щоб було видно, коли прайс звіряли востаннє.

Наслідок: **зміна тарифу — це правка одного файлу, і жодного рядка в роутах.**
Додати провайдера — додати запис у таблицю й гілку у `priceForTextEngine`.

## 6. Обробка помилок

Свідомо розрізняю чотири різні ситуації, бо вони вимагають різної реакції
клієнта:

| Ситуація | Код | Рішення |
|---|---|---|
| Некоректний input (порожнє / > 8000 символів) | `400` | валідація до будь-яких записів у БД |
| Сесія не існує | `404` | — |
| **Чужа сесія** | `404`, не `403` | навмисно: `403` підтвердив би, що такий `id` існує |
| Не автентифікований | `401` | `requireAuth` |
| Помилка провайдера | `502` | збій зовнішньої системи, не нашої |
| Помилка БД / непередбачене | `500` | деталі — у лог, назовні лише загальне повідомлення |

Три моменти, які вважаю найважливішими:

**Репліка користувача зберігається ДО виклику моделі.** Якщо провайдер упав,
текст, який людина щойно написала, не зникає з історії — вона просто повторює
спробу. Зворотний порядок (спершу модель, потім запис обох реплік) втрачав би
введений текст саме тоді, коли користувач найбільше роздратований.

**Сирі помилки не течуть назовні.** Назовні йде зрозуміле повідомлення,
`err.message` лишається в серверному лозі. Це перевіряється окремим тестом.

**Відсутність ключа — це конфігурація, а не помилка.** Якщо ключ моделі не
налаштований, сервіс віддає `200` з явно підписаною демо-відповіддю і **нульовою**
вартістю (щоб не забруднювати статистику вигаданими цифрами). Так застосунок
лишається клікабельним у dev-середовищі без ключа. Справжній збій живого
провайдера — це вже `502`.

## 7. Модульна структура

```
server/
  chatRoutes.ts   роути + чисті функції контексту/валідації (342 рядки)
  pricing.ts      ЄДИНЕ місце з числами тарифів
  store.ts        доступ до даних; ховає, SQLite це чи JSON-файли
  db.ts           схема БД
  auth.ts         requireAuth, req.principal
scripts/
  test-chatSessions.mts   71 тест
```

Головне архітектурне рішення — **впровадження залежності для виклику моделі**.
`registerChatRoutes(app, deps)` приймає:

```ts
{ generate, modelId, engine, onUsage?, loadStyleGuide? }
```

`generate` — функція `(prompt, systemInstruction) => {text, inputTokens,
outputTokens}`. Роути не імпортують SDK провайдера й не знають, який він.

Три наслідки, заради яких це зроблено:

- **Тестованість.** Уся HTTP-поведінка перевіряється з підставним генератором —
  без мережі, без ключа, детерміновано. Включно зі сценарієм «провайдер кинув
  виняток», який інакше довелось би відтворювати штучно.
- **Заміна провайдера** (Gemini → OpenAI → Claude) не зачіпає жодного рядка
  `chatRoutes.ts`.
- Клієнт моделі живе в замиканні `startServer()`; ін'єкція розв'язує це без
  винесення SDK у глобальний стан.

Шар доступу до даних теж абстрагований: `store.ts` дає однаковий API поверх
SQLite і поверх JSON-файлів (fallback для середовищ без `node:sqlite`), тож
роути не містять SQL.

## 8. Тестування

`npm run test:chat` — **71 тест, усі проходять.** Покриття за рівнями:

- **Чисті функції:** обрізання заголовка, згортання пробілів, ковзне вікно
  контексту (зокрема — що давня історія справді відрізається, а свіжа лишається),
  валідація довжини й типу.
- **Шар сховища:** CRUD, ізоляція чужих сесій, каскадне видалення реплік,
  рівність `total_cost_usd == SUM(messages.cost_usd)`.
- **HTTP-роути** на піднятому Express із підставним генератором — позитивний і
  негативний сценарій на кожен endpoint: `201/200/400/401/404/502`, накопичення
  лічильників, збереження репліки при збої провайдера, відсутність витоку сирої
  помилки, демо-режим без ключа.

## 9. Припущення і питання до уточнення

**Припущення, які я зробив:**

1. Один користувач — багато паралельних сесій; сесії не шеряться між людьми.
2. Історія не редагується й не видаляється частково — тільки сесія цілком.
3. Стрімінг відповіді (SSE) на цьому етапі не потрібен; відповідь віддається
   цілком. Це впливає на форму `POST /messages`, тому виніс окремо.
4. Вартість показується довідково, без жорстких лімітів і блокування.
5. Валюта — USD, без конвертації.

**Питання, на які хотів би відповідь до наступного етапу:**

1. **Чи потрібен стрімінг відповіді?** Це єдине питання, що змінює контракт
   API, а не лише реалізацію — тому воно перше.
2. **Чи потрібні ліміти/квоти** на користувача (за токенами або $), і що робити
   при перевищенні — м'яке попередження чи жорстке блокування?
3. **Глибина контексту:** 20 реплік — розумний дефолт, чи є вимога тримати
   повну історію (тоді потрібне саммарі витісненого хвоста)?
4. **Мультимодельність:** користувач обирає модель сам, чи вона фіксована на
   рівні сервісу?
5. **Retention:** чи є вимога видаляти історію через N днів (GDPR / вартість
   зберігання)?

## 10. Терміни та ризики

**Чи змінився початковий дедлайн:** ні, не змінився.

**ETA на наступний технічний етап (реалізація):** описане вище вже реалізовано
і покрито тестами. На доведення до продакшн-якості під вимоги, які уточняться
після відповідей на питання вище, закладаю **4–6 годин**:

- стрімінг (SSE), якщо потрібен — ~2 год;
- квоти/ліміти — ~1,5 год;
- саммарізація витісненого контексту — ~1,5 год;
- решта — на уточнення й доопрацювання.

**Ризики, які бачу зараз:**

1. **Вартість контексту.** Без ковзного вікна витрати ростуть квадратично від
   довжини розмови (кожна нова репліка тягне всю попередню історію). Вікно це
   знімає, але ціною глибини пам'яті — компроміс варто підтвердити з вашого боку.
2. **Розходження лічильників.** Денормалізований `total_cost_usd` теоретично
   може розійтися з сумою по репліках при частковому збої. Прикрито тестом на
   рівність; якщо потрібна сувора гарантія — обгортати запис у транзакцію.
3. **Точність usage-даних.** Ми довіряємо лічильникам, які повертає провайдер.
   Якщо він їх не віддасть (буває при деяких помилках), вартість запишеться
   нулем — тобто ми радше **недооцінимо** витрати, ніж завищимо. Це навмисний
   вибір напрямку похибки.
4. **Тарифи змінюються.** `PRICING_UPDATED_AT` фіксує дату звірки, але
   автоматичної перевірки актуальності немає — потрібен регламент ручної звірки.
5. **Ліміт швидкості провайдера.** Зараз збій просто повертає `502`. Якщо
   очікується помітне навантаження, знадобиться черга з backoff — це вплине на
   контракт (`202 Accepted` + опитування статусу).
