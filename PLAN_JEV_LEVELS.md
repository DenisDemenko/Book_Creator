## 1. Що вже є (і на що спираємось)

- **`server/core/flc/contracts.ts`** (Т1.6): наші контракти, не формат
  провайдера. `CharacterSnapshot` (герой, межа знань `as_of_chapter`, канон
  автора, підтверджені факти **лише з доказом**, стани, зв'язки, останні
  появи, ситуація, дозволені дії) і `DecisionResult` (ТЗ-H §6.3:
  `selected_action`, `scores`, `raw_distributions`, `confidence`,
  `model_version`, `snapshot_hash`, `decision_trace_id`, плюс `source`
  jev / mock / llm_fallback, `corrected`, `usage`, `latency_ms`); JSON Schema
  обох — як константи TS; стабільний `snapshotHash` (sha-256 канонічного JSON).
- **`server/core/flc/jev.ts`**: `HttpJevAdapter` (REST
  `POST api.typesafe.ai/v1/systemone`, модель закріплено `jev-1.13.0`),
  `MockJevAdapter` (детермінований від відбитка знімка),
  `LlmFallbackJevAdapter` (ті самі питання — LLM зі структурованою
  відповіддю), `evaluateWithFallback`, серверний валідатор `enforceAllowed`
  (лише дозволена дія, інакше найімовірніша дозволена з `corrected`). Питання
  — **лише Choice і Score**; Noul ще немає.
- **`server/core/flc/runtime.ts`**: `AgentRuntime` і `InProcessAgentRuntime` —
  агент бачить лише зареєстровані серверні tools, незмінний scope сесії,
  ліміт викликів, таймаут, журнал лише на дописування. Рішення Н1–Н2 (#257):
  **Harness у MVP напряму не йде** (developer preview, заборони тримаються на
  плагінах, а не на ядрі); адаптер Harness пишеться під цей самий інтерфейс,
  коли Harness вийде з preview.
- **`server/core/flc/cycle.ts`** і маршрут `POST /api/projects/:id/flc/prototype`
  (лише адміністратор): повний цикл retrieval → профіль → Jev → LLM →
  чернетка; нічого не записує в канон (ТЗ-H №3). Рішення ніде не
  зберігається — кожен виклик з нуля.
- **Ядро, з якого береться стан:** профіль героя «станом на главу N» (Т1.5),
  знання героя в часі й кандидати «герой ↔ факт» (Т2.1, Т2.4 В4), теги
  подій / рішень / порогів / поворотів / розкриттів (`EVENT_TYPES`), цілі й
  потреби (`/goal`, `/need`), риси (Т2.4). Цього досить для знімків усіх трьох
  рівнів без нових таблиць стану (пам'ять героя — Т2.6).
- **Бюджет і черга** (Т0.7) і **облік витрат** (`usage_log`, Т0.9) — готові:
  рішення Jev і запасного LLM списуються так само, як решта AI ядра.

## 2. Рішення щодо даних і коду (потрібні ваші «так» — див. §6)

**Де живе код.** ТЗ-H §7.2 задає `ai/adapters/{harness,jev,llm}` і
`ai/contracts/*.schema.json`. Пропоную `server/ai/` саме з цим розкладом:
`contracts/` — справжні файли `*.schema.json` (читаються й перевіряються тим
самим `validateAgainstSchema`, TS-типи поруч), `adapters/jev` — усе з
`flc/jev.ts`, `adapters/llm` — виклик LLM через ядро ШІ, `adapters/harness` —
`AgentRuntime` з `InProcessAgentRuntime`. `server/core/flc/` лишається й
реекспортує звідти — прототип, його тест і маршрут не ламаються.

**Три рівні — один адаптер, три набори питань.** `JevDecisionAdapter.decide({
level, characterId, sceneId?, situation, allowedActions? … })`:

| Рівень | Знімок | Питання (атомарні) | Кеш до… |
|---|---|---|---|
| Стратегічний | профіль станом на главу, цілі й потреби, значущі події героя, канон автора | Choice — провідна довга ціль (з цілей героя); Score — конфлікт мотивів 0–10; Choice — траєкторія (тримає курс / вагається / змінює ціль / ламається) | наступної **значущої події** |
| Сценічний | стратегічне рішення + умови сцени (учасники, ситуація, мета, заборони) | Score — страх, довіра, ризик (набір — з конфігурації); Choice — мотив у сцені | зміни **умов сцени** або «поворот» від режисера |
| Тактичний | сценічне рішення + поточна ситуація ходу | Choice — наступна дія з дозволеного списку; Score — відповідність установленому стилю поведінки; Noul — «чи узгоджується X зі знімком» (лише допоміжно) | не кешується (лише той самий знімок) |

Набори питань — **даними, а не кодом** (типова конфігурація; згодом —
на жанр чи сцену), бо ТЗ-H §6.2 вимагає агрегувати виміри «за явною
конфігурацією жанру/сцени», а не одним надскладним питанням.

**Значуща подія (ключ стратегічного кешу).** Відбиток лише тих даних, що
можуть змінити довгі цілі героя: теги порогу, повороту, рішення,
розкриття, наслідку й події, де герой — суб'єкт чи присутній, у межах
глав знімка; підтверджені факти профілю; канон автора (картка героя);
цілі й потреби героя. **Не** значущі: емоції, звичайні абзаци, правки
тексту без таких тегів, риси інших героїв. Однаковий відбиток — те саме
рішення з таблиці, без виклику Jev. Це й перевіряє критерійний тест.

**Таблиця `character_decisions`** (ТЗ-H §10 перелічує її серед таблиць FLC;
у `task.md` вона значиться в Т2.6, але зберегти рішення «з
`snapshot_hash`, версією моделі й підставами» й кешувати рівні без неї
неможливо). Пропоную створити її в Т2.5 (міграція `0015`): `project_id`,
`character_id`, `level` (strategic / scene / tactical), `scene_id`,
`simulation_id` (порожнє, доки немає Т2.7), `turn_index`, `cache_key`,
`parent_id` (сценічне → стратегічне, тактичне → сценічне), `questions`,
`options`, `result` (нормалізована відповідь), `selected_action`,
`validation` (що перевірив і що виправив валідатор), `snapshot_hash`,
`model_version`, `source` (jev / mock / llm_fallback / **author**),
`fallback_reason`, `basis` — підстави: id абзаців-доказів і тегів, з яких
зібрано знімок (не весь знімок: приватне не дублюється в журнал), `status`
(active / superseded / awaiting_author), `usage`, `latency_ms`, хто й коли.
Т2.6 додасть решту таблиць (`character_memories`, `character_states` …).

**Серверний валідатор жорстких обмежень** (ТЗ-H §6.3, FLC 2.0 §3):
дія — з дозволеного списку і не з заборонених сценою; траєкторія — з
дозволених; оцінки — у своїх межах; розподіл — лише по дозволених
варіантах. Порушення — найкраща дозволена альтернатива з позначкою
`corrected`; альтернативи немає — **рішення автора**.

**Запасний шлях (ТЗ-H №9, §13 «Fallback», «Fail closed»):** Jev → LLM зі
структурованою відповіддю → **рішення автора** (запис `awaiting_author`,
жодного автоматичного вибору); кожен перехід — з причиною в журналі
(`fallback_reason`). Низька впевненість (`confidence` нижче порогу
конфігурації) — теж на розгляд автору, а не «як вийшло» (ТЗ-H §6.2:
confidence — для маршрутизації, не гарантія). Стан при цьому не
губиться: знімок, питання й часткові відповіді лишаються в записі.

**Harness.** Лише інтерфейс `AgentRuntime` у `adapters/harness`, наша
реалізація — основна; `HarnessAgentRuntime` — заготовка «не налаштовано»,
що чесно відмовляє, і контрактний тест: заміна реалізації рантайму не
торкається ні ядра, ні маршрутів (підготовка до ТЗ-H №10). Справжня
інтеграція — коли Harness вийде з developer preview (рішення #257).

  перехоплювачем `fetch` (у хмарі мережі до TypeSafe немає). Інтерфейсу

## 4. Перевірка

- `test:jev-levels` (пам'ять + PostgreSQL): контракти (три адаптери — одна

  тактичний щоразу, ланцюжок `parent_id`, журнал (модель, відбиток, підстави
  без приватного змісту), права маршрутів (чужий 403, читач — перегляд без
  рішень).

  `test:timeline`, `test:continuity`, `test:core-ai-roles`, `test:core-jobs`.
