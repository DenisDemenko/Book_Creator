# Т5.8 — спостережуваність, feedback, оптимізатор і вартість

Реалізація за Graph Studio §26–29, критерії №24–26; журнал #390.
Стан: реалізовано, production-приймання та якість платних моделей очікують.

| Частина | Результат |
|---|---|
| Observability | Наявний журнал/trace: час, версія, вузол, модель, токени, вартість, рішення, впевненість, перевірка, людина, помилка, повтори; додані посилання на створені канонічні сутності/зв’язки |
| Feedback | Durable початкова AI-пропозиція, фактичний prompt/input reference, Jev, правка автора та знімок фінального канону в історії пропозиції |
| Graph Optimizer | Частки прийняття/відхилення/виправлень, середні впевненість/вартість/затримка, помилки/повтори; рекомендації з доказами без мутації production |
| Cost-aware routing | Необов’язкова політика LLM-вузла: класи cheap/standard/strong, ризик, складність, бюджет, ціль затримки, версійні тарифи; явне людське схвалення високого ризику |
| Regression evaluation | Порівняння готових результатів з погодженим фінальним payload; не викликає моделі й не запускає самонавчання |

Інтерфейс: Graph Studio → «Запуски» → вибрати запуск книги →
«Аналітика, feedback та оптимізатор». Завантаження контексту й правок
явне; сервер вимагає повний доступ власника/адміністратора книги та права
Graph Studio. Керування й оцінювання також потребують права публікації схем.

## Збереження і межі даних

Використовуються наявні workflow_runs/steps/checkpoints і дописуваний
story_proposal_events; нових таблиць або міграцій немає. Початкова
пропозиція й контекст фіксуються під час створення, фінальний payload —
зі справжнього запису під час CANON_WRITE. Подальша правка канону не
переписує цей приклад. Контекст входу отримується за перевіреним посиланням
на запуск тієї самої книги. Dataset — лише workflow-пропозиції з реальною
перевіркою автором, включно з відхиленими. Старі приклади без записаного
контексту позначаються неповними; бракуючі дані не вигадуються.

Це не збір усіх довільних правок рукопису або legacy analysis_findings.
Приватні TOOL-процеси Vault/симуляції не передають свої думки/секрети до
PROPOSAL й не експортуються як feedback. Стандартний trace відображає
поля самого вузла; приховані внутрішні модельні виклики приватних
інструментів не розгортаються в цьому наборі даних.

Аналітика обмежена останніми 200 запусків і 1000 пропозицій книги;
вибірка та знаменники показані. Acceptance включає прийняття з правкою,
Correction — частку перевірених пропозицій із правками, Confidence —
середнє лише відомих оцінок. Відсутні дані позначено null. Рекомендація
за високою часткою виправлень виникає від трьох перевірених пропозицій;
інші евристики стосуються помилок і повторів. Це підказки для контрольованої
редакції prompt/context/threshold у новій версії, не автоматичний оптимізатор.

## Налаштування політики LLM

У параметрі `cost_policy` вузла LLM зберігати JSON (цифри нижче — лише
приклад конфігурації, не актуальні тарифи провайдерів):

```json
{
  "version": "my-prices-2026-10-07",
  "budgetUsd": 0.05,
  "latencyTargetMs": 3000,
  "complexity": 0.2,
  "risk": 0.2,
  "humanRiskThreshold": 0.8,
  "candidates": [
    {"modelId":"<configured-cheap-id>","tier":"cheap","inputUsdPerMillion":1,"outputUsdPerMillion":2,"latencyMs":1000},
    {"modelId":"<configured-standard-id>","tier":"standard","inputUsdPerMillion":2,"outputUsdPerMillion":4,"latencyMs":2000},
    {"modelId":"<configured-strong-id>","tier":"strong","inputUsdPerMillion":5,"outputUsdPerMillion":10,"latencyMs":2800}
  ]
}
```

Вказати реальні підтримувані ID моделей, активні платформні ключі й
перевірені тарифи/оцінки затримки. Задати `max_tokens`; без нього для
цієї політики використовується 2048. Зміна політики — зміна версії workflow.
Без `cost_policy` вибір моделі лишається наявним. Некоректна політика
відхиляється під час серверної перевірки версії та виконання.

Максимум complexity/risk визначає мінімальний клас: <0.35 cheap,
<0.7 standard, інакше strong. Серед придатних моделей вибирається
найменша оцінена вартість. Input `costRouting` може лише підняти
ризик/складність або зменшити бюджет/ціль затримки. За замовчуванням
ризик ≥0.8 зупиняє запуск до явного схвалення власника/адміністратора.
Немає придатної моделі — людське очікування без запиту; resume не обходить
нульовий бюджет. Потрібно скасувати запуск і змінити політику у новій версії.

Оцінка вартості використовує UTF-8 розмір переданого prompt, ліміт виходу
й задані ставки. Це планова оцінка, не гарантія зовнішнього рахунку:
службовий контекст провайдера та тарифи можуть відрізнятися. Аудит зберігає
ставки, кандидатів, причини відсіву, політику, вибір, резерви кожної спроби
та фактичні модель/провайдер і оцінку вартості відповіді, повернену адаптером
(`costSource: adapter_estimate`, не рахунок постачальника). Перевищення фактичного
бюджету зупиняє граф після отриманої відповіді; вже виконаний запит не
скасовує рахунок. Суми невдалих запитів резервуються за оцінкою; це не
доказ їхньої фактичної оплати. Повтор і резервна модель не можуть обходити
політику, а фатальний бюджет/скасування не запускають повтори.

## Оцінювання

API (із правами Graph Studio й книги):

- `GET /api/core/workflow-runs/analytics?projectId=…&workflowId=…`
- `GET /api/core/workflow-runs/feedback?projectId=…&workflowId=…`
- `POST /api/core/workflow-runs/feedback/evaluate?projectId=…&workflowId=…`
  з `{ "cases": [{ "proposalId": "…", "payload": { … } }] }`.

Оцінювання — exact payload match, до 50 прикладів. Відхилені/не записані
в канон приклади повертають `not_applied`, а не помилковий еталон.
Нуль оцінених прикладів — null, не успішні 100%. Чужі й дубльовані
ідентифікатори відхиляються. Семантична якість, добір порогів і зміна
інструкцій потребують окремого рішення автора; автоматичного fine-tuning немає.

Ручний сценарій: [T5.8](docs/acceptance/T5.8.md).
