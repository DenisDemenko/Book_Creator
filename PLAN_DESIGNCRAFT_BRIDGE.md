# Міст Студія ↔ DesignCraft: транспорт, API і MCP

Дослідження від 19.10.2026. Питання власника: інтеграція вже пішла «через
API» — чи не варто натомість робити MCP-сервер?

**Коротка відповідь: це не вибір «або-або».** DesignCraft має **одну** шину
команд і **три** транспорти над нею. MCP — транспорт для агента, а не для
детермінованого рендера. Але саме зараз headless MCP — єдина наявна
**довгоживуча** сесія без вікна, і це змінює порядок дій.

---

## 1. Що таке DesignCraft (`D:/Rama/designcraft`)

Rust-воркспейс, v0.7.1, clean-room переписування InDesign. Кожна дія
користувача — команда (`crates/engine/src/cmd`), і всі три поверхні ведуть у
той самий реєстр команд:

| Поверхня | Транспорт | Сесія | Доступно без вікна |
|---|---|---|---|
| CLI (`run`, `script`) | процес + файл скрипта + JSON у stdout | одноразова, вмирає | так |
| MCP (`mcp`) | stdio JSON-RPC 2.0 | **жива** (in-process `Session`) | так |
| Control-канал (`--control PORT`) | TCP, JSON-рядки, лише 127.0.0.1 | жива | **ні — лише GUI-застосунок** |

Отже «API» і «MCP» — не альтернативи. API — це шина команд; MCP і
control-канал лише по-різному її везуть.

## 2. Що студія робить сьогодні

`server/pdf/engines/designcraftEngineV3.ts` (477 рядків) запускає CLI **на
кожен крок**. На одну книгу:

- 1 прохід autoflow;
- ~log₂(сторінок) проб бінарного пошуку по `layout.documentSetup {pages}` —
  кожна проба це окремий процес, повторне читання документа з диска і запис
  нового;
- до 3 проходів вставляння ілюстрацій;
- 1 фінальний прохід (колонтитули, зміст, експорт).

Для книги на 300 сторінок це ≈ 12–14 запусків процесу, кожен з повторним
розбором і перекомпонуванням документа, через тимчасові `.dcs`-файли і stdout.

Додатково `scripts/designcraft-cli-compat.sh` показує дві тріщини:

1. **awk переписує текст скрипта**, бо прибитий публічний бінарник 0.7.1 не
   має `text.selectStory`, а justify в ньому зветься `leftJustified`. Мову
   команд правлять регуляркою на рівні shell, у production.
2. **stdout як транспорт**: шим посеред конвеєра викликає node, щоб
   **зменшити** JSON-звіт, бо `document.inspect` і `story.get` на справжній
   книзі дають сотні КБ, а запускач процесів обрізає stdout.

## 3. Зміряно

110-сторінкова синтетична книга (182 000 знаків), ця машина, теплий кеш:

| Схема | Час |
|---|---|
| A. 7 проб = 7 окремих процесів, кожен перечитує документ | **2,56 с** |
| B. ті самі 7 проб в одній сесії **+ повний tagged PDF/X-4 на 110 стор.** | **1,13 с** |

B робить **більше** роботи за менш ніж половину часу. Чесні застереження:
Windows створює процеси дорожче за Linux (production — Linux), книга
синтетична й без ілюстрацій, продакшн-співвідношення буде меншим. Напрям,
проте, не під питанням.

Перевірено окремо: одна сесія `designcraft-cli mcp` тримає документ між
викликами, `execute` пропускає **будь-яку** команду рушія, а
`file.exportPdf {standard:"x4", tagged:true}` повертає
`{path, bytes, pages, warnings}` без тимчасових файлів.

## 4. Рекомендація по транспорту

**Детермінований рендер (сервер Студії → DesignCraft): не MCP.** MCP має
форму під модель: ~25 інструментів замість сотень команд, результати
загорнуті в content-блоки з `isError`, зображення як base64 всередині
контенту. Детермінованому виклику це обгортка, з якої він нічого не отримує.

**AI-функції (агент верстає або радить): саме MCP.** Discovery, схеми,
картинки назад як content — для цього MCP і існує.

Але довгоживучої headless-сесії, крім MCP, зараз немає. Тому два шляхи:

### Шлях 1 — ✅ зроблено 20.10.2026 (запис #449)

Студія запускає `designcraft-cli mcp` і говорить із ним JSON-RPC як машина, не
як модель. Реалізовано: `server/pdf/designcraft/session.ts` (клієнт),
`renderInSession` у `designcraftEngineV3.ts` за `DESIGNCRAFT_SESSION=1`.
Команди обидва шляхи беруть з тих самих білдерів
(`server/pdf/designcraft/commands.ts`), тож верстка однакова за побудовою.

**Результат збігається побайтово** — однакова кількість сторінок і однаковий
розмір PDF (різниця 0 Б) на трьох книгах. Виміряно
(`npm run bench:designcraft-session`, три прогони, один процес Node):

| Книга | Сторінок | Файловий | Сесійний | Виграш | Процесів |
|---|---|---|---|---|---|
| коротка з ілюстрацією | 4 | 739 мс | 184 мс | 4,01× | 6 → 1 |
| довга без ілюстрацій | 38 | 2039 мс | 827 мс | 2,47× | 10 → 1 |
| книжкового обсягу | 98 | 4248 мс | 2362 мс | 1,80× | 13 → 1 |

**Виграш спадає з обсягом книги**, бо запуск процесу — фіксована вартість: на
малій книзі вона домінує, на великій обидва шляхи платять однакову ціну
компонування. Міряно на Windows, де процеси дорожчі за Linux, тож у production
виграш буде ще меншим. Головне відкрите число — те саме співвідношення на
Linux і на справжній книзі.

### Шлях 2 — маленька зміна в Rust; обґрунтування змінилось

> **Після спайку (#449): аргумент «це швидше» слабший, ніж здавалось.** На
> книзі книжкового обсягу виграш 1,80× на Windows, тобто на Linux менше.
> Робити Шлях 2 варто не за швидкість, а за те, що він дає: один процес
> замість тринадцяти, зникнення обмеження stdout (через яке в образі досі
> живе node-обрізання звіту в шимі) і можливості, недосяжні між процесами —
> двопрохідний корінець під KDP та кілька форматів експорту з однієї верстки.
> Перед тим як писати Rust, варто зміряти те саме на Linux.

Додати `designcraft-cli serve --control PORT` — headless control-сервер.
`Headless` у `crates/mcp/src/headless.rs` **уже реалізує** імена методів
control-каналу (`engine.execute`, `document.inspect`, `ui.render`,
`app.export`). Прив'язати TCP-слухач і крутити рядки в нього — приблизно 50
рядків. Виграш великий: **наявні `.dcs`-скрипти студії працюють без змін
проти живої сесії — досить додати `--connect PORT`**, бо
`designcraft-cli script --connect PORT` уже існує. Це найдешевша можлива
міграція наявних 477 рядків.

Порядок: Шлях 1 — щоб довести виграш на справжній книзі; Шлях 2 — як постійна
форма.

## 5. Жорстке обмеження, яке не можна відкрити пізніше

З `ARCHITECTURE_EXTERNAL_API_WRITERSCAN.md`: **книга живе в IndexedDB
браузера, серверна копія — дзеркало**, і наступне збереження з браузера
перезаписує серверну.

Отже **DesignCraft має лишитися рендерером знімка, а не другим джерелом
правди.** Якщо потрібен зворотний рух (автор підправив макет у DesignCraft, і
це збереглося), єдина безпечна форма — та сама, що вже працює для сканів:
DesignCraft → «Вхідні»/пропозиція → автор приймає в Студії → записується в
layout-spec книги **в браузері**. Файл `.designcraft`, що лежить на сервері як
авторитетний макет, зникне з першим натисканням клавіші в Студії — точно як
зникли б прямі записи WriterScan.

Наслідок: рішення про макет належать `PdfLayoutSpec`/темі (їдуть разом із
книгою), а не документу `.designcraft`.

## 6. Можливості, які вже є і не використані

Усе через `execute`, без нового Rust:

1. **Повні опції `file.exportPdf`** — `standard: "x4"|"a2b"`, `tagged`,
   `marks`, `bleed`, `spreads`, `compressImages`; повертає `{pages, warnings}`.
   Студія зараз експортує через `--export out.pdf` (типові значення) і потім
   відкриває PDF через pdf-lib лише щоб порахувати сторінки.
2. **EPUB і HTML із тієї ж сесії** — `file.exportEpub`,
   `file.exportFixedEpub`, `file.exportHtml`. Студія публікує на KDP/Etsy; це
   один додатковий виклик на документі, який уже зверстаний.
3. **Друкований KDP, схоже, не заблокований.** V3 оголошує
   `supportsPrint: false` (корінець і дзеркальні поля → Nova). Але `file.new`
   приймає `facingPages` і `margins: {inside, outside}` (це і є дзеркальні
   поля), `layout.marginsAndColumns {margins, adjustLayout}` змінює їх **після**
   верстки, а `file.exportPdf` вміє `bleed` і `marks`. Справжньою перепоною
   була курка з яйцем: ширина корінця залежить від кількості сторінок, а та —
   від верстки. **Жива сесія розв'язує саме це**: верстка → читаємо
   `pageCount` → рахуємо корінець → `layout.marginsAndColumns` з новим
   внутрішнім полем → перевірка overset → експорт із bleed і marks. Варте
   спайку перед тим, як вважати `supportsPrint: false` остаточним.
4. **`designcraft-cli validate-pdf FILE`** — вбудована перевірка на
   відповідність PDF/X-4. Готова брама публікації під KDP.
5. **Data merge** (`data.source.select`, `data.merge`) — для освітніх
   шаблонів і курсів.

## 7. Розбіжність версій — ✅ зроблено 19.10.2026 (запис #446)

awk-шим переписував мову команд регуляркою, у shell, у production. Перевірка
показала, що обидва його шаблони **мертві**: `text.selectStory` не емітує
жоден виробник скриптів у репозиторії, а `"align":"justify"` теж — `dcAlign()`
у `styleCommands.ts` і в рушіях V1/V2 уже віддає `leftJustified`. Причому
`leftJustified` — не пережиток старої версії, а єдине правильне написання:
рушій (і 0.7.1, і поточні джерела) на `justify` відповідає
`unknown variant 'justify', expected one of left, center, right, leftJustified,
centerJustified, rightJustified, fullyJustified, towardsSpine, awayFromSpine`.

Тому awk не замінено «розумнішим awk». Натомість:

- `server/pdf/designcraft/capabilities.ts` — проба `designcraft-cli commands`
  (кеш на процес, за шляхом до бінарника) і чиста перевірка скрипта;
- `assertScriptSupported` у `designcraftEngineV3.ts` звіряє **кожен**
  згенерований скрипт перед запуском: усі id команд мусять існувати у
  встановленому бінарнику, усі значення `align` — належати набору, який рушій
  приймає. Невідповідність зупиняє рендер із назвою кроку й команди;
- awk зі шима прибрано; лишилось тільки обрізання звіту (інша хвороба —
  ліміт stdout, лікується сесійним транспортом, п. 4);
- `scripts/test-designcraftCapabilities.mts` (`npm run
  test:designcraft-capabilities`, у ланцюгу `npm test`) тримає інваріант:
  скрипти всіх 15 тем × 2 вирівнювання чисті, `text.selectStory` перевірено в
  обидві сторони, а з живим бінарником константа `align` звіряється з
  рушієм безпосередньо.

Тобто розбіжність версій тепер **дані**, а регресія виробника скрипта більше
не маскується, а зупиняє рендер.

Node-стрибок для обрізання stdout зникає сам, коли транспорт стане сесійним.

## 8. Власний MCP-сервер Студії — окрема, теж добра ідея

Інша мета: дати **Клоду** читати книгу. У студії вже є `/api/external/v1` з
токенами `nst_` (контракт WriterScan) — MCP-сервер над цим тонкий, і модель
автентифікації вже існує. Тоді агент тримає два сервери: MCP Студії для
рукопису, MCP DesignCraft для верстки — і для AI-шляху зв'язок
студія↔designcraft не потрібен узагалі. Це і є чистий поділ: шлях рендера —
машина-машині по сесійному транспорту, творчий шлях — агент над двома MCP.

## 9. WASM-редактор у Студії — третя фаза, потрібен Rust

`apps/designcraft-web` збирає повний редактор у WASM (trunk, wgpu). Спокусливо
для «автор бачить макет у Студії». Але власна документація застосунку каже:
**у браузері control-канала немає** (сокет не послухати), File→Open/Place йдуть
через браузерний вибір файлів, save/export стають завантаженнями. Вбудувати
його в Студію — це новий мостик JS↔wasm (postMessage → команди рушія).
Справжня робота, не налаштування. На близький термін не планувати.

## 10. Як це запустити

CLI уже збудований: `D:/Rama/designcraft/target/release/designcraft-cli.exe`
(0.7.1 з джерел). **GUI не збудований** — потрібен окремий довгий build.

```sh
# Перелік і опис команд
designcraft-cli commands footnote
designcraft-cli describe file.exportPdf

# Разовий скрипт (те, що студія робить зараз)
designcraft-cli script page.dcs --save page.designcraft --export page.pdf

# Жива headless-сесія (Шлях 1): JSON-RPC у stdin
designcraft-cli mcp

# Настільний застосунок + control-канал (знадобиться для Шляху 2 як зразок)
cargo build --release -p designcraft
cargo run --release -p designcraft -- --sample --control 7979
designcraft-cli script page.dcs --connect 7979
```

## Чого це дослідження НЕ покриває

- Виграш зміряно на **синтетичній** книзі без ілюстрацій, на Windows. На
  production-Linux із справжньою книгою співвідношення буде іншим — п. 1
  порядку робіт існує саме щоб його зміряти.
- Шлях 2 (`serve --control`) оцінено за читанням `headless.rs`; код не
  написаний і не скомпільований.
- Твердження з п. 6.3 (друкований KDP можливий) — висновок із документації
  команд, а не з виконаного спайку. `supportsPrint: false` поки лишається
  правдою.
- MCP-сервер Студії (п. 8) не проєктований далі за «тонка обгортка над наявним
  зовнішнім API».
- Нічого з цього не реалізовано: це план, код студії не змінювався.
