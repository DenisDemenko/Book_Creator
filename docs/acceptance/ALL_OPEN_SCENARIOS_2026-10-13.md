## Оновлення файлів на Windows

Папка власника: `D:\Rama\Book_Creality`. Remote `production` має вказувати
на `https://github.com/DenisDemenko/Book_Creator.git`; `origin` у цій папці
може вказувати на інший репозиторій, тому оновлюємо саме `production/master`.

```powershell
cd "D:\Rama\Book_Creality"

git stash push -u -m "Local changes before T9.9 update"
if ($LASTEXITCODE -ne 0) { throw "Локальні зміни не збережено" }

git fetch production
if ($LASTEXITCODE -ne 0) { throw "Завантаження з GitHub не виконано" }

git merge --ff-only production/master
if ($LASTEXITCODE -ne 0) { throw "Оновлення не виконано — надішліть помилку" }

git log -1 --oneline
git stash list
```

Локальні tracked/untracked правки збережуться у stash; ignored файли,
зокрема `.env`, лишаються на місці. Перелік резервних копій показує
`git stash list`. Якщо локальна історія розійшлася з master, merge
зупиниться; помилку треба розібрати перед наступними кроками.
Залежності в цій зміні не оновлювалися. Після оновлення файлів:

```powershell
npm test
if ($LASTEXITCODE -ne 0) { throw "Тести не пройшли" }

npm run build
if ($LASTEXITCODE -ne 0) { throw "Збірка не завершилася" }
```

### Т9.9 — ручне приймання погоджень і видань

Статус на 13.10.2026: **НЕ ВИКОНАНО на production — 0/16 сценаріїв**.
Локальні автоматизовані модель10/0, API+SQLite33/0, API+JSON30/0,
Chromium12/0 не замінюють цей прогін. [Реалізація](../labyrinth/T9.9.md).
Оформлення виправлено в коді; [локальний візуальний звіт](../reports/T9.9-DESIGN-2026-10-13.md)
перевіряє повну Studio з тестовими особами, а не production/Firebase.

Передумови: задеплоєний Т9.9/Core v41, окремий тестовий проєкт,
завершений маршрут і прийнята приватна книга Т9.8. Записати deployed SHA,
URL книги, edition ID/версію, дату, ролі й результат кожного сценарію.
Використати звичайний вхід у незалежних профілях браузера: письменник,
два учасники, видавець/ілюстратор та гість. Наприклад, надані власником
акаунти `dahindaniel@gmail.com`, `fusionlabstudio2026@gmail.com`,
`zhdanova9301@gmail.com`; наявність їхніх grant/підписок перевірити окремо.
Паролі, cookies, токени та API-ключі до звіту не додавати.

#### 1. Авторський вхід і запрошення до погодження — НЕ ВИКОНАНО

1. Письменник зберігає нову книгу й відкриває «Видання проходження».
2. Створює версію з собою та авторами включених внесків.
3. Учасники відкривають «Видання з моєю участю» в читачі джерела.
4. Гість, сторонній і чужий адміністратор відкривають той самий приватний URL/API.

Очікується: лише учасники версії отримують рукопис для погодження;
авторські налаштування доступні власнику. Сторонні не отримують текст.

#### 2. Титульний склад і явне рішення — НЕ ВИКОНАНО

1. Додати псевдонім співавтора, редактора/ілюстратора та подяки.
2. У кожному акаунті звірити текст, власний оригінал і редакцію, ім’я й роль.
3. Спробувати погодити без кожного з п’яти підтверджень, також прямим API.
4. Після всіх підтверджень погодити від власного імені.

Очікується: неповне підтвердження відхилено; автор не може підписати
рішення іншого учасника. Публічні імена відповідають погодженому складу.

#### 3. Ліцензія й комерційні частки — НЕ ВИКОНАНО

1. Перевірити усі права захищені, CC BY 4.0 та власний текст ліцензії.
2. Увімкнути продаж; задати 90%, 110%, потім рівно 100% для всього складу.
3. Кожен учасник перевіряє свою частку й умови перед особистим рішенням.

Очікується: тільки рівно 100% приймаються для продажу; безоплатна версія
не містить прихованих часток. Зміна умов створює нову версію без старих згод.

#### 4. Відмова, мовчання й вилучення — НЕ ВИКОНАНО

1. Один співавтор відмовляється; інший не відповідає.
2. Автор пробує фінальний експорт і публікацію через форму та API.
3. Для відкликаного початкового внеску явно обрати вилучення й нову версію.

Очікується: відмова/мовчання блокують видачу. При вилученні зникає сам
внесок із нової версії, збережена робоча книга не переписується непомітно.

#### 5. Чинний редактор і пропозиції — НЕ ВИКОНАНО

1. Учасник погодження пробує відкрити повний редактор без окремих прав.
2. Власник запрошує його співавтором і надає доступ до потрібної сцени.
3. Співавтор надсилає Change Proposal, обговорює правку; власник зливає її.
4. Перевірити історію ревізій, авторство правки та внесок у новому виданні.

Очікується: погодження не відкриває редагування. Прямий запис співавтора
вимагає пропозиції. Незлита пропозиція блокує видання; схвалена правка
має джерело й потребує погодження її автора.

#### 6. Редакція після погодження — НЕ ВИКОНАНО

1. Зібрати всі згоди, потім змінити текст/назву в робочій книзі.
2. Спробувати погодити, експортувати й опублікувати стару review-версію.
3. Створити нову версію, повторити рішення; окремо змінити ім’я або обкладинку.

Очікується: застарілі дії відхилено. Нова версія має новий hash та
pending-рішення. Раніше опублікований текст залишається незмінним.

#### 7. Окрема публікація й права видавця — НЕ ВИКОНАНО

1. Погодити всі рішення; перевірити, що сама згода не публікує текст.
2. Читач/редактор без дозволу публікації пробує прямий POST.
3. Погоджений видавець із `canPublish` окремо підтверджує публікацію.

Очікується: публікує лише погоджений письменник/видавець із чинним
дозволом. Кнопка має окреме підтвердження повної публічної видачі.

#### 8. Захист старих publish API — НЕ ВИКОНАНО

1. Для непогодженої тестової `LB-STORY-…` викликати старий PDF publish
   без клієнтського поля `labyrinthStory`.
2. Підмінити текст погодженого `LAB-EDITION-…` у старому publish payload.
3. Перевірити спробу продажу версії з безоплатними умовами.

Очікується: всі обходи відхилено до створення продукту/платного виклику;
джерело й погоджений знімок перевіряються на сервері.

#### 9. Втрата відповіді, повтор і конкурентні дії — НЕ ВИКОНАНО

1. Перервати мережу після прийняття create/decision/publish/comment.
2. Повторити через кнопку повтору з тим самим ключем.
3. Відправити застарілу ревізію рішення та змінений payload з тим самим ключем.

Очікується: один результат/запис історії, без подвійного видання;
CAS і колізія ключа повертають конфлікт, а не перезаписують рішення.

#### 10. Обкладинка, титул і всі експорти — НЕ ВИКОНАНО

1. Додати дозволену PNG/JPEG, передмову та подяки; перевірити ліміт 2 МБ.
2. Після всіх згод отримати PDF, DOCX, EPUB, HTML, Markdown, JSON.
3. Відкрити PDF/Word/читач EPUB та звірити титул, metadata авторів,
   порядок глав, ліцензію, передмову й точний текст з погодженою версією.

Очікується: файли відкриваються, writer/coauthors присутні і в титулі,
і в метаданих; решта ролей у титульному складі. Приватні джерела відсутні.
Для друкарні додатково перевірити її вимоги до обкладинки й верстки.

#### 11. Публічний читач і доступність — НЕ ВИКОНАНО

1. На задеплоєній версії звірити бренд, книжкову сторінку, карту,
   світлу/темну тему та друк публічного HTML-читача зі стилями сайту.
   Реалізацію й локальний огляд описано у звіті #434.
2. Відкрити авторську панель та inbox усередині повної Студії, звірити
   шапку/меню/фон/тему й отримати скриншоти саме цього інтерфейсу.
   Використати реальний вхід і deployed SHA. Локальні скриншоти #434
   показують повну оболонку, але не замінюють цей production-результат.
3. Відкрити публічне посилання гостем у desktop, Safari/Android і на 390px.
4. Перейти між розділами клавіатурою, перевірити focus та екранний читач.
5. Звірити місце героя; переключити нижній і верхній рівні карти.

Очікується: пройдений маршрут читається без горизонтального прокручування;
маркер відповідає розділу. Невідвідані місця, чати й закриті знання відсутні.

#### 12. Відкликання до, під час і після видачі — НЕ ВИКОНАНО

1. Відкликати свою згоду перед публікацією.
2. На staging затримати PDF-рендер і відкликати згоду до його завершення.
3. Після публікації відкликати рішення; повторити guest read й export.

Очікується: публікація/пізня відповідь PDF заблоковані. Наступне читання
закрите, історія збережена; старі завантажені файли не видаляються з пристроїв.

#### 13. Відкликаний grant і вимкнений акаунт — НЕ ВИКОНАНО

1. Після згод відкликати доступ співавтора до джерела та книги.
2. Окремо вимкнути його тестовий акаунт або доступ до reader edition джерела.
3. Повторити approve/publish/export/guest read без перезавантаження UI.

Очікується: наступні серверні запити перевіряють актуальні права й не
видають текст. Пізні відповіді UI не відновлюють приватний перегляд.

#### 14. Історія незалежних видань — НЕ ВИКОНАНО

1. Опублікувати v1; змінити рукопис і ліцензію, погодити та опублікувати v2.
2. Відкрити обидва посилання й історію; відкликати тільки рішення v2.

Очікується: v1 зберігає власний текст/умови/авторство, v2 має окремі
рішення. Повний цикл двох різних маршрутів додатково проходиться в Т9.10.

#### 15. Перезапуск і відновлення — НЕ ВИКОНАНО

1. На staging перезапустити сервер після створення версії та частини згод.
2. Перевірити версії, рішення, коментарі й повтор команди після рестарту.
3. Повторити для PostgreSQL + SQLite; JSON-режим перевірити окремо.

Очікується: знімок, audit і receipts збережені; нове рішення не з’являється
саме. JSON-режим не заявляє доступність SQLite-only редакторських пропозицій.

#### 16. Приватність і зовнішня публікація — НЕ ВИКОНАНО

1. Порівняти guest HTML/metadata та файли з тестовими приватними маркерами.
2. Перевірити response headers, повтор URL після відкликання та shared cache.
3. Для погодженого продажу перевірити існуючу інтеграцію на sandbox/preview
   без реального списання; звірити застосовану версію й комерційні умови.

Очікується: `no-store`, без account IDs/email/приватних повідомлень або
непройдених сцен. Умови часток записані, автоматичні виплати не заявляються.
Реальний продаж і фінансовий облік приймаються за сценаріями відповідної
чинної платіжної інтеграції та її налаштованого облікового запису.

Для кожного результату: PASS/FAIL, дата, actor role, SHA, book/edition
версія, кроки й очікуваний/фактичний результат. Прикласти дозволені
скриншоти/файли без секретів. Відкриті сценарії перенести до Т9.10,
не відмічаючи їх пройденими лише через зелений deploy.

### Т9.10 — два різні проходження → дві окремі книги й видання

Статус на 13.10.2026: **НЕ ВИКОНАНО — 0/18 сценаріїв**.
Це наскрізне живе приймання Т9.1–Т9.9. Підготовка цього чекліста,

Використовувати окремий тестовий проєкт, власні дозволені тексти та
незалежні профілі браузера. Учасники: автор, щонайменше два читачі,
видавець, за потреби ілюстратор та гість. Акаунт адміністратора не
замінює перевірки прав іншого учасника.

Два результати позначати A та B. Зберегти окремі run ID, draft ID,
book ID, edition ID, версії й hash. **Обидва видання можуть бути v1**:
це різні книги, а не дві редакції одного проходження.

#### 1. Середовище, вхід і права — НЕ ВИКОНАНО

Зафіксувати deployed SHA, URL Studio, Core schema та тестовий проєкт.
Увійти окремими акаунтами, перевірити підписки, рольові grants і дозволи
редагування/AI/публікації. Відкрити ті самі приватні URL гостем і стороннім.
Очікується: діють серверні права; чужі ролі або переключення UI не дають
доступу. Доказ: SHA, ролі, grants та HTTP-результати без токенів.

#### 2. Канонічна карта й два прохідні маршрути — НЕ ВИКОНАНО

Автор створює нижні коридори, мости та реальні переходи між рівнями,
сцени, героя, ресурси, два маршрути й фінали. Налаштувати попередження,
запасний вихід і допустимі правила Jev; явно відкрити незмінну версію.
Очікується: геометрія, словесні описи й переходи узгоджені; технічної
безвиході немає. A і B використовують ту саму зафіксовану версію карти.

#### 3. Група A, запрошення й участь — НЕ ВИКОНАНО

Створити групу A, прийняти запрошення у незалежних профілях, обрати
псевдоніми та кандидатуру у співавтори. Перевірити чергу, голосування,
спільну дію та відкликання одного тестового запрошення.
Очікується: лише чинні учасники виконують дозволені дії; вступ або хід
не присвоює співавторство автоматично. Доказ: group/run ID та журнал.

#### 4. Маршрут A, механіки й маркер — НЕ ВИКОНАНО

Пройти маршрут A через міст, подію та дозволений обхід до фіналу.
На кожному виборі звіряти позицію/рівень героя, доступні напрями,
словесний опис, ресурси та наслідки. Окремі механіки перевіряти за
[Т9.5](T9.5.md); результат кожної записати окремо.
Очікується: рішення змінюють стан лише дозволеним способом; маркер
відповідає місцю, а Jev не вигадує прохід крізь стіну або неможливий вихід.

#### 5. Особисті знання й приватність групи — НЕ ВИКОНАНО

Додати різні знання героїв, персональні сцени й приватні тестові маркери.
Звірити UI та прямі API-запити кожного учасника, гостя й стороннього.
Очікується: чужі знання, чати й невідвідані місця не розкриваються;
спільна дія не переносить особисту інформацію іншого героя.

#### 6. Внески, псевдоніми й згода — НЕ ВИКОНАНО

Додати літературні внески двох учасників, окремо погодити використання
й відкликати один тестовий внесок. Перевірити джерело, автора й редакцію.
Очікується: включається лише дозволений текст; відкликання перевіряється
сервером. Публічний псевдонім не замінює персональну згоду.

#### 7. Завершення A й точні джерела — НЕ ВИКОНАНО

Завершити A; у Т9.8 сформувати збірку та звірити кожну подію, час,
джерело, наслідок і фінал. Для проходження від checkpoint перевірити
точну передісторію. Очікується: покинуті гілки, службові плани та приватні
маркери не стають текстом; завершений журнал залишається незмінним.

#### 8. Ручна й AI-редакція збірки — НЕ ВИКОНАНО

Перевірити ручну редакцію. Окремо, з налаштованим доступом і бюджетом,
отримати літературну пропозицію реального DeepSeek, звірити її з журналом,
відхилити одну й прийняти відредаговану пропозицію. Перевірити помилку
провайдера й відкликання згоди під час запиту.
Очікується: AI не додає неіснуючих подій, не отримує прихованих матеріалів
і не публікує самостійно; помилка не створює часткову книгу. Ручний та
реальний AI-результати записати окремо; stub не підтверджує провайдера.

#### 9. Окрема приватна книга A — НЕ ВИКОНАНО

Явно прийняти збірку A, отримати новий book ID, відкрити й зберегти книгу
в редакторі. Повторити запит після втрати відповіді.
Очікується: одна приватна книга з правильними джерелами; первісна книга,
канон і журнал не переписані. Доказ: run/draft/book IDs та серверна ревізія.

Окремо надати співавтору доступ до потрібної сцени. Надіслати Change
Proposal, обговорити й злити правку власником; звірити історію й авторство.
Очікується: саме погодження не дає редагування; незлита пропозиція блокує
фінальну версію. Автор прийнятої правки отримує власне погодження видання.

#### 11. Погодження й окрема публікація A — НЕ ВИКОНАНО

Підготувати склад, ролі, ліцензію, частки, передмову й обкладинку. Отримати
п'ять підтверджень від кожного учасника, звірити точний hash і власні внески.
Окремо опублікувати уповноваженим письменником/видавцем за [Т9.9](T9.9.md).
Очікується: сама згода не публікує; гостю доступна тільки погоджена версія.

На тій самій версії карти створити окрему групу або прогін B. Обрати

Очікується: окремий run ID, фактично інший маршрут і журнал. Копіювання

Для A і B відкрити guest HTML, PDF, DOCX, EPUB, Markdown і JSON.

Очікується: файли відкриваються в відповідних читачах, приватних маркерів
і account IDs немає, результати відповідають власним журналам та згодам.

#### 15. Заборонені дії й відкликання — НЕ ВИКОНАНО

Окремо перевірити гостя, стороннього, читача без прав редагування/публікації,

Очікується: наступні запити відхилено; B закрите, чинне A залишається

Очікується: один результат без дубля ходу/книги/видання; застаріла дія
отримує конфлікт, відкликання блокує пізню видачу. Зберегти audit/receipts.

#### 17. Відновлення й перезапуск — НЕ ВИКОНАНО

Очікується: стан відновлюється без втрат і дубля; згода не виникає сама.

Очікується: керування доступне, горизонтального прокручування немає;

- Перехід до сцени й точного абзацу, профілю героя; для інших сутностей —
  доступне джерело, для матеріалів — посилання на файл.

Перший виклик старого API запрошень також перевіряє `books.ownerId`:

Книга лишається серверним джерелом. Обмежений редактор записує лише дозволений
патч сцени. Картки доступних героїв тепер передаються також через API джерела
та історії, за `externalRef`; недозволені картки залишаються прихованими.

Коментарі й завдання зберігаються поруч із книгою в SQLite Railway,
у `collaboration_items`; сповіщення — у `collaboration_notices`.

сповіщення транзакційні; конкурентні зміни перевіряють `expectedVersion`.
Максимум 2000 записів на книгу та 500 сповіщень на одержувача.

Сервер перевіряє права на кожну ціль та повторно фільтрує сповіщення при
читанні. Чужа/відкликана ціль не виходить через API. Вміст коментарів не
розсилається через WS: оновлення читаються через авторизований API.
Secret Vault, приватні контексти й результати AI не копіюються до співпраці.

```powershell
npm run live:workflow-human-review

```

`test:workflow-human-review`: 41 перевірка у пам’яті; з
`CORE_TEST_DATABASE_URL` — додатково 41 у PostgreSQL. Використовувати нову
ізольовану тестову базу: фікстура створює книгу `book` і процеси `review_*`,

17 перевірок справжнього RunsPanel, Express API, LangGraph і Memory-сховища.

Текстова модель й Jev контрольовані, платних запитів немає.

Покрито: три рішення; незмінний канон до рішення; відмова сторонньому;
відкликаний CANON_WRITE; застаріла ревізія; неправильна форма правки;
продовження з персистентної контрольної точки; сутність і зв’язок;
повний модельний ланцюжок, походження моделі/промпту/Jev/онтології;
авторська правка, остаточний стан і рішення в трасі; технічна PAUSE перед
HUMAN_REVIEW не підміняє людське рішення.

#### Ручне приймання після деплою

Використати окрему тестову книгу, синхронізовану з ядром, із живим ID абзацу.
В Graph Studio опублікувати процес START → PROPOSAL (target entity) →
HUMAN_REVIEW (reviewer author); accept/edit → CANON_WRITE (target entity) →
END, reject → END. Запуск має містити projectId тестової книги та input:

```json
{
  "proposal": {
    "payload": {"type": "character", "name": "Тест Т5.6", "canonical": {}},
    "evidence": ["ЖИВИЙ_ID_АБЗАЦУ"],
    "confidence": 0.9
  }
}
```

1. У «Запусках» відкрити paused-процес. Переконатися, що є докази,
   перевірка й походження, а підтвердженого героя у каноні ще немає.
2. «Прийняти»: процес succeeded, герой confirmed, пропозиція CANON;
   у журналі — автор рішення й ревізія.
3. Новий запуск з іншою назвою: змінити name в JSON форми та натиснути
   «Прийняти з правками». Канон містить виправлену назву, authorEdit —
   попереднє значення та список змінених полів.
4. Третій запуск: «Відхилити». Пропозиція REJECTED, нового героя немає.
5. Поки форма відкрита, змінити пропозицію в іншій вкладці. Старе рішення
   має дати конфлікт. «Перечитати пропозицію» показує новий зміст і ревізію;
   повторне рішення працює. У двох вкладках відкрити ту саму пропозицію. Вирішити в першій;
   друга не повинна створити ще один підтверджений запис.
6. Обліковий запис із доступом Graph Studio, але без схвалення цієї книги,
   не повинен мати змоги прийняти її пропозицію. Відкликати доступ до книги
   між паузою та рішенням — відмова без запису в канон.
7. Замість ручного input під’єднати PROMPT → LLM → VALIDATOR перед PROPOSAL;
   перевірити платформний DeepSeek і реальне походження моделі/промпту.

Керування Graph Studio потребує наявного права публікації схем. Це не
надає CANON_WRITE: його перевіряють окремо для книги (власник, адміністратор
або доступ approve+, згідно з PLAN_STORY_CORE.md §2). reviewer editor додатково
вимагає роль редактора для делегованого учасника. Власник/адмін зберігає доступ.

Універсальний реєстр цього етапу підтримує entity/relation. Для fact/memory/
mention діють наявні прив’язки конвеєрів; CANON_WRITE не записує їх довільно
й не змінює текст книги. Тип сутності визначає активна онтологія.
Continuity Gate — наступне завдання Т5.7.

Не перевірено автоматично: виробнича Firebase-сесія, платний DeepSeek,
мобільний інтерфейс і реальні багатокористувацькі сесії. Перед наступним
прийманням також нагадати про відкладені переходи до джерел і паралельне
редагування/DeepSeek з Т4.3 (#380–381).

   Виходи block шлюзу й reject людського рішення ведуть до окремого END.
   У checks шлюзу задайте ["age"] або всі шість перевірок.
3. Передайте PROPOSAL payload з targetId героя, type героя, name і
   canonical: {"вік": 40}, із чинним evidence абзацу. Очікуйте block,
   видиму причину в трасі, відсутність форми схвалення та незмінний канон.
4. Відхиліть заблоковану пропозицію в реєстрі перед новою спробою:
   відкриті пропозиції одного target дедуплікуються.
5. Повторіть із віком 30. Очікуйте pass і форму людського рішення.
   Прийміть пропозицію: CANON_WRITE показує новий pass, записує схвалену
   сутність і зберігає походження. Рукопис не змінюється.
6. У новому запуску дочекайтеся форми, змініть підтверджену рису героя
   на 45 в іншій вкладці й лише потім прийміть. Очікуйте failed у
   CANON_WRITE, видиму актуальну причину й відсутність запису пропозиції.
   Так само перевірте зміну payload на суперечливий у формі «Виправити».
7. Перевірте workflow без окремого CONTINUITY_GATE: суперечлива
   схвалена пропозиція все одно блокується всередині CANON_WRITE.
8. Перевірте видалений evidence; стороннього користувача; порожній або
   невідомий checks. Некоректні дані/права не повинні дозволяти запис.
9. Відкрийте трасу на телефоні: причина має читатися без виходу сторінки
   за ширину. При потребі повторіть із реальним DeepSeek перед PROPOSAL;
   це окреме production-приймання модельного ланцюга.

Для перевірки знань нового тексту в input запуску додайте
continuityDraft: {characterId, sectionId, draftText}. Згадка таємниці,
яку герой дізнається пізніше, має блокувати запис; невідомий герой/сцена
також блокує. Без цього контексту працює перевірка вже збережених знань.

#### Правила й межі

Підтверджені та needs_review суперечності, а також повні детерміновані
висновки правил блокують. Непідтверджені AI-висновки й недостатні дані
показуються як попередження. Dismissed/resolved та проблеми незалежних
сутностей/доказів не блокують цю пропозицію.

Перевіряються time, age, knowledge, place, object, causality. Проєкція
entity-update враховує скалярні canonical-поля, що відповідають уже
підтвердженим рисам; relation-проєкція додає пропонований зв'язок лише в
пам'яті. Вкладені об'єкти й нові невідомі типи рис не аналізуються як
суперечливі риси. Немає оцінки правдоподібності Jev чи блокування всіх
ручних записів через окремий Story Core API. Повторна перевірка захищає
від змін під час людської паузи; транзакційне блокування всіх паралельних
канонічних операцій у цьому етапі не реалізоване.

Продакшн/Firebase і реальні багатокористувацькі сесії ще не прийняті.
Перед наступним production-прийманням нагадати також про Т4.3 #380–381.

#### Налаштування і ручний прогін після деплою

1. У Graph Studio → «Процеси» знайдіть опублікований системний
   semantic_change_detector. Він створюється при старті ядра; наявні
   опубліковані версії сід не перезаписує. Jev Choice має вісім категорій:
   STYLE_ONLY, CHARACTER_STATE, EVENT, RELATIONSHIP, LOCATION, TIMELINE,
   FACT, NO_SEMANTIC_CHANGE. Низька/невідома впевненість і збій обох
   провайдерів дають видиму потребу перевірки без широкого аналізу.
2. Підготуйте окремі опубліковані процеси аналізу подій і місць. Вони
   отримують change.before/after, paragraphIds, sectionIds, entityIds і
   semanticCategory. Для одного героя є також characterId; для кількох
   сутностей процес має явно працювати з entityIds. Тексти книги й канон
   автоматичний аналіз не переписує; може створювати пропозиції.
3. У «Напрямки» додайте реєстр semantic_change, варіант event та процес
   аналізу подій. Другий напрямок location прив'яжіть до аналізу місць.
   Допустимі варіанти: style_only, character_state, event, relationship,
   location, timeline, fact. NO_SEMANTIC_CHANGE не має напрямку аналізу.
   Без увімкнених напрямків автоматичних модельних запитів немає.
4. Збережіть тестову книгу з двома незалежними сценами, дочекайтеся
   початкової core_sync. Перша індексація — базовий знімок без AI.
   Повторіть збереження без змін: нових дельт і запусків не повинно бути.
5. Змініть подію лише в одному абзаці першої сцени й збережіть книгу.
   У задачах/«Запуски» очікуйте job:semantic_change → Jev → EVENT →
   один event-підграф. Вхід містить лише змінений абзац, його сцени та
   старі/нові сутності; незалежної сцени в запиті класифікатора немає.
   Відкрийте дочірній запуск з батьківської траси.
6. Змініть місце: очікуйте LOCATION і тільки location-процес. Зміна
   пробілів без зміни сутностей/порядку має дати NO_SEMANTIC_CHANGE
   без модельного запиту. Переміщення сцени має зберегти дельту позиції
   навіть без зміни тексту; опублікуйте timeline-напрямок для аналізу.
7. Вимкніть event-напрямок, повторіть зміну події. За наявності іншого
   увімкненого напрямку класифікація відбудеться, але event-підграф не
   запуститься; причина видима. Архівування детектора зупиняє також
   вже поставлені в чергу його задачі.
8. Змініть абзац повторно до виконання старої задачі. Застарілий знімок
   має пропускатися без AI; якщо правка сталася під час Jev-запиту,
   повторна перевірка має зупинити запуск підграфа. Видаліть абзац або
   сцену: дельта зберігає before та старі сутності, after = null.
9. Перевірте ліміт бюджету й скасування задачі. Бюджетний збій Jev не
   повинен спричиняти додатковий платний fallback-запит. Збій планування
   аналізу не має скасовувати збереження книги; semanticDispatch показує
   причину та число вже поставлених задач.
10. Відкрийте трасу на телефоні: категорія, причина та область зміни
    мають читатися в ширині екрана. Повторіть з реальною TypeSafe/Jev
    або налаштованим запасним AI-модулем (зокрема DeepSeek) під реальною
    сесією; цього production-приймання ще не виконано.

#### Межі

Класифікується головний тип зміни кожного абзацу, не всі можливі типи
одночасно. Події про правки карток героїв без зміни тексту сюди не входять.
Абзаци понад 4000 символів завершуються видимою помилкою, щоб не
класифікувати мовчки обрізаний текст. Це відповідає поточному ліміту
рядка Jev; chunking довгих абзаців ще не реалізований.

Кожна дельта має окрему задачу з ідемпотентним ключем. Задача має одну
спробу: збій/перезапуск не повторює автоматично платні запити; ручний
повтор доступний у «Запуски». Незавершений запуск після аварії воркера
потребує ручного розбору. Немає транзакційного блокування авторського
редагування на весь час підграфа або злиття кількох дельт однієї сцени.

Напрямок має бути активним опублікованим процесом читання/пропозицій.
CANON_WRITE, HUMAN_REVIEW, довільні TOOL і JEV_ROUTER в автоматичних
підграфах заборонені; вкладені SUBGRAPH перевіряються також. Обмеження
повторно діє під час виконання вузлів та успадковується дочірніми
запусками/повторами. Людина працює з отриманими пропозиціями окремо.

Продакшн, платний Jev/DeepSeek, повний редактор і реальні сесії ще не
прийняті. Перед production-прийманням нагадати також про Т4.3 #380–381.

### Т5.7 В3 — Adaptive Workflow

Критерій Graph Studio §39 №20: важливість зміни визначає глибину аналізу за конфігурацією процесу.

#### Реалізація

Системний процес `adaptive_workflow`: актуальність before/after → JEV_SCORE `importance` → `adaptive_dispatch` → один опублікований підграф. Новий процес додається при старті ядра; наявні версії не перезаписуються. Щоб застосувати адаптацію після core_sync, у «Напрямках» прив'яжіть потрібну категорію реєстру `semantic_change` до `adaptive_workflow`.

У вузлі `importance` налаштовуються питання, 2–10 рівнів, `scale_min`, `scale_max` і політика впевненості. У вузлі `dispatch` параметр JSON `adaptive_policy` містить пороги та id підграфів:

```json
{
  "medium": 3,
  "high": 6,
  "critical": 8,
  "low": "skip",
  "targets": {"minimal": "", "light": "", "normal": "", "deep": ""}
}
```

| Оцінка | Рівень | Дія |
|---|---|---|
| Нижче medium | LOW | skip або minimal за політикою |
| Від medium до high | MEDIUM | light |
| Від high до critical | HIGH | normal |
| Від critical | CRITICAL | deep |

Пороги включні знизу, строго зростають і лежать у шкалі. Оцінка — нормалізоване значення JEV_SCORE; позиція моделі округлюється до сотих. Різні глибини виконують налаштовані адміністратором процеси, а не одну фіксовану кількість модельних викликів. Порожній id означає «підграф не налаштований» і видиму причину пропуску. Немає прихованого запасного маршруту або автоматичного вмикання в наявних книгах.

Перед оцінкою та після відповіді повторно перевіряється джерело. Ненадійна оцінка чи запасний LLM без впевненості потребують перевірки у трасі; вони не запускають аналіз. Це не пауза HUMAN_REVIEW і не автоматичний повтор. Облік токенів і скасування проходять через бюджет черги. Автоматичні підграфи не виконують CANON_WRITE, HUMAN_REVIEW, довільні TOOL чи JEV_ROUTER; дозволені лише службові маршрутизатори детектора й адаптивного процесу. Канон автора не змінюється.

#### Автоматичний прогін

- `npm run test:adaptive-workflow`: маршрути всіх рівнів, межі, LOW minimal, інша шкала, нова версія, помилкова політика, незмінність сіда, відсутній/архівований/небезпечний підграф, застаріле джерело до/під час оцінки, невпевненість, збій провайдерів, бюджет Jev і запасного LLM, завеликий текст, реальна черга, дочірні запуски й повтор.
- `CORE_TEST_DATABASE_URL=... npm run test:adaptive-workflow`: той самий сценарій у Memory і PostgreSQL з SQL-чергою, у новій окремій тестовій базі.
- `npm run build`, потім `npm run live:adaptive-workflow`: Chromium, справжні WorkflowEditor/RunsPanel та HTTP API, зміна JSON політики в чернетці → перевірка → тест → публікація → core_sync/черга → вибраний підграф. Звіт і дочірня траса, ширина 390 px. Артефакти — окрема тимчасова тека, надрукована командою.

Модельні відповіді контрольовані, цільові підграфи тестові: це перевірка маршрутизації й конфігурації, не якості реального аналізу.

#### Ручне production-приймання

1. Перед прогоном повернутися до відкладених переходів Т4.3 (журнал #380–#381) — власник просив нагадати.
2. Відкрити Graph Studio → Процеси ШІ → Adaptive Workflow. Переконатися, що робоча версія лише для перегляду. Створити чернетку.
3. У `importance` вибрати шкалу, питання і впевненість. У `dispatch` вказати активні опубліковані процеси читання/пропозицій для minimal/light/normal/deep. Встановити різні пороги, перевірити, передати в тест і опублікувати.
4. У «Напрямках» підключити EVENT або іншу категорію semantic_change до adaptive_workflow. Використати окрему тестову книгу, права якої дозволяють роботу з ШІ.
5. Зберегти стилістичну, помітну та критичну зміни різних абзаців. У «Запусках» відкрити детектор → Adaptive → дочірній аналіз. Звірити фактичну оцінку, пороги, рівень, глибину, область абзаців і підграф. Конкретний результат оцінює реальний Jev/резервний провайдер; важливість не виводиться з назви правки.
6. Для LOW змінити skip на minimal у новій версії та повторити. Вимкнути/архівувати один цільовий процес — переконатися, що інший не запускається замість нього.
7. Змінити абзац, доки оцінка ще триває: попередній запуск має завершитись причиною stale. Права та незмінність канону перевірити під письменником; налаштування — адміністратором. Перевірити звіт на телефоні.

Production/Firebase та якість платного Jev/DeepSeek у цьому новому ланцюгу ще потребують ручного приймання. Раніше власник підтвердив, що платформний DeepSeek віддає текст; це не замінює перевірку адаптивного процесу. Т5.7 загалом відкритий: наступний В4 — Causality Engine.

### Т5.7 В4 — Causality Engine

Критерій Graph Studio §39 №23: Causality Engine створює Proposed Relation, а не мовчки змінює World Graph.

#### Що реалізовано

Процес `causality_engine`: підтверджена нова подія → кандидати з попередніх подій/рішень/цілей/станів → Jev Choice → Jev Noul → перевірена пропозиція причинного зв’язку. Для CAUSES використовується чинний тип онтології **caused_by**, напрям **наслідок → причина**. Сам процес не додає канонічного ребра.

Сід створює тільки відсутній процес, без перезапису версій адміністратора. Після core_sync нова подія з підтвердженого тегу може потрапити сюди через напрямок `semantic_change/event`. Процес також можна обрати як підграф Adaptive Workflow. Без увімкненого напрямку нових автоматичних витрат немає. Для ручного запуску передайте `{"eventId":"id сутності події"}` та id книги у Graph Studio → Запуски.

Автоматичний вхід шукає саме нові id подій у дельті абзацу. Якщо нових подій кілька, потрібен ручний вибір однієї: немає прихованого пакетного аналізу. Зміна лише картки без дельти тексту, створення AI-1 поза core_sync і історичне заповнення всіх подій не запускаються автоматично; для них є ручний eventId. Відхилені сутності/згадки та чернеткові абзаци не слугують доказами.

Кандидати мають підтверджену згадку, що передує події. Використовується час світу, коли він є в обох сценах, інакше порядок сцен; всередині сцени — абзац та позиція згадки. Флешбек, розказаний пізніше, може бути причиною. Найближчі кандидати обмежені параметром `max_candidates` у вузлі `propose` (1–20, початково 8). До моделі передається до 2000 символів кожного абзацу, а в пропозиції зберігаються id повних живих абзаців. Це обмежений пошук кандидатів, а не доказ повноти всіх причин книги.

Jev Choice має варіант none: відсутність переконливої причини завершує процес без Noul. Невідомий/виправлений вибір і невідома впевненість запасного LLM не запускають автоматичну пропозицію. У вузлі `support` можна змінити питання, поріг Noul (початково 0,7) і політику впевненості у новій версії, без зміни коду. Часова попередність сама по собі не достатня: потрібна підтримка Noul.

Джерела, стан сутностей, час і причинні зв’язки повторно перевіряються перед модельними етапами й перед збереженням. Витрати Jev/LLM проходять через бюджет задачі. Повторні/одночасні прогони не дублюють відкриту пропозицію; відхилена пропозиція для того самого знімка також не пропонується повторно. Наявний канонічний причинний зв’язок не породжує ще одну пропозицію.

Пропозиція містить два абзаци-докази (або один спільний), версію процесу, запуск і обидва рішення Jev із моделлю та впевненістю. Вона проходить чинний валідатор онтології. У трасі також видно перевірку причинності Т2.9 у проєкції Continuity Gate, без запису до рукопису чи діагностики. Блокування шлюзом не дорівнює автоматичному відхиленню: автор бачить пропозицію й перевіряє її. Запис у канон повторно проходить штатні перевірки та потребує прав автора.

#### Автоматичні перевірки

- `npm run test:causality-engine`: кандидати й флешбек, Choice/Noul, межа порогу, none, доказ/походження, незмінність канону, дедуплікація й паралельні прогони, невпевненість, збій провайдерів/бюджету, stale між етапами, конфігурація й незмінність сіда, core_sync → черга → детектор → пропозиція, заборона AI-схвалення й авторське відхилення.
- `CORE_TEST_DATABASE_URL=... npm run test:causality-engine`: той самий набір у Memory та PostgreSQL із SQL-чергою, на окремій тестовій базі.
- Після `npm run build`: `npm run live:causality-engine`. Chromium і справжні RunsPanel/StoryGraphPanel, HTTP Story Core: перегляд пропозиції → авторська правка → схвалення без зміни канону → окремий запис у канон. Звіт на 390 px, скриншоти та report.json у надрукованій тимчасовій теці.

Модельні відповіді контрольовані. Ці перевірки доводять роботу механізму, не якість причинних висновків реальної моделі.

1. Повернутися до відкладених переходів Т4.3 (#380–#381): власник просив нагадати перед наступним прогоном у production.

### Т5.7 В5 — Mystery Director

Реалізовано 07.10.2026; критерій Graph Studio №22. Процес `mystery_director`
і кнопка у Secret Vault використовують один приватний аналіз. Весь Т5.7
залишається відкритим до В6 й приймання на продакшні.

#### Як працює

World Truth — лише вибрана закрита світова таємниця з Vault. Reader Knowledge —
попередні недрафтові абзаци в порядку читання. Character Knowledge — окремі
підтверджені знання кожного героя до сцени в часі світу, з наративним порядком
як запасним варіантом. Аналіз виконується **на початок сцени**; її власний текст
не вважається вже прочитаним. Інші приватні секрети не передаються.

Один пакет Jev містить Score (п’ять рівнів, результат 0–10), Noul (ризик
передчасного розкриття) та Choice: REVEAL, HINT, MISDIRECT, HIDE, DELAY.
За ризику ≥0.7 або невиконаних умов причинності REVEAL замінюється на DELAY.
За впевненості <0.6 або невідомої впевненості — HIDE і рішення автора.
За відсутності чи збої TypeSafe використовуємо приватний LLM модуля
«Голос героя»; він не має каліброваної впевненості й не дозволяє розкриття.

Це рекомендації, а не готові фрагменти чи нові факти. MISDIRECT не робить
хибне твердження каноном. REVEAL не змінює статус секрету або рукопис.
Розкриття — окрема підтверджена дія автора через наявний сервіс Т4.1.

#### Приватна межа процесу

Graph Studio: START → приватний TOOL `mystery_director` → END. Три питання Jev
виконуються всередині приватного інструмента, а не загальних JEV-вузлів:
звичайні контрольні точки зберігають стан, тому туди не передається plaintext.
Параметри питань і пороги цього приватного інструмента задані в коді В5.

Вхід ручного запуску: id книги та JSON з `secretId`, `sceneId`,
`expectedRevision` актуального Vault. Не вставляйте сам секрет у JSON.
Запуск потребує доступу власника або адміністратора; процес не дозволений
як автоматичний semantic_change підграф. Graph Studio додатково вимагає
свої права на запуск. Зашифрований план зберігає рекомендацію та відбиток
знань; траса й HTTP-відповідь — лише типізовані оцінки, кількості й id.
Вільний текст, запити до моделі та її помилки не потрапляють у трасу.

Зміна знань або умов під час запиту відкидає план. CAS Vault відкидає
паралельний запис. Перше використання фіксує секрет навіть якщо провайдер
згодом відмовить — регенерація вже використаної істини заборонена.
REPLAY зі старою ревізією не виконує повторний запис: для нового аналізу
потрібні свіжі `expectedRevision` і ручний запуск.

Ліміти В5: до 20 підтверджених героїв, 40 000 символів попереднього рукопису
та 90 000 символів усього контексту. Завеликий контекст відхиляється,
а не обрізається мовчки. Знання героїв тут походять із підтверджених
подій, розкриттів і фактів профілю; суб’єктивні приватні спогади та чужі
таємниці не додаються. Усі перевірки використовують підставні відповіді
моделей, не оцінюють художню якість реального Jev / DeepSeek.

### Т5.7 В6 — Character Decision Engine: Simulation Mode

Реалізовано 07.10.2026, журнал #388; критерій Graph Studio №21.
Production/Firebase та якість на справжніх Jev/DeepSeek ще потребують ручного приймання.

#### Що працює

Системний процес `character_decision_engine`: START → приватний TOOL → END.
Інструмент виконує один хід існуючого прогону Magic Scene: знімок героя й
умови сцени → стратегічне, сценічне й тактичне рішення Jev → дозволена дія
→ LLM-реалізація → спостережувана подія → суб’єктивний спогад і знімок стану.
Choice обирає дію, Score оцінює мотиви/страх/довіру/ризик/стиль, Noul перевіряє
знання й межі сцени. Оцінки Noul діагностичні: не є доказом істинності.

Досвід отримують лише спостерігачі події, включно з героєм, що виконав дію.
Спогад має `simulationId`, `truth: unknown`, `character_belief`, `suggested`;
приватна думка й намір у нього не копіюються. Наступний хід бачить досвід
свого прогону, інший прогін — ні. LLM не отримує права довільно переписувати
цілі, емоції чи канонічні риси; новий стан — знімок доступних знань і пам’яті.

Усі рівні рішення обмежено початком сцени в часі світу, включно зі
стратегічним: пізніша сцена тієї самої глави більше не потрапляє в його
знімок або ключ значущих подій. Пам’ять власного прогону доступна вже після
спостереження. Кеш стратегічного рішення ізольовано за `simulationId`.

#### Автоматичний прогін

```bash
npm run test:character-decision-engine
CORE_TEST_DATABASE_URL=postgresql://... npm run test:character-decision-engine
npm run build # CSS для браузерної перевірки
npm run live:character-decision-engine
npm run test:jev-levels
npm test
npm run lint
npm run build
```

Результати локально: 44/44 Memory + PostgreSQL, 25/25 live (22 серверні
та 3 Chromium); окремий test:jev-levels — 105/105. Повторний повний
`npm test`, фінальні `npm run lint` і `npm run build` — exit 0.

PostgreSQL-команда потребує окремої тестової БД: застосовує міграції,
створює тестові проєкти. Браузерний прогін використовує Chromium, справжній
RunsPanel і локальний HTTP, включно з шириною 390 px; артефакти зберігаються
в тимчасовій теці, надрукованій командою. Моделі контрольовані, платних
запитів та входу в production цей прогін не робить.

Перевіряються незмінність рукопису/канону, майбутні знання, різні аудиторії
й прогони, низька впевненість/відсутній провайдер, авторська дія, неправильна
LLM-відповідь, повтор запиту, CAS/конкуренція, скасування, відкликаний під
час LLM доступ, зміна основи, бюджет без запасного виклику, заборона
CANON_WRITE, ремонт частково записаної пам’яті без дубля події чи моделі.

#### Ручне приймання на production

1. Перед прогоном нагадати про відкладену перевірку Т4.3 (#380–381).
   Власник або адміністратор з правом ШІ зберігає тестову книгу на сервері.
   Вибрати сцену й 2–3 підтверджених героїв; у Magic Scene увімкнути їхню
   сценічну автономність і створити прогін. Записати його `simulationId`
   та поточну `revision`; зберегти контрольну копію рукопису.
2. У Graph Studio вибрати опублікований процес «Рішення героя — симуляція».
   Якщо системного сіда немає, оновити сервер і перевірити доступність Core.
   Вказати проєкт та input:

   ```json
   {"mode":"simulation","simulationId":"<id>","expectedRevision":1,"requestId":"acceptance-cde-01"}
   ```

   `expectedRevision` замінити актуальною ревізією прогону, а не книги.
3. Запустити один хід. У Runs перевірити Simulation Mode, героя, дію,
   джерело, числові Score/Noul, ідентифікатори досвіду й станів. Траса не
   повинна містити репліку, думку, snapshot чи текст таємниці. У приватному
   протоколі Magic Scene власник перевіряє саму репліку й видиму дію.
4. Запустити наступний хід з новими revision/requestId. Герой-спостерігач
   має врахувати попередню подію. Повторити старий requestId або REPLAY:
   кількість подій і спогадів не зростає. Новий окремий прогін не отримує
   досвіду першого. Додати майбутню сцену з фактом-канаркою: герой до неї

5. При очікуванні автора нова подія не створюється. Власник поновлює

6. Порівняти рукопис і канон до/після. Не натискати затвердження в книгу:
   воно належить окремому наявному авторському шляху через гілку.
   Сторонній користувач не запускає приватну симуляцію.
7. Для реальної моделі налаштувати модуль «Голос героя» та перевірити
   платформний DeepSeek. При відсутньому Jev використовується наявний
   LLM fallback; це не перевірка якості TypeSafe. Для закритих секретів
   потрібен захищений Railway `SECRET_VAULT_KEY_BASE64`; наявний ключ
   Vault не замінювати. Зафіксувати якість реплік і джерело рішення.

#### Межі

Це один хід Magic Scene з 2–3 героями, не необмежений автономний цикл.
Canonical Mode і автоматичний semantic підграф заборонені. Запуск у Graph
Studio також потребує права керування схемами. Секрети залишаються в
наявному приватному Vault-кроці; загальні вузли не отримують plaintext.
Рішення автора, пропозиції та затвердження фрагмента не автоматизуються.
Після збою запису досвіду вже збережена подія лишається в протоколі;
повтор ремонтує пам’ять і стан, не запускаючи модель знову.

#### 1. Feedback і фінальний канон

Створити тестовий workflow PROMPT → LLM → VALIDATOR → PROPOSAL →
HUMAN_REVIEW → CANON_WRITE; гілка Reject іде до END. Наявні права,
Continuity Gate та перевірки ревізії залишаються обов’язковими.

1. Виконати чотири різні пропозиції: Accept, Edit, Edit, Reject.
2. У «Запусках» вибрати запуск цієї книги, завантажити аналітику:
   4 перевірених пропозиції, Acceptance 75%, Rejection 25%, Correction 50%.
   Інші запуски у вибірці збільшують лише кількість/метрики запусків.
3. Відкрити авторські виправлення. Знайти початковий AI-payload, prompt
   та input, confidence, Jev, автора, before/after і фінальний канон.
   У Reject фінальний канон відсутній.
4. Змінити прийнятого героя окремою авторською правкою: збережений
   фінальний приклад для попереднього рішення не повинен змінитися.
5. Сторонній користувач і учасник без повного доступу не отримують dataset.
   Порівняти дві книги: чужі приклади не з’являються у своїй.

#### 2. Оптимізатор і регресія

1. За двох правок із чотирьох прикладів є рекомендація переглянути prompt,
   контекст і поріг; показані ідентифікатори доказових запусків/пропозицій.
2. Порівняти workflow-версію до/після перегляду: жодних змін чи автопублікації.
3. У форму регресійного порівняння вставити payload прийнятого канонічного
   прикладу й його proposalId: точний збіг 100% для цього одного прикладу.
   Змінити поле — 0%. Reject — `not_applied`; чужий ID — відмова.
4. Перевірити workflow без запусків: «немає даних», без підроблених часток.

#### 3. Маршрутизація за вартістю

Приклад і правила `cost_policy`: [план](../../PLAN_WORKFLOW_OBSERVABILITY.md).
Внести реальні ID/ставки, опублікувати окремий тестовий workflow з LLM.

1. Низький ризик/складність: вибирається найдешевший допустимий кандидат.
   В trace є версія політики, ставки, оцінка, фактична модель й вартість.
2. Підняти складність до 0.5 у новій версії: cheap-клас не допускається.
3. Підняти ризик до 0.9: запуск призупинено до моделі. Натиснути
   «Схвалити модель і продовжити»: виконується один запит; звичайний
   resume і стороннє схвалення не повинні його запускати.
4. Бюджет 0 або всі моделі повільніші за ціль: платних запитів немає.
   Звичайне схвалення не обходить відсутність придатної моделі.
5. У input спробувати знизити risk і збільшити budgetUsd: авторські
   обмеження не послаблюються. Зменшити бюджет — обмеження враховується.
6. При контрольованому збої перевірити резерв кожної спроби й зупинку
   повторів після вичерпання бюджету. Резервна модель поза кандидатом
   політики не викликається. Витрати на вже виконаний запит лишаються
   в trace навіть при фінальному failed.
7. Реальні тарифи й затримки DeepSeek/Jev перевіряти окремо; оцінені
   цифри не вважати підтвердженим рахунком або гарантією latency.

#### 4. Trace та інтерфейс

На комп’ютері й 390 px перевірити час, версію, вузол, рішення/confidence,
validation/human result, модель, токени, cost, latency, retries, warnings,
errors і доступні ідентифікатори створених сутностей/зв’язків. Порожні
поля TOOL не повинні видаватися за нульові витрати прихованих моделей.
Приватні секрети/думки не стають feedback. Перевірити повернення до старої
версії: policy та збережені приклади відповідають версії того запуску.

### Т6.5 — ручний прогін співпраці

Після деплою виконати під реальними сесіями власника, співавтора й читача.
Потрібна серверна книга у SQLite; ролі та наданий доступ — у Core.

1. Власник надає співавтору edit однієї сцени. Інша сцена залишається прихованою.
2. Співавтор відкриває «Спільна робота → Пропозиції та внески», натискає
   «Завантажити зміни», обирає сцену, змінює текст і надсилає пропозицію.
   Серверний текст і ревізія не змінюються. Чужої сцени немає у списку.
3. Власник відкриває пропозицію та «Показати початковий текст». Перевіряє
   відмінність, автора й ревізію. «Схвалити та злити» створює нову ревізію
   та один внесок з початковою/результатною ревізіями й схвалювачем.
4. Повторне злиття або одночасна дія в іншій вкладці не створює ще одного
   внеску. Читач і співавтор не можуть схвалювати через прямий API.
5. Подати другу пропозицію, потім змінити ту саму книгу іншим дозволеним
   записом. Злиття застарілої пропозиції дає 409; новий текст не втрачається.
6. Відхилення лишає джерело без змін. Відкликання edit автора до схвалення
   блокує злиття. Перевірити також відкликання доступу до читання журналу.
7. Перевірити прямий PATCH і realtime від співавтора: немає тихого
   перезапису. Звичайний редактор із edit може змінити дозволену сцену;
   її правка також з'являється в журналі внесків.
8. В Graph Studio → «Граф співпраці» вказати ID книги. Перевірити п'ять
   представлень, реальних людей і ролі, області доступу, внески й розгляд.
   Учасник з доступом тільки до однієї сцени отримує 403 на повний граф.
9. У START контрольного процесу задати
   `collaboration_events=["CONTRIBUTION_RECORDED"]`, перевірити та
   опублікувати процес. У каталозі подій вказати його ID й запустити за
   внеском. У «Запусках» перевірити `input.collaborationEvent`, правильну
   книгу та production-версію. Подія іншої книги або непідписаний тип
   не запускає процес. Не починати з платної генерації для цього тесту.
10. Повторити подання/схвалення та перегляд графа на ширині 390 px.

Автоматичний прогін:

```bash
npm run test:collaboration-contributions
npm run build
npm run live:collaboration-contributions
npm test
```

Для інтеграції з PostgreSQL використовувати нову тестову базу:

```bash
CORE_TEST_DATABASE_URL=postgresql://.../fresh_test_db npm run test:collaboration-contributions
```

Юридичні погодження співавторства, замовлення/результати фахівців та

змінну SECRET_VAULT_KEY_BASE64; чинний ключ сховища не замінювати.

### Т6.6 — ручне приймання

Після деплою: серверна книга у SQLite, Core, власник, дизайнер/ілюстратор
і учасник з доступом до однієї сцени. Використати окрему тестову книгу.

1. В Graph Studio перевірити палітру COLLAB_QUERY з вісьмома операціями
   та COLLAB_PROPOSAL. Опублікувати контрольний граф START → COLLAB_QUERY
   (GET_AVAILABLE_CONTEXT) → PROMPT → LLM → END. Шаблон PROMPT:
   `{{query_q}}`, де q — ID query-вузла.
2. Для обмеженого учасника перевірити дозволену сцену в контексті. Інша
   сцена, приватні нотатки книги та чужі учасники не повинні потрапляти

3. FIND_SPECIALIST з args.roleId=designer: власник бачить активного
   дизайнера. Обмежений учасник не отримує приховані профілі інших людей.
4. GET_ACCESS_SCOPE повертає власні права; GET_OPEN_TASKS — тільки
   завдання з доступними цілями; GET_CONTRIBUTIONS — дозволені сцени.
   GET_DELIVERABLES повідомляє недоступність до реалізації етапу 7.
5. Контрольований процес: налаштувати LLM cost_policy з risk=0.9, щоб
   після COLLAB_QUERY він чекав явного схвалення моделі. Відкликати
   доступ, потім продовжити. Перед LLM процес має зупинитися. Якщо дані
   змінилися, потрібен новий запуск. Під чужими правами не читати/керувати
   журналом або підпроцесами співпраці.
6. COLLAB_PROPOSAL: title=«Створити обкладинку», target — JSON доступної
   сцени, candidateId — ID активного дизайнера. Після запуску є pending
   пропозиція, але ще немає завдання, призначення чи нового доступу.
7. Для model output: LLM → VALIDATOR з JSON-схемою title/target →
   COLLAB_PROPOSAL(from_output=true). Перевірити, що недоступна ціль
   або неактивний кандидат не проходять серверну перевірку.
8. Власник відкриває «Спільна робота → Пропозиції та внески → Пропозиції
   завдань ШІ», завантажує їх, читає причину й явно вводить ID виконавця.
   «Підтвердити завдання» створює один запис у «Коментарі й завдання» та
   сповіщення виконавцю. Повторне підтвердження не дублює завдання.
9. Відхилення не створює завдання. Відкликання прав автора або доступу
   виконавця до цілі перед підтвердженням блокує дію. Ролі та наданий
   доступ після будь-якої дії лишаються такими, як були.
10. Повторити розгляд на 390 px. Перевірити відсутність переповнення й
    помилок консолі.

```bash
npm run test:collaboration-ai
npm run build
npm run live:collaboration-ai
npm test
```

PostgreSQL: `CORE_TEST_DATABASE_URL=postgresql://.../fresh_test_db npm run test:collaboration-ai`.

Платні моделі та Firebase перевіряються окремо після контрольованого
прогону. Перед production згадати відкладений Т4.3 й захищений
SECRET_VAULT_KEY_BASE64; чинний ключ Vault не замінювати.

### Т7.1 — основа Creative Studio

Реалізація в двох репозиторіях за рішенням #304. Читати після деплою
Marketplace API + Prisma-міграції, Marketplace Web і Studio.

#### Межі етапу

Профіль фахівця — розширення SellerProfile, окрема модерація, один userId.
Старі заявки продавців залишаються такими самими. Нова чернетка фахівця
має sellerApplicationSubmitted=false і не потрапляє в продавців.
Схвалення фахівця не змінює User.role, SellerStatus, підписку чи доступ
до книги. Окрема заявка продавця повторно використовує той самий профіль.

CreativeProject — SQLite `creative_projects`, FK до серверної книги.
Зараз тільки власник створює й читає чернетки; specialistId/orderId=null.
До вибору фахівця і надання scope дійдемо в наступних етапах. Немає
автоматичного запрошення, grants, копіювання тексту або публікації брифу.

#### Ручний прогін — фахівець та модератор

1. У Marketplace відкрийте `/creative-marketplace`, потім «Профіль
   фахівця» (`/specialists`). Гість бачить лише схвалені профілі та
   пропозицію увійти. Немає кнопок створення замовлення/escrow/workspace.
2. Під додатковим логіном дизайнера введіть ім’я, опис, країну, мови,
   спеціалізації, приклади робіт, послуги й доступність. Списки — по рядку;
   роботи/посилання — HTTP(S). Інструменти, умови й аватар необов’язкові.
3. Збережіть чернетку; перезавантажте сторінку. Дані і DRAFT зберігаються.
   В інкогніто без цього логіна чернетку не видно. У списку заявок
   продавців адміністратора її теж немає.
4. Надішліть збережену заявку: SUBMITTED. Незбережені зміни блокують
   надсилання. Після подання форма не редагується.
5. Адміністратор на `/specialists` бачить чергу. Спершу натисніть
   «На розгляді»: UNDER_REVIEW. Поверніть NEEDS_CHANGES з поясненням.
   Без пояснення повернення/відхилення не приймається.
6. Дизайнер бачить пояснення, доповнює й зберігає заявку, подає повторно.
   Адмін знову бере на розгляд і схвалює. Публічний список показує профіль,
   але не email, userId, зауваження чи історію модерації.
7. В окремій тестовій заявці перевірте REJECTED — не публікується.
   У двох вкладках зі старою версією спробуйте повторні рішення:
   одна операція успішна, друга повідомляє про змінену заявку.
8. Схвалений фахівець ще не продає й не читає чужу книгу. Окрема заявка
   продавця використовує той самий профіль і проходить стару процедуру;
   підписка для продавця в Studio залишається обов’язковою.
9. Повторіть ключові дії англійською `/en/specialists` і на 390 px.

#### Ручний прогін — власник книги

1. У Studio відкрийте свою серверну книгу → «Спільна робота» →
   «Творчі проєкти». Вкажіть назву й створіть чернетку.
2. Перезавантажте сторінку: чернетка лишається. Немає кнопки запуску

3. Інший учасник або сторонній логін не бачить ці чернетки й не може
   створити проєкт через API. Книга, її учасники й grants не змінилися.
4. Перевірте повідомлення при надто короткій назві/помилці мережі.

## T7.2 — повний сценарій

Джерело: [T7.2.md](T7.2.md).

### Т7.2 — бриф і доступ до книги

#### Що реалізовано

Власник серверної книги відкриває «Спільна робота → Творчі проєкти», створює
проєкт і переходить до «бриф і доступ» (`/studio/creative/access/[id]`).
Приватний бриф, scope і версії зберігаються в SQLite Studio. Конструктор
підтримує 12 типів роботи та всі поля §2.3. AI отримує тільки поля форми;
результат треба переглянути й зберегти вручну. Публікація потребує preview
та явного підтвердження автора.

Marketplace приймає тільки публічний snapshot через захищений API-міст,
ідентифікує автора за серверним Firebase UID, зберігає один CreativeOrder
для зовнішнього CreativeProject. Повторний запит не створює дублікат;
та сама ревізія незмінна. Статус — MODERATION. Автор бачить свої snapshots
на `/creative-briefs` (англійською `/en/creative-briefs`). Публічної біржі,
модерації замовлень і заявок виконавців ще немає: це Т7.3.

Доступ використовує Т6.2 AccessGrant, а не окреме сховище. Додано конкретний
предмет, медіафайл і Visual Bible. Вибір у дереві зберігає майбутній scope,
але нічого не відкриває. Окремий grant активному учаснику потребує
підтвердження; є початок/кінець дії, відкликання та аудит. NONE не відкликає
раніше видані grants: права книги об’єднуються. WORK для тексту дає контекст
VIEW без редагування рукопису; робочі дії виконавця — Т7.4. MANAGE не робить
людину власником брифу та не дозволяє публікувати його замість автора.

Частин книги в поточній моделі немає; дерево показує глави і сцени. Style
Bible з’явиться у Т7.5; поточний UI пояснює відсутність. Якщо такі дані вже
є у книзі, окремий explicit grant підтримується. Немає автоматичного
призначення фахівця, grants чи копіювання рукопису до Marketplace.

#### Перед production-прийманням

1. Деплой Marketplace API з Prisma-міграцією `20261008090000_creative_briefs`,
   потім Web і Studio. У Studio Core PostgreSQL застосовує міграцію 0034;
   SQLite таблиця брифів створюється при першому використанні.
2. Використати чинний міст: Marketplace `BRIDGE_API_KEY`, Studio захищені
   налаштування адреси й ключа мосту. Ключі не публікувати і не змінювати
   чинний `SECRET_VAULT_KEY_BASE64` (втрачається можливість читати vault).
3. Переконатись, що власник має Firebase-акаунт і право зовнішньої публікації.
   Для AI потрібні чинні дозволи/підписка та доступний провайдер.
4. Для перевірок зробити окрему тестову книгу без приватних реальних текстів.

#### Ручний прогін

1. Автор створює творчий проєкт, заповнює тип, опис, результат, формат,
   розміри, стиль, концепти, раунди правок, дедлайн, бюджет/умови,
   публічні референси, AI policy та вихідні файли. Зберігає і перезавантажує.
2. У дереві обирає одну сцену, предмет і один медіареференс. У всіх інших
   матеріалів лишається NONE. Дизайнер без grants нічого не бачить;
   збереження scope саме по собі доступу не надає.
3. «Допомогти скласти ТЗ»: відповідь у формі, серверний бриф незмінний.
   Окремо зберегти AI-чернетку. У двох вкладках з однаковою версією зберегти
   різні зміни: один успіх, друга вкладка повідомляє про конфлікт.
4. Preview: без checkbox надсилання недоступне. Підтвердити і надіслати:
   MODERATION, snapshot у Marketplace лише власнику. У ньому немає
   рукопису, scope, приватних ID сцен/предметів або ключів провайдерів.
5. Змінити і зберегти нову чернетку: попередній підтверджений snapshot
   лишається незмінним до нового підтвердження. При недоступному мосту
   показується помилка; повторне надсилання не дублює замовлення. Якщо
   процес обірвався під час надсилання, оновити сторінку та повторити
   підтвердження через хвилину.
6. Автор додає дизайнера активним учасником без широкого доступу. В окремій
   формі явно надає VIEW на предмет і WORK на один медіафайл. Дизайнер
   читає тільки ці ресурси; чужий предмет, сцена та інший файл недоступні.
   Пряма адреса забороненого файлу також повертає 404.
7. Окремо надати VIEW на Visual Bible: доступна тільки після grant.
   Переконатись, що запрошення з попереднім доступом до всієї книги не
   маскує перевірку мінімальних прав.
8. Надати доступ зі стартом у майбутньому: він ще не діє. Перевірити
   завершення строку. Відкликати файл: наступний API-запит/завантаження
   відхилено. Автор бачить події access_granted/access_revoked з цілями
   та строками в аудиті.
9. Сторонній, гість і адміністратор, який не є власником, не читають
   приватний бриф і дерево. Інший акаунт Marketplace бачить лише свої
   брифи. Перевірити 390 px, перезавантаження та прямий creative URL.

#### Автоматизовані перевірки і межі

`npm run test:creative-briefs` запускає справжні HTTP-запити до Express і
SQLite з Core Memory; `CORE_TEST_DATABASE_URL=...` — той самий сценарій
на PostgreSQL з міграціями. `-- --browser` додає Chromium і справжню React
форму. API Marketplace має `creative-briefs.e2e-spec.ts` з реальною БД
і guards; лише Firebase TokenVerifier підмінено локально.

DeepSeek, ключем мосту й Railway. Не позначати їх як перевірені в проді.

## T7.3 — повний сценарій

Джерело: [T7.3.md](T7.3.md).

### Т7.3 — біржа творчих замовлень: ручне приймання

Реалізовано в Studio і Fusion-Lab-Marketplaes. Локальні перевірки не замінюють прогін із реальним Firebase та production bridge після деплою обох сервісів.

#### Передумови

Marketplace API має застосувати міграцію `20261008120000_creative_orders`; web і Studio — містити Т7.3. Перевірити health і журнал міграцій. Потрібні власник книги, адміністратор маркетплейсу й два схвалені профілі фахівців. Email не об’єднує акаунти: зв’язування зі Studio виконується лише за Firebase UID. Не передавати паролі, токени чи ключ мосту в чат.

#### Окремі живі прогони

1. **Публічність.** Власник створює приватний CreativeProject і бриф, явно публікує snapshot. До схвалення каталог не показує замовлення, сторонній detail повертає 404. Після модерації гість бачить тільки публічний бриф; приватний рукопис, сцени, grants, email та внутрішні ідентифікатори не передаються.
2. **Модерація.** Адміністратор відкриває чергу «Модерація»: повертає бриф із причиною або відкриває замовлення. Неадміністратор отримує відмову. Повторне рішення зі старою версією отримує конфлікт. Змінений бриф після повернення публікується повторно; відкритий бриф не можна тихо замінити.
3. **Каталог.** `/uk/creative-orders` та `/en/creative-orders`: перевірити пошук, категорію, бюджет, формат, мову, крайній термін, AI policy, статус і пагінацію. Бюджет — текстовий пошук, не числовий діапазон валют. Проєкти цього етапу — книги. Бриф без мови позначається як «інша».
4. **Заявка.** Схвалений дизайнер подає повідомлення, посилання на роботи, строк, умови та декларацію ШІ. Перевірити редагування, відкликання й повторну подачу. Другий фахівець подає інші умови. Гість, власник власного замовлення та несхвалений профіль не подають заявку. AI FORBIDDEN не приймає USES_AI. Приватні API-посилання не використовувати як портфоліо.
5. **Порівняння і вибір.** Власник бачить обидві заявки, роботи, строки й умови, обирає одну та ставить підтвердження. Без підтвердження вибір відхиляється. Одночасний вибір із двох вкладок: один успіх, один конфлікт; обраний рівно один виконавець. Змінені після відкриття сторінки умови вимагають повторного завантаження. Статус SPECIALIST_SELECTED зберігається після reload; нові заявки більше не приймаються.
6. **Зв’язування Studio.** Власник у брифі підтверджує синхронізацію замовлення. Створений раніше CreativeProject отримує виконавця й статус без дубліката. Якщо фахівець ще не входив у Studio, зберігається його Firebase UID та показується очікування; після його входу повторити синхронізацію. Вимкнений локальний акаунт не прив’язується. Старе рішення чи чужий order не перезаписують проєкт.
7. **Доступ окремо.** До й після вибору порівняти учасників, ролі та grants: вони не змінюються. Фахівець не отримує рукопис автоматично. Власник окремо додає активного учасника й задає конкретні дозволи через наявний механізм Т7.2. Перевірити дозволений матеріал і відмову для іншої сцени.
8. **Скасування.** Власник явно скасовує замовлення, потім архівує; сторонній не змінює статус. Скасоване не видно в публічному каталозі. Синхронізація переносить статус у Studio. Раніше видані grants відкликаються окремо власником — скасування не є автоматичним відкликанням.
9. **Акаунти й телефон.** Вийти та зайти іншим акаунтом без reload: приватні заявки/керування попереднього користувача не залишаються видимими. Повторити каталог, заявку й вибір на ширині 390 px; UA/EN, відсутність горизонтального переповнення та помилок JavaScript.

#### Автоматична перевірка

Studio: `npm test`, `npm run lint`, `npm run build`; окремо `npm run test:creative-orders` і `npx tsx scripts/test-creativeOrders.mts --browser` (потрібна збірка/CSS і Chromium).
Marketplace: `npm test`, `npm run typecheck`, `npm run build`; API e2e із локальним PostgreSQL; `node scripts/live-creative-orders.cjs` запускає справжні API/Postgres і компоненти з тестовою ідентичністю. Деталі та ізоляція БД — `docs/creative-orders.md` другого репозиторію.

#### Межі

Реальний Firebase, production bridge і розгортання ще не підтверджені цим локальним прогоном. Реальний ШІ тут не викликається. Workspace/матеріали/чат — Т7.4; оплата й escrow — наступні етапи. Статуси IN_PROGRESS/REVIEW/COMPLETED зарезервовані, цей етап не має довільних переходів у них. Точна реалізація макета Stitch 9 — Т8.3, макет у поточних репозиторіях відсутній. Перед production прийманням нагадати про відкладений Т4.3 і перевірку SECRET_VAULT_KEY_BASE64 на Railway, чинний ключ не замінювати.

## T7.4 — повний сценарій

Джерело: [T7.4.md](T7.4.md).

### Т7.4 — Creative Workspace: ручне приймання

Приватний простір у Studio: `/studio/creative/workspace/<creativeProjectId>`.
Посилання є у творчому проєкті/брифі; Marketplace показує його власнику та
обраному фахівцю. Вибір не надає дозволів. Це сценарій після деплою;
локальний Chromium використовує тестову ідентичність, не Firebase.

#### Передумови

Розгорнути актуальні Studio й Marketplace API/Web. Studio зберігає нові
таблиці й файли BLOB у SQLite на наявному persistent volume. Окремої
PostgreSQL-міграції цього етапу немає. Перед застосуванням зробити резервну
копію SQLite штатними засобами (разом із WAL або через SQLite backup).
Власник синхронізував вибір Т7.3; фахівець увійшов у Studio, доданий як
активний учасник. Автор у вкладці «Учасники» явно надає VIEW/COMMENT/WORK
на цей Workspace; медіатека й сцени надаються незалежно. Потрібні PNG,
друга версія PNG, MP4/WEBM і PDF до 20 МБ. Не надсилати токени чи паролі в чат.

#### Окремі прогони

1. **Доступ.** Власник відкриває Workspace. В іншій сесії обраний фахівець
   без grants отримує 403. VIEW дозволяє перегляд і завантаження вже наявних
   файлів, але не створення/коментування. WORK дозволяє власні роботи й
   коментарі. Сторонній учасник, навіть із доступом до книги, не відкриває
   цей Workspace. Окремий дозвіл у вкладці «Учасники» має підтвердження,
   дати початку/закінчення й явне відкликання; нова роль чи обрання не
   створює його. У Core він зберігається як deliverable/<creativeProjectId>,
   WORK відповідає edit тільки цієї області, не книги. Адміністратор, який не є власником/обраним учасником,
   також не обходить цю перевірку. Тимчасові grants працюють тільки у строку.
2. **Матеріали книги.** Дати фахівцю одну сцену й одну сутність. Вкладки
   «Матеріали» та «Переглянути дозволений текст» не показують інші сцени,
   приватні нотатки чи чужі сутності. Референси медіатеки фільтруються
   наявними дозволами; endpoint файла перевіряє права окремо.
3. **Завантаження.** WORK-фахівець додає PNG: з’являється v1/DRAFT.
   Перезавантажити сторінку — файл і авторство збережені. ZIP/GLB доступні
   для скачування; image/video/PDF мають viewer. SVG/HTML, підроблений MIME,
   понад 20 МБ та вичерпана квота відхиляються. Квота використовує тариф
   завантажувача; чинний загальний механізм не повертає використаний обсяг
   при видаленні/невдалому подальшому кроці.
4. **Перевірка.** Фахівець ставить явне підтвердження й подає v1 на review.
   Автор просить зміни з обов’язковою причиною. Фахівець повторно подає
   матеріал: RESUBMITTED. Автор затверджує й окремо позначає FINAL.
   Фахівець не має кнопки/права затвердження. Два рішення зі старою ревізією:
   тільки одне успішне, друге конфлікт. APPROVED/FINAL не додають файл до
   канону, не змінюють рукопис і не створюють оплату.
5. **Нові версії.** Після правок додати v2 через «Нова версія вибраної
   роботи». v2 — нова чернетка з parent v1; байти й статус v1 збережені.
   Два одночасні додавання дають одну v2. Немає заміни чужої роботи
   фахівцем. Стару версію не можна затвердити після появи новішої;
   FINAL/ARCHIVED не приймає дочірню версію. Окрема нова робота — інший root.
6. **Порівняння.** Вибрати v2 та v1: перевірити «Поруч», «До / після»
   зі зміною положення, «Накладання» з прозорістю. Масштаб 50–200%, fullscreen,
   скачування обох версій. На телефоні canvas прокручується всередині,
   сторінка не розширюється горизонтально.
7. **Annotations.** Клікнути точку зображення й додати текст; нормовані
   координати зберігаються біля конкретної версії. Показати pin повторно.
   Для відео — таймкод, перехід до нього; для PDF — текстовий коментар.
   Автор/автор коментаря закриває його; чужий фахівець не вирішує коментар
   автора. Невірні координати/негативний таймкод відхиляються. Сервер
   обмежує таймкод 24 годинами, тривалість відео не аналізує.
8. **Чат.** Автор і фахівець у двох сесіях: текст, HTTPS-посилання,
   згадування другого учасника, вкладення конкретної приватної версії.
   Події завантаження, review й annotation з’являються в чаті/історії.
   Оновлення polling кожні 5 секунд. Перевірити попередні пакети історії
   (по 100), read cursor і непрочитані. Чужий asset/згадування відхиляється;
   чат не замінює pin-коментарі.
9. **Відкликання.** Автор відкликає Workspace grant (і чинний media grant, якщо його
   надавали окремо) під час роботи фахівця:
   наступний API/file-запит відмовляє, polling прибирає Workspace й cached
   viewer з інтерфейсу. Після відновлення grant історія залишається. Статус
   учасника suspended також закриває доступ. Скасоване/архівне/завершене
   замовлення — read-only; grants відкликаються окремо власником.
10. **Телефон і сесія.** На ширині 390 px усі десять вкладок доступні;
    desktop огляд має три колонки. Вийти/увійти іншим акаунтом: компонент
    перевідкривається й не зберігає приватні дані попередньої сесії. Перезапуск
    сервера з тим самим томом зберігає файли, версії, чат і annotations.
11. **AI Tools.** Вкладка веде до наявної AI Studio, без ключів у браузері
    й автоматичної генерації. GET_DELIVERABLES повертає тільки метадані
    доступних Workspace; scoped manuscript context не розширюється.
    Реальний DeepSeek/Firebase — окремий production-прогін, не локальний тест.

#### Команди

Studio: `npm run test:creative-workspace`, `npm test`, `npm run lint`,
`npm run build`; Chromium після збірки —
`npx tsx scripts/test-creativeWorkspace.mts --browser`.
Шлях браузера можна задати CHROME_PATH; живий тест відео потребує ffmpeg. Для перевірки Core/PostgreSQL
CORE_TEST_DATABASE_URL має вказувати тільки на ізольовану тестову БД.

Marketplace: `npm test`, `npm run typecheck`, `npm run build`, API e2e
із TEST_DATABASE_URL тестового PostgreSQL. Production БД для тестів не використовувати.

#### Межі й наступне

Файли зараз приватні у Workspace, перенесення результатів у спільну Media
Library/походження — Т7.5; Visual/Style Bible і канон — Т7.6. Ліміти:
20 МБ/файл, історія 100/пакет, AI summaries 200; антивірусного сканера та
серверного транскодування цього етапу немає. PDF viewer залежить від браузера,
завжди доступне скачування. Chat має polling, без WebSocket і push/email.
Точний макет Stitch — Т8.3. Реальні production/Firebase/volume/bridge
перевіряються цим сценарієм після деплою. Нагадування перед production:
відкладений Т4.3 і перевірка захищеного SECRET_VAULT_KEY_BASE64 на Railway;
чинний ключ не замінювати.

### Т7.5 — живий прогін медіатеки з походженням

Після деплою Studio на https://www.fusionlab.in.ua/studio. Потрібні окремі
сесії власника та обраного активного фахівця. Використати тестову книгу й
творчий проєкт, не робочі рукописи. Ключі/паролі в консоль чи звіт не копіювати.
Перевірити persistent DATA_DIR/SQLite volume й зробити штатний backup до
оновлення схеми. Нових міграцій Marketplace немає.

3. Зберегти демо-карту v1: вхід і вихід унизу, два краї мосту нагорі, драбина/сходи, коридор і `overNodeIds`. Власний прогін починається з нижнього входу, seed, ревізії0, окремих ресурсів/станів і початкової контрольної точки. Автор preview явно вказаний як учасник, його герої перелічені; режим `author_preview`, не робоча адаптивна складність.
4. Пройти `up → bridge → down`. Очікується вихід на нижньому рівні; поточні рівні визначаються вузлами, а герой не телепортується до мосту з коридору. Вартість і тривалість враховані; первісний об’єкт карти й рукопис не змінені.
5. У другому прогоні з нижнього входу вимкнути generator. Змінюються тільки generator і прямо пов’язана bridge-gate; other-door в іншій кімнаті та стан першого прогону не змінюються. На міст із закритою решіткою пройти не можна. Взаємодія з далеким об’єктом відхиляється.
6. Додати v2 без bridge. Старий прогін і v1 лишаються незмінними; новий прогін, створений з v2, не має видаленого переходу. Перезапустити пул/сховище — ID, seed, ревізія, учасник, герої й стан відновлюються.
7. Відправити дві дії з однаковою ревізією: один200, один409. Дві нові версії карти з однаковою expectedRevision: один201, один409. Невдалий запис не додає дубля події або зайвої версії; клієнт після409 перечитує стан.
8. Перевірити журнал: ревізія0 й кожна прийнята дія, актор, причина ручної структурної перевірки, версія карти, фактичний checkpoint, before/after hashes. JSONB-перестановка ключів не змінює hash. Списки карт/версій повертають тільки метадані, повний snapshot читається окремо.
9. Власні scene/entity IDs приймаються, чужі scene/entity IDs відхиляються. Чужий map/run ID у іншій книзі дає404. Складений SQL FK має відхилити чужу версію навіть повз API. UPDATE історичного snapshot/checkpoint відхиляється базою. Видалення тестового проєкту прибирає його дані без перешкод для решти ядра.
10. Гість, вимкнений акаунт, сторонній, читач і редактор не читають повний граф та не пишуть його. Власник і адміністратор бачать авторські дані. Надання доступу до сцени не відкриває приховані події лабіринта. Усі приватні відповіді `no-store`; без готового ядра —503.
11. Передати невалідні рівні, дублікати, відсутні вузли, невідомі об’єкти/стани, негативні ресурси, NaN, неоднозначні переходи або довільні поля API/готовий стан. Очікується відмова без часткового запису.

#### Після production-деплою

12. Звірити Railway startup: готове ядро, схемаv35, без migration checksum error. Перевірити справжній Firebase-вхід автора/адміністратора й одного читача. Поточна сесія має застосуватися до захищених API; тестовий `x-test-user` існує тільки у тестовому скрипті, production ним не авторизується.
13. На окремій тестовій книзі повторити пункти3–8 через автентифікований API-клієнт. Стабільні ID й байти приватних даних не публікувати; достатньо статусів, ревізій і hashes. Для іншої реальної книги не використовувати цю модель без дозволу її власника.
14. Перевірити відновлення після штатного перезапуску сервісу, який виконують під час узгодженого деплою, та роботу решти Studio. У новій UI-сторінці це ще не проходиться: конструктор буде Т9.2, доступний читач — Т9.6.

Не закриваються цим пунктом: глобальна безпечна прохідність/останній вихід, фази пасток, Jev/DeepSeek, груповий хід, цифровий читач, збірка/співавторство/експорт/видання. Їхні прогони — Т9.2–Т9.10. Зафіксувати SHA, час, середовище, які саме пункти пройшли, та що лишилось неперевіреним.

### Т9.2 — авторський конструктор книги-лабіринта

Реалізація доповнює **Конструктор структури** Studio режимом **Книга-лабіринт**.
Старі шаблони розділів працюють у режимі **Структура розділів**. Текст
сцен лишається в розділах книги та відкривається у звичайному редакторі.
React Flow використовується як у графі історії; онтологія, workflow та
граф сутностей не стають окремою копією ігрової карти.

#### Локальна перевірка

```powershell
cd "D:\Rama\Book_Creality"
npm run test:labyrinth-design
npm run test:labyrinth
npm test
npm run build
```

`test:labyrinth-design` перевіряє статичну прохідність. За замовчуванням
`test:labyrinth` перевіряє модель, але **не** PostgreSQL/API/браузер.
Для повного прогону потрібна **окрема тестова PostgreSQL з pgvector**:

```powershell
$env:CORE_TEST_DATABASE_URL = "postgresql://USER:PASSWORD@HOST:PORT/SEPARATE_TEST_DB"
npm run live:labyrinth-builder
Remove-Item Env:CORE_TEST_DATABASE_URL
```

Браузерний скрипт наразі використовує Chromium `/usr/bin/chromium` у хмарі.
Це локальний Express, справжня PostgreSQL та тестова ідентичність,
а не Firebase або production. Створюються лише тимчасові проєкти;
їхні дані прибираються після прогону. Не вказуйте production DB.

#### Живе приймання після деплою

1. Увійти власником синхронізованої книги. Відкрити **Конструктор структури**.
   Перевірити, що старі шаблони розділів доступні й не змінилися.
2. Вибрати **Книга-лабіринт → Нова карта**. Ввести назву. Створити нижню
   сцену «Вихід» і дві верхні сцени «Лівий міст», «Правий міст».
   Вибрати «Вихід» у списку виходів, зняти позначку виходу з «Вхід».
3. До створення переходів має з’явитися зауваження про недосяжний вихід.
   Створити коридор Вхід → Вихід, сходи Вхід → Лівий міст,
   міст Лівий міст → Правий міст, драбину Правий міст → Вихід.
   Для мосту вибрати нижні коридори у полі **Коридори під мостом**.
4. Побачити всі вузли й переходи на графі, перемкнути нижній/верхній рівень,
   перетягнути вузол та перевірити зміну X/Y у формі. Повторити на 390 px:
   усі налаштування доступні через форми без точного наведення на карту.
5. Для вузла вибрати **Сцена з книги**. Зберегти карту, натиснути
   **Відкрити текст у редакторі**. Має відкритися саме цей наявний розділ.
   Карту потрібно зберегти перед переходом; вона не створює копію рукопису.
   Новий текстовий розділ створюється звичайним конструктором/редактором книги,
   після збереження та core_sync його можна прив’язати до карти.
6. Додати два механізми: генератор і решітку. Початкові стани нових
   механізмів — `on`/`off`. У переході генератора `on → off` додати
   **Зміни пов’язаних об’єктів**: решітка → `off`. Для мосту додати умову
   решітка = `on`. Перевірити, що правило збережене після перезавантаження.
7. Додати подію, вибрати її зону, попередження, час підготовки, тривалість,
   паузу до повтору, підказку обходу, умови та наслідки. Спробувати зону,
   з якої немає дозволеного переходу назовні: має з’явитися «немає обходу».
   Сам текст підказки не усуває це зауваження. Додати справжній обхід.
8. **Перевірити карту**: сервер перевіряє схему, власні сцени/сутності та
   статичну прохідність. Невалідна схема не зберігається. Статичні зауваження
   дозволяють зберегти авторську версію для подальшого виправлення;
   це не публікація й не гарантія безпечної гри.
9. Зберегти v1, запустити **Тестовий прогін**. Пройти сходами, мостом,
   драбиною. Перевірити позицію героя, хід і витрату енергії. Спробувати
   перемкнути генератор унизу й перейти закритим мостом: сервер відхиляє дію.
10. Правка карти закриває панель прогону; вона не змінює його зафіксовану v1.
    Зберегти v2, перезавантажити Studio, відкрити карту та вибрати v1:
    попередні дані мають залишитися незмінними.
11. Відкрити карту в двох вкладках. У першій зберегти нову версію, у другій
    спробувати запис зі старою ревізією. Має бути конфлікт; її правка
    лишається у формі. **Завантажити останню версію** пропонує підтвердити
    втрату незбережених змін. Або **Зберегти як нову карту** збереже їх окремо.
12. Спробувати змінити режим конструктора/вкладку Studio або закрити сторінку
    з незбереженою картою: має бути попередження. Чернетка не зберігається
    автоматично в браузері — перед виходом використати збереження версії.
13. Увійти читачем/запрошеним редактором/стороннім: повна карта та приховані
    події недоступні. Перевірити реальний Firebase-вхід власника та адміна.
    Перезапустити Railway: збережені версії доступні через штатний Core.

#### Межі цього етапу

Статична перевірка враховує напрямки, початкові стани, окремі переходи
механізмів та умови/ефекти окремої події. Обхід шукається поза її небезпечною
зоною без переходу через інші небезпечні вузли; це консервативне зауваження.
Вона не доводить достатність ресурсів, час порятунку, комбінації пасток чи
послідовність перемикачів. **Т9.3** забезпечить ці правила під час гри.
**Т9.4–Т9.5** — Jev і готові механіки; **Т9.6–Т9.7** — читач/група.
Події у тестовому прогоні автоматично не виконуються, ШІ не викликається.
Доступ повного конструктора — власник/адмін за існуючими правилами Т9.1.

### Т9.3 — стан, ресурси, наслідки та перевірка прохідності

Реалізовано приватний авторський **Безпечний прогін** у Конструкторі структури → Книга-лабіринт. Він працює для одного героя на незмінній версії карти. Старий «Тестовий прогін» залишається структурною перевіркою; через його API не можна обійти захист безпечного прогону.

#### Правила рушія

- Автор запускає шаблон події вручну. Попередження та підказка порятунку показуються до небезпеки; далі проходять фази активності, перезаряджання й готовності. Jev обиратиме події в Т9.4.
- Час сюжетний, у цілих кроках. Рух триває за правилом ребра, взаємодія та очікування — один крок. Запуск попередження не витрачає час. Під час руху герой перебуває у початковій точці; в останній крок спочатку прибуває, потім отримує шкоду. Прибуття драбиною точно в момент активації газу дозволяє врятуватися.
- Витрати переходу застосовуються один раз. Активна небезпека списує задані ресурси за кожен крок перебування в її зоні. Перекриття перевіряється протягом усього переходу. Блокування входу не забороняє виходити з небезпечної зони.
- Переходи можуть вимагати предметів. Механізми змінюють ресурси, додають/витрачають предмети та додають знання. Дані інших сутностей і текст канону не змінюються.
- Ефекти подій тимчасово накладаються на базовий стан механізмів. Після завершення події накладення зникає. Заплановані суперечливі ефекти в одному часовому інтервалі відхиляються.
- Перед створенням прогону та кожною дією сервер шукає реальний маршрут до виходу: напрямки, механізми, предмети, ресурси, час і всі заплановані небезпеки. Доведений маршрут входить до приватного журналу. Очікування допустиме, коли герой справді може пережити його. Статичної зв’язності недостатньо.
- Пошук обмежений бюджетом. Якщо безпеку не доведено, дія відхиляється без запису чи витрати ресурсів. Це може консервативно відхилити складну прохідну карту; автор отримує окреме повідомлення про бюджет. Невизначеність не видається за безпеку.
- Нуль здоров’я від шкоди, від’ємні ресурси та втрата останнього маршруту відхиляються. Сценарний фінал із поразкою тут ще не оголошується: для нього потрібне явне авторське правило фіналу. Групова безпека — Т9.7, повний читач із прихованою картою — Т9.6.

#### Збереження й повтори

Кожна прийнята дія записує незмінну контрольну точку з ресурсами, предметами, знаннями, базовими об’єктами, часом і таймерами. Ревізія захищає одночасні дії. Повтор з тим самим ключем і тілом повертає попередню відповідь навіть після перепідключення; інше тіло з тим самим ключем відхиляється.

«Відновити як новий прогін» створює окрему гілку з точної контрольної точки. Старий прогін зберігається. Seed і версія карти незмінні; ресурси не поповнюються автоматично, час і попередження не скидаються. Кнопка «Збережені прогони» показує останні 20 прогонів відкритої версії карти та дозволяє продовжити після перезавантаження сторінки. «Оновити прогін» отримує актуальну ревізію після конфлікту. Стартова ревізія нової гілки — 0; сюжетний час береться зі знімка. Журнал фіксує джерело відновлення.

Міграція Core **36** додана окремо; попередня 35 не змінена. Доступ лише власнику/адміністратору книги за чинним Core ACL. Читач, редактор, сторонній та гість не отримують приховану карту чи керування.

```powershell
npm run test:labyrinth-runtime
npm run test:labyrinth
npm test
npm run build
```

#### Окремі живі сценарії після деплою

1. **Вхід і міграція.** Власник відкриває Книгу-лабіринт; сервер Core готовий зі схемою 36. Редактор/читач не бачать прихованих правил і не можуть викликати runtime API. Існуючі карти v1 та структурні прогони відкриваються.
2. **Газ і драбина.** У прикладі зробити умови газу порожніми, зоною — нижній вхід, підготовкою — 2, тривалістю — 3, шкодою здоров’ю — 100. Зберегти нову версію. Створити Безпечний прогін, запустити газ: видно попередження та обхід. Одразу піднятися драбиною: здоров’я 100, енергія 9, герой і маркер на верхньому рівні. Перевірити також драбину тривалістю 2. При всіх доступних виходах тривалістю 3 запуск газу має бути відхилений.
3. **Останній вихід і кілька пасток.** Зв’язати два альтернативні маршрути з різними решітками. Перша запланована подія перекриває один шлях, залишаючи досяжний інший. Друга перекриває решту до завершення руху та не дає безпечно перечекати небезпеку. Другий запуск відхиляється; час, ресурси й журнал не змінюються. Якщо безпечне очікування справді можливе, тимчасове перекриття може бути прийняте.
4. **Ресурси, предмети й знання.** Вимагати ключ для єдиного виходу; механізм має додавати ключ, витрачати предмет та енергію, додавати знання. Пройти механізм один раз, перевірити точні значення. Дія, яка витрачає останній необхідний ключ без шляху повернення, відхиляється. Недостатніх ресурсів і невідомих предметів недостатньо для обходу правила.
5. **Фази й відновлення.** Зберегти контрольну точку під час попередження. Зробити два кроки; відновити попередню точку як новий прогін. Порівняти всі ресурси, знання, інвентар, час і залишок попередження. Старий прогін не переписаний. Після перезапуску сервера значення ті самі; завершений ефект не залишається в базовому стані; до завершення cooldown повторний запуск відхиляється.
6. **Повтор і конкуренція.** Два одночасні однакові запити з одним ключем повертають один результат. Два різні запити зі старою ревізією: приймається один, другий має конфлікт. Ресурс не списується двічі. Повтор прийнятого запиту після перезапуску повертає збережену відповідь.
7. **Ваш SVG і мобільний екран.** Завантажити наданий приклад, зберегти, створити Безпечний прогін. Рух/очікування/відновлення узгоджують час, словесний опис і жовту точку. На вузькому екрані кнопки доступні; новий запит не починається під час попереднього. Власний генератор поки не підключається — Т9.11.

Результати production/Firebase, реального restart Railway й ручного проходження власником ще потрібно зафіксувати після деплою. Реальні AI-виклики цьому етапу не потрібні.

## T9.4 — повний сценарій

Джерело: [T9.4.md](T9.4.md).

### Т9.4 — Jev-директор напруги

Директор доповнює авторський **Безпечний прогін**. Карта та події залишаються незмінною збереженою версією; художній текст канону не переписується. Після руху або взаємодії інтерфейс може запускати рішення автоматично; очікування й час читання самі по собі не є приводом для оцінки слабкості. Є окрема кнопка «Хід директора» та вимикач автоматичних рішень.

#### Правила та джерела

- Автор явно вмикає директора, задає цільову напругу, пороги, cooldown, timeout, число перевірюваних кандидатів і бюджет спроб ШІ. Без налаштувань старі карти та прогони працюють як раніше.
- Події позначаються як ускладнення, порятунок, перепочинок або підказка, з пріоритетом. Подія без ролі директора запускається лише вручну. Порятунок/перепочинок/підказка не можуть списувати ресурси небезпекою чи блокувати вхід у її зону.
- Детермінований Score враховує здоров’я й ресурси відносно початкових авторських значень, активні небезпеки та останні 8 маршрутних ходів. Повернення назад зменшують оцінку впевненості. Це стан вигаданого героя, не психологічний діагноз людини. Ресурс нижче або на рівні 15% також вважається критичним.
- Для критичного героя ускладнення виключається ще до моделі. Директор шукає порятунок, перепочинок або підказку; сам не лікує героя і не видає перемогу. За високої напруги обирається полегшення, для впевненого маршруту — дозволене ускладнення, для невизначеного — підказка/перепочинок.
- Кандидати перевіряються рушієм Т9.3 до моделі: умови, cooldown подій, час, ресурси, предмети, несумісні ефекти та досяжність виходу. ШІ обирає тільки з цього списку або залишає світ незмінним.
- Чинний адаптер Jev отримує пакет **Score/Noul/Choice**. Noul перевіряє авторську відповідність і ризик передчасного розкриття; він не доводить прохідність. Невпевнена, некоректна чи недозволена відповідь відхиляється. Високий модельний Score додатково зупиняє ускладнення.
- При відсутності/збої Jev ті самі питання переходять чинному `LlmFallbackJevAdapter`, через роль AI-2 ядра Студії. Адаптер LLM не повідомляє confidence: для порога використовується визначеність Noul `abs(2p−1)`, а в трасі це явно позначено. Модельна оцінка не видається за доказ.
- Якщо ШІ вимкнено, бюджет вичерпаний, відповідь запізнилася чи провайдери недоступні — спрацьовує авторський безпечний резерв за ролями/пріоритетом/seed або нічого не змінюється. Рух і відновлення залишаються доступними. Seed забезпечує відтворення правил, але не гарантує однакової відповіді зовнішньої моделі.

#### Бюджет, timeout та збереження

Бюджет — кількість спроб адаптера на прогін, а не обіцянка грошового тарифу. Не більше двох спроб на рішення: Jev, потім запасний LLM. Немає автоматичних повторів платного запиту. Максимум 12 кандидатів, до 8000 символів пакета контексту/питань; запасний LLM обмежено 500 вихідними токенами. Ключі, URL та довільні налаштування провайдера з клієнта не приймаються.

Міграція Core **37** додає окремий журнал резервування спроб. Резерв комітиться до виклику моделі й зберігається, навіть якщо доступ відкликали або основна транзакція відкотилася. Затримка резервування може консервативно витратити слот без завершеного виклику. Авторський timeout спільний для Jev і запасного шляху; пізня відповідь не застосовується. У трасі сумуються повідомлені токени всіх відповідей; невідомі витрати невдалих/запізнілих спроб позначені окремо, не прирівняні до нуля.

Проєктний ACL і поточний акаунт/роль перевіряються до платного виклику та перед записом результату. Шлях ШІ вимагає `canUseAi`; офлайн-директор цього дозволу не потребує. Паралельні однакові запити з одним ключем повертають один результат і не оплачують модель двічі. Інше тіло з тим самим ключем відхиляється. Рішення та причина зберігаються в незмінному журналі з версією карти, хешами, доказом маршруту й виміряною затримкою.

Контрольна точка зберігає рішення, маршрутну пам’ять і лічильники. Новий прогін після відновлення — окрема гілка зі знімка; бюджет обмежує кожен прогін, не замінює тарифів/прав доступу всієї платформи. Директор не запускається на кожному кадрі й не обіцяє затримок зовнішнього ШІ у частки секунди.

#### Окремі живі сценарії після деплою

1. **Авторські налаштування.** Власник відкриває Конструктор → Книга-лабіринт. Увімкнути директора, ціль 55, критичне здоров’я 25%, поріг маршруту 50%, cooldown 2, бюджет 2, timeout 3000 мс. У подій призначити ускладнення та порятунок/перепочинок з пріоритетами. Зберегти нову версію й створити Безпечний прогін. Незбережені налаштування не мають змінювати стару версію.
2. **Ті самі правила, різні герої.** На старті здоров’я 100, енергія 10; без ШІ здоровому герою дозволено ускладнення. У другому прогоні авторський механізм списує 80 здоров’я: директор обирає порятунок/перепочинок, не ускладнення. Здоров’я залишається 20, вихід досяжний, причину видно в інтерфейсі й журналі. Не плутати початкове здоров’я 20/20 із витраченим 20/100.
3. **Автоматичний цикл.** Увімкнути «Рішення після руху та взаємодії». Після переходу перевірити одну дію директора, попередження, узгоджені позицію й маркер. Кілька очікувань або повільне читання не збільшують «страх» і не додають маршрутних ходів. Вимкнути автоматичний режим; кнопку директора можна викликати окремо.
4. **Прохідність понад модель.** Запропонувати подію, яка перекриває останній вихід або дає неминучу шкоду до драбини. Вона відкидається до моделі; журнал містить відмову `conditions_or_safety`. Невідомий id, стороння дія чи довільний URL не приймаються. Рятувальна роль зі шкодою має відхилятися при збереженні карти.
5. **Cooldown і бюджет.** Запустити директора, повторити в той самий сюжетний час: причина `cooldown`, новий платний виклик відсутній. Через дозволені кроки перевірити нове рішення. Після вичерпання бюджету — причина `budget` і безпечні правила. Паралельний повтор з одним ключем повертає одну ревізію, один виклик і той самий receipt після перезапуску.
6. **Timeout/невпевненість/відмова.** На тестовому провайдері затримати відповідь довше timeout, дати неправильний Choice, низький Noul або збої обох моделей. Прогін продовжується з резервною подією/без зміни світу; ресурси не губляться, пізня відповідь не з’являється. Окремо перевірити збій Jev → успіх запасного LLM. Секрети провайдера не потрапляють у відповідь/журнал.
7. **Відкликання під час виклику.** Після резервування спроби вимкнути акаунт або забрати адмінську роль/доступ до книги. Результат не застосовується. Резерв бюджету залишається після відмови; повтор із відновленим доступом не дає безкоштовного нового платного виклику понад ліміт.
8. **Відновлення.** Зберегти точку після рішення, продовжити кілька ходів, відновити як новий прогін. Порівняти ресурси, час, таймери, рішення/причину, cooldown і маршрутну пам’ять. Перезавантажити сторінку, відкрити «Збережені прогони», продовжити ту саму гілку. Стара гілка не переписується.
9. **Реальний Jev та DeepSeek — окремо.** У production під власником із `canUseAi` перевірити платформні ключі й модель ролі AI-2. Дозволити 2 спроби та явно увімкнути ШІ. Перший прогін — реальний Jev; другий — недоступний Jev і справжній DeepSeek у запасному шляху. Записати source/model, Score/Noul/Choice, причину, фактичні токени/витрати та затримку. Успіх контрольованого адаптера не замінює цих прогонів.

#### Межі підтвердження

Реальні Jev/DeepSeek та production/Firebase ще не прийняті. У цьому хмарному прогоні `JEV_API_KEY`, `TYPESAFE_API_KEY`, `DEEPSEEK_API_KEY` відсутні; production-платформне сховище не підключалося. Ключі в чат не потрібні. Груповий директор — Т9.7, повний читач — Т9.6, бібліотека механік — Т9.5.

#### Передумови й спільний цикл

1. Записати активний deployment SHA/URL, акаунт і час. В окремій тестовій книзі відкрити **Конструктор структури → Книга-лабіринт → Дворівневий приклад**. Не підміняти робочу карту без згоди.

3. Натиснути «Додати механіку до чернетки». До збереження немає нової серверної версії чи нового прогону. Переглянути попередження, обхід, прив’язку, умови й відповідь; зберегти нову версію явно.
4. Запустити **Безпечний прогін** одного героя; вручну запустити нову подію. На фазі попередження прочитати ознаки, обхід і залишок ходів. Перевірити активну фазу, відповідь, повідомлення про припинення та cooldown.
5. Повторити новим прогоном без відповіді: природне завершення знімає тимчасовий ефект. Після дострокової відповіді спочатку закінчити cooldown і підготувати механіку повторно; повтор не дублює подію чи витрату.

Кожну механіку перевірити окремо й записати PASS/FAIL, mapId/mapRevision/runId/runRevision, ресурси/час до та після дії. Стан має зберігатися на сервері. Далі перевірити поєднання.

### Словесний вибір маршруту та позначка героя

Оновлення12.10.2026: повний сольний читач Т9.6 реалізовано; актуальні окремі сценарії — [T9.6](T9.6.md). Нижче збережено приймання попереднього авторського огляду.

У Studio: **Конструктор структури → Книга-лабіринт**.
Вибрати власну карту або **Приклад із вашого SVG**, зберегти версію,
запустити **Тестовий прогін**. Панель **Що бачить мандрівник** описує
поточне розгалуження. Жовта позначка на графі або на SVG показує героя.
Після успішного ходу опис і позначка оновлюються автоматично.

#### Прогін

1. На маленькому дворівневому прикладі вибрати напрямок погляду «Схід».
   Нижній коридор має описуватися як «йти прямо»; зміна на «Південь»
   перетворює його на «повернути ліворуч». Вертикальні переходи описуються
   як підйом/спуск сходами, драбиною або підйомником.
2. Пройти драбиною й мостом. Маркер має перейти до того самого вузла,
   який названо в описі. У режимі «За останнім ходом» напрямок береться
   з останнього руху, а вертикальний перехід без зміщення його зберігає.
   На старті напрямок — північ; його можна явно змінити у панелі.
3. Закрити решітку або вичерпати енергію. Такий шлях не називається
   доступним вибором, причина пояснюється. Словесний огляд не виконує дію.
4. Для мосту задати нижні вузли у полі **Коридори під мостом**.
   Якщо герой у такому або сусідньому вузлі, міст згадується в огляді.
   Майбутні події, приховані герої та їхній інвентар в опис не включаються.
5. Завантажити **Приклад із вашого SVG**, зберегти нову карту, запустити
   прогін Івана. Жовта точка спочатку у верхній лівій клітинці.
   Перейти в «Коридор 1:2»: точка зміщується вниз на одну клітинку,
   текст називає новий коридор. Перевірити на мобільному 390 px.
6. На SVG перевірити червоні стіни, сині мости й точку. Для редагування
   перемкнутися на **Граф карти**. Для нового вузла без відповідності
   вихідному SVG система показує граф із маркером.
7. У другій вкладці зробити хід. При наступному читанні огляду перша
   вкладка підхоплює новішу серверну ревізію; новий текст не поєднується
   зі старим маркером. Під час запиту відображається стан завантаження.
8. Нова версія карти не переписує огляд старого прогону: він використовує
   власну mapRevision. Читач/редактор/сторонній не читає авторський endpoint.
   Production/Firebase-приймання виконати після деплою окремо.

#### Перевірка 300-DPI друку

Для растра перевіряти **ефективні PPI** у фактичному фізичному розмірі. Позначка «300 DPI» у метаданих та назва режиму 4K самі по собі не підтверджують придатність до друку.

- Для кожного зображення записати реальні **W × H пікселів**, розмір у макеті **w × h мм** і обрізку. Мінімум: `ceil(w / 25.4 × 300)` × `ceil(h / 25.4 × 300)` пікселів; ефективні PPI рахувати для використаної після обрізки частини зображення.
- Формат для погодження: **A5 148 × 210 мм**. За вильотів 3 мм з усіх боків потрібні 154 × 216 мм, щонайменше **1819 × 2552 px**. Для суцільного A5-розвороту 296 × 210 мм з зовнішніми вильотами 3 мм — 302 × 216 мм, щонайменше **3567 × 2552 px**. Корінець, безпечні поля та технічні вимоги звірити з друкарнею.
- Після розміщення й обрізки перевірити обличчя, краї, дрібні предмети та написи у масштабі друку. Менший результат позначити як непридатний для цього розміру; апскейл оцінюється окремо й не видається за нативну деталізацію.
- Експортувати погоджений макет; перевірити шрифти, вильоти й колірний профіль. Технічну перевірку файлу та фізичний пробний друк записувати окремо. Без пробного друку не позначати фізичну якість як перевірену.

### YOUTUBE-TRANSCRIPT-1 — імпорт розшифровки YouTube

Реалізовано 11.10.2026. Екран: Studio → База знань → YouTube · Розшифровка.

Книга має бути збережена на сервері. Операція доступна власнику або учаснику з повним прямим правом редагування книги. Частковий редактор, читач, сторонній і гість не отримують проєктне джерело. Співавтор, який працює через review/proposals, не обходить цей режим прямим імпортом.

Автоматичний імпорт читає лише доступні публічні caption tracks YouTube: мови, авторські/автоматичні субтитри, сегменти з таймкодами. Не використовує OCR/аудіорозпізнавання або ШІ. Якщо YouTube блокує запит, вимагає вхід чи не надає субтитрів, доступний ручний SRT/VTT/TXT. Доступність цього способу залежить від відповіді YouTube; обхід його обмежень не реалізовано.

Джерело додається через чинний onUpdateBook/storage flow Бази знань: локальне автозбереження та серверне дзеркало з перевіркою ревізії. Це не окреме підтвердження успішної серверної синхронізації: перевірте статус/серверну копію перед очищенням браузера. Новий імпорт не змінює глави; виділіть уривок у джерелі та скористайтеся чинною дією «Зберегти текст в книгу». Таймкоди належать оригіналу, редагований текст позначено окремо. Посилання на відео лишається в метаданих джерела та журналі вставлення.

#### Виконані локальні перевірки

3. Клієнт-співавтор переглядає й редагує лише наданий уривок; чужі випадки й приватний конспект закриті. Публічне авторське ім’я підтверджене окремо.
4. Реконструкція або складений випадок позначені; модель не додає вигаданих фактів до вихідної нотатки.
5. Відкликання дозволу під час генерації: пізня відповідь не застосовується; повторний експорт/публікація блокуються до перегляду матеріалу. Раніше видані копії показані як окреме питання, без хибної обіцянки видалення.
6. Автор і співавтор погоджують фінальний текст; видання містить лише дозволений зміст та погоджені авторські імена.

#### 8. Т10.1–Т10.12 — Mafia Story Studio

- Історична публікація тестової книги на вітрині: уточнити, чи вже закрита пізнішим прогоном; старий «білий екран»/git-auth не переносити як чинний blocker. Якщо ще потрібна — явно погоджена тестова публікація, точні текст/обкладинка/автор/ціна, відкриття картки й штатне прибирання тестового запису.

## Загальний протокол закриття та операційні передумови

#### 13. Черга роботи та протокол закриття

Рекомендований наступний пункт — **Т9.10**; окремо завершити Т9.11 та native-розширення STL. Т8.2/Т9.5/Т9.6/Т9.7/Т9.8/Т9.9 реалізовані, їхні production-сценарії ще потребують ручного приймання. |---|---|---|---|---|---|---|

Пункт закривається після виконання потрібної реалізації, позитивних і негативних сценаріїв, запису фактичних доказів та усунення критичних відмов. Пройдений build/push/healthcheck не закриває права, секрети, AI-якість чи згоду на публікацію.

Хмарне середовище: install/start і три репозиторії збережено в чернетці; Publish/fresh-task restore ще не виконано. Перевірка після публікації — відновлені checkout-и/версії, установка, запуск і повторний export→імпорт на ізольованій базі. Це операційна перевірка, а не ще один невиконаний пункт коду.
