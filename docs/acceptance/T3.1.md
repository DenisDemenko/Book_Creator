# Т3.1 — співпраця, 06.10.2026

Реалізація сторінки `/projects/:projectId/collaboration` завершена.
Команда й доступ використовують чинний реєстр ролей Т6.1 та Access Grants Т6.2:
роль не надає доступу до тексту, реальна людина не стає персонажем.

## Реалізація

- Команда: учасники, призначення й відкликання ролей, спеціалізації,
  запрошення з роллю та посиланням; надання й відкликання доступу через AccessPanel.
- Коментарі до книги, глави, сцени, конкретного стабільного абзацу,
  сутності, ілюстрації або серверного матеріалу книги; редагування й завершення.
- Завдання: авторський текст, активний виконавець із доступом до цілі,
  строк, відкрито/завершено, редагування та перепризначення керівником.
  Виконавець змінює лише статус свого завдання.
- Особисті сповіщення про коментарі/зміни/призначення; стійкий стан прочитання;
  нагадування про прострочення виконавцю без дублів. Оновлення сторінки кожні
  10 секунд. Це сповіщення всередині застосунку; надсилання нагадувань поштою
  чи системні push-повідомлення не додавалися.
- Історія серверних ревізій, порівняння тексту сцен, повний доступний знімок;
  відновлення всієї книги лише власником або адміністратором, з явним
  підтвердженням і перевіркою поточної ревізії. Відновлення створює нову ревізію.
- Перехід до сцени й точного абзацу, профілю героя; для інших сутностей —
  доступне джерело, для матеріалів — посилання на файл.

Перший виклик старого API запрошень також перевіряє `books.ownerId`:
інший користувач не може привласнити серверну книгу, знаючи її ID, чи
переглянути її запрошення до першої реєстрації cowork.

Книга лишається серверним джерелом. Обмежений редактор записує лише дозволений
патч сцени. Картки доступних героїв тепер передаються також через API джерела
та історії, за `externalRef`; недозволені картки залишаються прихованими.
Захист симуляцій/AI лишається у чинних маршрутах ядра та перевірках дозволів.

Коментарі й завдання зберігаються поруч із книгою в SQLite Railway,
у `collaboration_items`; сповіщення — у `collaboration_notices`.
Таблиці створюються автоматично, видалення книги каскадне. Запис і його
сповіщення транзакційні; конкурентні зміни перевіряють `expectedVersion`.
Максимум 2000 записів на книгу та 500 сповіщень на одержувача.
При недоступному SQLite API повертає 503. JSON fallback для цих таблиць немає.

Сервер перевіряє права на кожну ціль та повторно фільтрує сповіщення при
читанні. Чужа/відкликана ціль не виходить через API. Вміст коментарів не
розсилається через WS: оновлення читаються через авторизований API.
Secret Vault, приватні контексти й результати AI не копіюються до співпраці.

## Перевірки

- `test:collaboration-workspace`: 48 перевірок SQLite + Memory;
  з `CORE_TEST_DATABASE_URL` — ще 48 із реальним PostgreSQL ядра.
- `live:collaboration-workspace`: ті самі набори та 12 Chromium-перевірок,
  разом 108. Коментар, завдання, виконання іншим учасником, роль, джерело
  сцени/абзацу, порівняння й підтверджене відновлення; ширина 390 px.
- `test:collab-routes` із PostgreSQL — 28/0, включно із захистом першого
  запрошення, позитивним записом власника та незмінністю власності після відмови.
- `live:access-realtime`: 30 перевірок справжнього зібраного сервера,
  PostgreSQL, WS, заборонених правок, фільтрації книги й відкликання.
- Повний `npm test`, фінальні `lint` та `build` — exit 0.
- `live:acceptance` — 44 сторінки/розміри/теми зі справжнім зібраним сервером
  і PostgreSQL; співпраця також на 390/1440 px, dark/light.
- `test:collaboration-source`, `test:access-enforcement`, `test:access-routes`,
  `test:realtime-auth`, `test:collab-routes`, `test:collab-participants`
  входять у повний `npm test` разом із новим набором співпраці.

Для живого прогону спершу `npm run build`, потім
`CORE_TEST_DATABASE_URL="$TEST_DATABASE_URL" npm run live:collaboration-workspace`.
Новий тест створює унікальний проєкт, видаляє лише його, не скидає схему.
`live:access-realtime` скидає `fusion_core`: для нього використано окрему
локальну тестову базу `t31_realtime`, не продакшн.

Браузерні PNG: `/tmp/t31-browser/work-390.png`, `access-390.png`,
`history-390.png`. Це контрольована React-оболонка з реальними API, не повний App.

## Сценарії для спільного ручного прогону

| Окрема частина | Дії | Очікування |
|---|---|---|
| Команда й ролі | Власник відкриває «Команда й доступ», призначає роль редактора, запрошує людину поштою; окремо дає доступ до однієї сцени | Роль і наданий доступ показані окремо; без доступу зміст не відкривається; запрошення має посилання |
| Коментарі | Коментатор додає записи до сцени, абзацу, героя та зображення; відкриває джерело; пробує чужу сцену через API | Свої записи збережені, абзац має точний ID; чужий запис/ціль закриті; простий переглядач не пише |
| Завдання | Власник задає виконавця й строк; виконавець завершує; керівник змінює строк/виконавця | Статус збережений; виконавець не змінює текст; призначення учаснику без доступу відхиляється |
| Сповіщення | Виконавець відкриває сторінку після призначення; позначає прочитаним; для іншого завдання задають минулий строк | Особистий inbox; прочитання переживає перезавантаження; прострочення не дублюється й зникає після завершення |
| Історія | Автор змінює сцену, порівнює ревізії, підтверджує відновлення; другий клієнт пробує стару поточну ревізію | Знімок і тексти доступні за правами; відновлення додає ревізію; застарілий запис отримує 409 |
| API та WS | Два клієнти: редактор однієї сцени й переглядач іншої; точкова правка, підміна повної книги, потім відкликання доступу | Чужий текст не надходить; недозволена правка не збережена; відкликання діє на наступному запиті та перепідключенні |

## Межі

Повний App локальної production-збірки не перевірений: відсутня справжня
Firebase build-конфігурація. Chromium перевіряє робочі компоненти й API.
Railway, реальні поштові листи та платний AI у цьому прогоні не перевірялися.
Приймання Т4.3 загалом лишається частковим через інші незакриті критерії.
