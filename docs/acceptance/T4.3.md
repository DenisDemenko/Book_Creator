## Прогони та зміни

- Повний npm test; після уточнення схеми Score 0–10 — повторний повний
  npm test і test:jev-levels. Контрактні перевірки — 7.
- Magic Scene з браузером і PostgreSQL — 55+55; Jev Memory/PostgreSQL —
  178; допит Memory/PostgreSQL — 224. Т2.8 входить у npm test.
- live:acceptance — 44 варіанти ізольованого CorePageView зі справжніми
  API/PostgreSQL, серверною сесією й виробничим CSS. JS повного App
  замінюється тестовою оболонкою через request interception; це не тест
  повної навігації App. 44 варіанти без переповнення; фони всіх 22 пар
  dark/light різняться. Google Fonts недоступні через мережеву політику:
  перевірено системні fallback-шрифти. Favicon не є критерієм цього стенда.
- Матеріали: /tmp/t43-browser/report.json та 44 PNG. Переглянуто мобільні
  гілки у світлій темі та тодішній каркас співпраці в темній. Оновлення Т3.1: /tmp/t31-browser — робочі записи, команда й історія на 390 px.
- Нові команди: test:adapter-contract і live:acceptance. Новий тест
  10 ходів не змінює рукопис; контрактний тест замінює реалізацію рантайму
  при незмінному споживачі й перевіряє версії HTTP Jev, hash, scope/tools.
- JSON Schema DecisionResult тепер явно обмежує Score 0–10. Серверний
  hard validator уже вмів обмежувати такі оцінки; тепер це є й у схемі.

Початковий PostgreSQL-прогін зіпсовано паралельними старими тестами,
що виконують DROP SCHEMA в тестовій базі. Повторення на окремих t43_jev
і t43_interview успішні; це не помилка продукту. Браузерний стенд працює
на t43_browser і видаляє лише власний UUID-проєкт, без DROP SCHEMA.
Використовувати тільки окремі локальні тестові бази, ніколи production.

## Відкриті залежності

Т3.1 закрито в #370; протокол та ручні сценарії — [T3.1.md](T3.1.md).

1. Наскрізний App, переходи до всіх джерел та одночасний редактор + AI.
   Локальна production-збірка падає під час Firebase initialization
   (auth/invalid-api-key): при збірці немає VITE_FIREBASE_API_KEY,
   VITE_FIREBASE_AUTH_DOMAIN, VITE_FIREBASE_PROJECT_ID. Потрібна справжня
   конфігурація в налаштуваннях збірки; ключі не вигадувалися.
2. Реальний DeepSeek Harness та його upgrade. Поточний MVP за раніше
   погодженим рішенням використовує in-process runtime.
3. Платні моделі, семантична якість прози та Railway не перевірені.

Перед продакшн-перевіркою на прохання власника нагадати про захищений
SECRET_VAULT_KEY_BASE64 на Railway; значення не передавати в чат чи Git.
Т4.3 залишається частково прийнятим до закриття зазначених залежностей.
