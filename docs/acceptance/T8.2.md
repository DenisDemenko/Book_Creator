# Т8.2 — ручне приймання STEAM Teams v2.0

Макети: Stitch 9 `fusion_lab_steam_teams_v2.0_1` і `_2`. Реалізація — Fusion-Lab-Marketplaes, публічні `/teams` і `/teams/:id`, українська й англійська.

1. Оновити Marketplace, виконати `npm ci`, `npm test`, `npm run typecheck`, `npm run build` з власною Firebase конфігурацією. Реальний вхід у production перевіряється окремо.
2. Відкрити каталог в обох мовах: палітра cream/terracotta/sage, вступ, чотири лічильники, пошук, напрями, двоколонкові картки, правила й нижній CTA. Дані мають відповідати опублікованим командам, не числам макета.
3. Перевірити всі п’ять напрямів. Українські значення API лишаються однаковими в обох локалях; підписи англійською перекладені. Фільтр має бути видимим у URL та `aria-pressed`.
4. Знайти команду за назвою, комбінувати пошук із напрямом, перевірити порожній результат і скидання. Після reset поле пошуку має очиститися; після refresh фільтри відновлюються з URL. Лічильники всього каталогу не змінюються від фільтра.
5. «Створити команду» веде до чинної форми `/account/teams/new`, «Мої команди» — до кабінету. Увійти власником, створити команду зі згодою на фото й дочекатися модерації. До схвалення вона не має з’являтися публічно.
6. Запросити двох зареєстрованих учасників. Один приймає, другий чекає. Склад профілю показує лише підтверджених, а кількість зайнятих місць включає очікуване запрошення. Назви й фактичні ролі мають відповідати кабінету. Немає вигаданого ментора, рейтингу чи спеціалізації.
7. Відкрити команду з фото й без фото, перевірити мету/опис і всі п’ять посилань на розділи. Після вибору розділу він доступний, активне посилання позначене. Довгий текст не перекриває sidebar.
8. Власник додає фото й публічний STL/PDF через кабінет. У профілі перевірити назву, розмір і скачування точних байтів файла. Без файлів — зрозумілий порожній стан. Артефакти тут публічні; не завантажувати в них секрети книги.
9. Вакансії, заявки, структурований стек, етапи, командний чат, ревізії, пакетний експорт і Resource ACL мають чесний PLANNED. Не повинно бути фальшивих форм подання/чатів/прогресу чи успішних сповіщень без API.
10. Участь у команді не надає доступу до книги. Професійна роль тепер призначається з активного реєстру Studio в кабінеті команди; імпорт до книги потребує окремого підтвердження власника книги й команди. Доступ до тексту надається незалежно через Access Grants.
11. Перевірити невідому й неопубліковану команду: 404, без приватного складу чи файлів. При недоступному API каталог лишається доступним із порожнім станом.
12. Пройти на телефоні 390px: пошук, reset, картки, навігація розділів і файли. Немає горизонтального переповнення сторінки; широка таблиця може прокручуватись всередині. З клавіатури видно focus; кнопки/посилання мають доступні назви.

## Межі

Локальна хмарна перевірка використовує реальні Next/Nest/PostgreSQL з ізольованими тестовими даними й тестовим Firebase verifier. Це не підтверджує production login, деплой, роботу реальних акаунтів, наскрізне шифрування, age verification або автоматичні виплати. Т8.3 та етап 9 не реалізуються в цьому пункті.


## Ролі й підтверджений міст — 12.10.2026

Локально: Marketplace Postgres/API23/0 (10 нових + 13 регресійних), Studio API12/0, Chromium компоненти5/0 з контрольованим API. API/parser tests не є Firebase production-прийманням. Типи/build успішні; фінальні перевірки фіксуються в журналі #421.

1. Увійти власником команди в /account/teams/:id. Реєстр повинен завантажитися зі Studio; owner/member залишаються окремими статусами. Запрошений, який не прийняв, не може отримати професійну роль.
2. Обрати підтвердженого учасника й «Редактор», перевірити блокування кнопки без згоди. Підтвердити: роль збережена, каталог/профіль показує правильну UA/EN назву, журнал має автора дії та ревізію. Чужий користувач/звичайний учасник/гість через API не можуть це повторити.
3. Фрілансер потребує активної спеціалізації; невідома/застаріла роль, власність проєкту, несумісна комбінація й зайнята одинична роль відхиляються. Owner/member не змінюються.
4. Два браузери з однаковою ревізією: один запис успішний, другий отримує409. Після оновлення форми можна повторити; однакове призначення не дублює роль.
5. Під власником книги, який також є власником команди, відкрити Studio → Спільна робота → Команда → Ролі з STEAM-команди; ввести ID команди та переглянути snapshot. Перегляд нічого не призначає. Стороння команда, відсутній міст чи незареєстрований/вимкнений Studio-акаунт відхиляються.
6. Обрати підтверджену роль і явну згоду. Імпорт призначає тільки цю роль в цій книзі; у події є teamId/assignment/revision/registry. Учасник все ще не читає книгу без окремого Access Grant. Після самостійного надання власником scope перевірити лише дозволений уривок.
7. Відкликати роль команди до підтвердження старого snapshot: імпорт відхиляється409. Оновлення реєстру також відхиляє стару форму; перепризначення підтверджує нову версію.
8. Відкликання ролі команди не скасовує незалежну роль/дозвіл книги. Власник відкликає роль книги штатною кнопкою Studio, а наданий доступ — окремою дією. Немає мовчазного видалення ручних ролей/доступів.
9. Відключити реєстр: нові призначення не приймаються, помилка видима. Відкликання збереженої ролі команди доступне, журнал збережений. Перезапуск API зберігає roles/revision/audit.
10. На390px і з клавіатури перевірити селектори, спеціалізацію, згоду, журнал, revoke, повідомлення409/503 та обидві мови. Окремо перевірити реальний Firebase-вхід.

Порядок розгортання: Studio з public schema endpoint → Marketplace API з міграцією → Marketplace frontend. STUDIO_ROLE_REGISTRY_URL — серверна адреса реєстру; типово https://www.fusionlab.in.ua/studio/api/collaboration/team-role-registry. Для знімків команди використовується чинний x-bridge-key. Нових секретів немає; реєстр не містить даних книг/користувачів.
