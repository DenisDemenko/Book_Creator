# Слеби та столи Fusion Lab

Модуль для індивідуального столу з дерева й епоксидної смоли. Джерело складу, котирувань, резервів і передзамовлень — PostgreSQL маркетплейсу. Studio Book_Creator адмініструє ті самі дані через наявний серверний міст.

## Сторінки

- `/table-builder` (також локалізовані маршрути): публічний 2D-конструктор, фільтри, розміри, колір смоли, ніжки, погодження серверного котирування. Для додавання в кошик потрібен Firebase-вхід.
- `/cart`: окремий блок столів з повною ціною, передоплатою 50%, залишком, оплатою LiqPay та станом виробництва. Звичайні товари лишаються у своєму існуючому checkout.
- `/admin/slabs`: адміністратор маркетплейсу — фото, калібрування, контур, склад, тарифи, виробництво.
- Nova OS → **Слеби та столи**: ті ж склад і виробництво через API-міст.
- Nova OS → **Управління цінами** → **Опублікувати тарифи конструктора столів**: явне затвердження ставок поточного меблевого калькулятора.

Палітра, кнопки, картки й поля відповідають `globals.css` маркетплейсу. Хост передає шрифти й дизайн-токени редактору. Ізольований iframe запобігає витоку CSS та дозволяє використовувати той самий редактор у двох застосунках. Токени Firebase та секрет мосту в iframe не передаються.

## Перед встановленням

1. Перевірити базові SHA пакетів. Застосовувати патчі до відповідних репозиторіїв; чужі незакомічені правки зберегти. Пакет не містить секретів чи баз.
2. У marketplace: `npm ci`, потім з `apps/api` — `npx prisma generate`, `npx prisma migrate deploy` з налаштованим `DATABASE_URL`. Є нова міграція `20261026000000_slab_tables`.
3. Зібрати й установити API, потім вебмаркетплейс. Старий API не знає `/tables` та `/bridge/tables`, тому встановлюється першим.
4. Зібрати й установити Book_Creator. Там використовується вже наявне налаштування адреси API мосту та зашифрованого ключа; новий секрет не потрібен.
5. У Студії опублікувати тарифи з меблевого калькулятора. Перевірити окрему ставку дерев’яних ніжок у «Слеби та столи → Калькулятор витрат».
6. Додати власні фото та перевірити контури. Реальна база автоматично не наповнюється демонстраційними слебами.
7. Перевірити sandbox LiqPay: його `server_url` — `/tables/payments/liqpay/callback` на `API_PUBLIC_URL`, повернення — `/cart` на першому `WEB_ORIGIN`. Потрібні наявні `LIQPAY_PUBLIC_KEY`, `LIQPAY_PRIVATE_KEY`; `LIQPAY_SANDBOX=1` лише для тесту.

Не застосовувати міграцію до production під виглядом локального тесту. Деплой і реальні платежі цією сесією не виконувалися.

## Фото й масштаб

Знімок зверху, без перспективного спотворення, на однотонному контрастному фоні. Задати відому відстань у см і позначити її кінці. Автоматична сегментація відділяє найбільший об’єкт від кольору фону або прозорості. Контур редагується вершинами; є ручне малювання. Shift+клік додає вершину, Alt+клік видаляє. Перед збереженням перевіряються масштаб і самоперетини. Клієнт стискає фото, сервер приймає до 500000 символів data URI. Контур можна завантажити SVG з фізичними одиницями мм.

Фото під кутом не дає метрологічно точних розмірів за одним відрізком. Внутрішні отвори, порожнини та пористість дерева не моделюються окремо. Перед виробництвом потрібна перевірка майстром. Максимум 6 унікальних слебів та 128 вершин кожного контуру.

## Розрахунок

Розміри — см. Площа дерева обчислюється всередині форми столу; виступи обрізаються. Площа заливки = площа столу мінус об’єднання площ дерева. Чисельний крок — найбільший габарит / 650; це оцінка, не CAD-обчислення точної площі. Перетини понад 2 см² блокуються; надто малі й тонкі деталі можуть вимагати ручної перевірки.

Літри = вільна площа м² × товщина см × 10. Маса = літри × густина × (1 + запас / 100). Дерево оплачується повними вибраними слебами, разом з обрізками. Роботи й фініш — ставки на м²; ніжки — за комплект; націнка — на всі витрати. API перевіряє товщину, доступність і конфігурацію та ігнорує передану клієнтом ціну.

При публікації калькулятора Студії смола переводиться з грн/л у грн/кг за густиною 1,1 кг/л. Фініш і решта витрат нормалізуються на прямокутну площу базового шаблону; підстілля береться за комплект. Ефективна націнка включає податки й маржу калькулятора. Така модель відтворює повну собівартість базового шаблону; для іншого розміру це саме модель ставок на м², а не повторний розрахунок усіх технологічних операцій. Ставка дерев’яних ніжок зберігається окремо. Адміністратор погоджує публікацію.

Котирування діє 30 хвилин до додавання в кошик. Ціна, конфігурація, слеби та витрати фіксуються на сервері. Редагування композиції скидає погодження. Гроші в БД — цілі копійки; передоплата = ceil(totalMinor/2).

## Передзамовлення та оплата

`cart → pending → queued → making → ready`.

На checkout транзакція блокує передзамовлення й атомарно резервує кожен слеб. Повторний checkout повертає той самий платіж. Чужі передзамовлення недоступні. Скасування неоплаченого передзамовлення або підтверджена відмова платежу звільняє резерв. Покинуті pending-замовлення автоматично не прострочуються: їх скасовує покупець; окрема процедура прострочення/адмінскасування не входить у цю версію.

`queued` ставиться лише після перевірки підпису LiqPay, номера, UAH і точної суми 50%. `wait_accept` не вважається сплаченим. Sandbox приймається тільки при `LIQPAY_SANDBOX=1`. Повторний callback не дублює виробництво. Пізній платіж за скасоване замовлення переходить у `payment_review`, не відбираючи слеби іншого замовлення. Адміністратор має вирішити його вручну; автоматичне повернення, chargeback, стягнення другої половини й адміністративний платіжний арбітраж не реалізовані.

Демо доступне без реальних ключів лише за існуючою політикою `demoConfirmationsAllowed()`. Демо/sandbox помітні в кошику та виробництві, не видаються за реальні кошти.

## API-міст

`/bridge/tables/state`, `POST /bridge/tables/slabs`, `DELETE /bridge/tables/slabs/:id`, `PUT /bridge/tables/costs`, `GET /bridge/tables/production`, `PATCH /bridge/tables/production/:id`.

Сервер Студії викликає їх через обмежені `/api/admin/slab-tables/*` маршрути з `requireAdmin`; ключ залишається на сервері. Зміна тарифів вимагає поточної `expectedVersion`, щоб два адміністратори не затерли ставки один одного.

## Перевірки

Локальна PostgreSQL — окрема тестова база. Перевірено 7 інтеграційних сценаріїв: адміндоступ і власність, серверна ціна, конфлікт версій витрат, конкурентне резервування, повторний checkout/скасування, підпис/сума/idempotency платежу, пізня оплата та захист мосту. Є 5 геометричних тестів, сегментація білого й прозорого фону, реконструкція ставок калькулятора Студії та перевірки TypeScript.

Браузер Chromium: завантаження синтетичного фото → масштаб 100 см → автоконтур → PostgreSQL → 2D-композиція → серверна ціна → редагування скидає ціну → погодження → серверний кошик. Авторизований редактор перевірявся через ізольований тестовий хост зі стандартною тестовою автентифікацією API; сама публічна сторінка Next.js перевірена через її справжній RPC-хост. Додатково знято мобільний стан. Справжній Google/Firebase-вхід, production Studio та реальне списання LiqPay не перевірені.

Підсумок регресії: 170/171 API e2e пройшли в повному прогоні; єдиний тест team-passports-browser вимагав відсутньої тоді production-збірки. Після успішного Next.js build цей тест повторено: 1/1 пройшов (15 браузерних перевірок). Отже всі 171 сценарії мають успішний результат за основним прогоном і цільовим повтором; весь набір після build повторно не запускався. API unit — 16/16; web tests — успішні. TypeScript в обох застосунках — exit 0. Studio adminOS — 58/58, калькулятор — 23/23; нові тести мосту — успішні. API і Next.js production build — exit 0. Studio Vite/esbuild та обидва допоміжні кроки build виконані; CLI tsx замінено на node --import tsx лише для локальної перевірки через IPC EPERM. TypeScript Studio після вилучення згенерованого dist із робочого каталогу пройшов з heap 4 ГБ; перший прогін після build вичерпав ліміт 2 ГБ. Це локальні результати, не GitHub CI.
