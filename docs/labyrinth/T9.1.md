# Т9.1 — модель дворівневого лабіринта

Реалізовано 09.10.2026. Це приватна авторська модель, версії й структурний API. Конструктор без коду — Т9.2, повна прохідність/небезпеки — Т9.3–Т9.5, цифровий читач — Т9.6. Нового публічного інтерфейсу проходження ще немає.

## Дані та зв’язки

Договір: `shared/labyrinth.ts`. Невеликий приклад: `shared/labyrinthDemo.ts`.

- Вузли мають стабільні ID, нижній/верхній рівень, цілі координати, опис, укриття й необов’язковий `sceneId` на наявну сцену ядра.
- Переходи: нижній коридор, верхній міст, сходи/драбина/підйомник між рівнями; напрям, тривалість, вартість ресурсів, умови станів об’єктів. `overNodeIds` дозволений лише мосту й містить лише нижні вузли.
- Механізми: двері, решітка, перемикач, генератор, бар’єр, схованка, механізм мосту. Автор явно задає допустимі стани й переходи. Ефект змінює лише об’єкти, на які правило прямо посилається, незалежно від рівня; не всі об’єкти поруч.
- Герої мають власний старт, ресурси, інвентар, цілі, страхи й знання. `entityId` героя/об’єкта повторно використовує підтверджену сутність цієї книги. Канон сутності не копіюється і не змінюється. Контрольована власна модель ресурсів не є оцінюванням емоцій людини.
- Шаблони подій мають вузли, умови, попередження, час підготовки, тривалість, cooldown, ефекти й спосіб уникнення. Т9.1 зберігає декларації; не запускає газ/ворогів чи Jev.

Валідатор відхиляє дублікати, невідомі поля/посилання/стани, нелегальні рівні, неоднозначні переходи, конфліктні ефекти, негативні ресурси й завеликі списки. Він перевіряє структуру; досяжність з урахуванням усіх небезпек і ресурсів — окремий рушій Т9.3.

## Версії, канон і збереження

Міграція `0035_labyrinth.sql` у `fusion_core`: maps, immutable versions, runs, run events/checkpoints. Використовується наявний `CORE_DATABASE_URL` і пул ядра, не окрема SQLite-база або `DATABASE_URL` Marketplace. SQL накочується штатним запускачем із checksum/advisory lock. Старі міграції не змінені. Docker вже копіює всю теку `core-migrations`.

Кожна нова карта отримує v1. Подальший запис **додає** v2/v3, а не редагує v1. Версія має hash, автора, час і `bookRevision` канону. Hash канонічно сортує ключі, тому JSONB/Windows не змінює його порядком властивостей. Прогін посилається на конкретні `(projectId,mapId,mapRevision)`, seed і власний стан. Поточний режим — `author_preview`: учасник-автор та його hero IDs фіксуються явно; це не автоматичне запрошення учасників книги. Складність та груповий контроль розширяться у Т9.3–Т9.7. `bookRevision` фіксує джерело; Т9.1 не створює знімок усіх байтів рукопису, не підмінює служби історії книги й не збирає видання.

Дія зберігає новий стан і контрольну точку однією транзакцією; журнал включає ревізію, автора, ручну причину, версію карти, normalized action, before/after hashes і фактичний стан. Ревізія0 — початкова контрольна точка. UPDATE старих карт/контрольних точок заблоковано тригерами. Складені FK не дають прогону послатися на карту іншої книги. Видалення самого проєкту штатно прибирає його модель; endpoint видалення історичних версій не доданий.

`turn` — кількість ручних структурних дій; `storyTime` — сума їхніх тривалостей у ходах. Це локальні лічильники прогону, не дубль календаря/таймлайна канону. Подальші фазові таймери, паузи, контрольні відновлення й довга сюжетна дуга належать наступним задачам.

## Приватний API

База: `/api/core/projects/:projectId/labyrinth`. Поточна сесія Studio обов’язкова. Усі маршрути — лише власнику книги або адміністратору; читач/редактор/сторонній не отримує повну карту, знання й приховані події. Спільний доступ до книги не є доступом до майбутнього читача лабіринта. Користувацькі екрани й фільтрація знань героя будуть у Т9.6–Т9.7 через наявні правила доступу.

| Метод / шлях | Дані / результат |
|---|---|
| GET `/maps` | До100 останніх метаданих; без великих графів; `mode=author_structural_preview`, `readerAvailable=false` |
| POST `/maps` | `{definition,expectedRevision:0}` → immutable v1 |
| GET `/maps/:mapId/versions` | До100 метаданих версій, новіші першими |
| GET `/maps/:mapId/versions/:revision` | Конкретний повний snapshot |
| POST `/maps/:mapId/versions` | `{definition,expectedRevision}` → наступна версія |
| POST `/maps/:mapId/runs` | `{mapRevision,seed}` → незалежний авторський прогін |
| GET `/runs/:runId` | Поточна ревізія/стан/seed/версія карти |
| GET `/runs/:runId/events?after=N` | До100 контрольних точок після ревізіїN; без курсора — з початку |
| POST `/runs/:runId/structural-actions` | `{expectedRevision,action}` → новий стан та подія |

Структурні дії:

```json
{"kind":"move","heroId":"hero","edgeId":"up"}
```

```json
{"kind":"interact","heroId":"hero","objectId":"generator","to":"off"}
```

Перехід вимагає правильної початкової позиції, напрямку, виконаних умов і ресурсів. Взаємодія — присутності біля механізму й дозволеного переходу стану. Це ручна авторська перевірка графа; вона не видається за читача із захистом від останнього заблокованого виходу. Повний safety gate буде у Т9.3.

Ревізії — цілі числа, не рядки. Для конкурентних записів карти/прогону — row locks + CAS: один успіх, інший409. Клієнт не надсилає готовий стан, автора, роль, номер нової версії, AI-ключ або команду публікації. Усі відповіді `Cache-Control:no-store`. Без готового ядра —503, чужий ID —404 після перевірки прав, некоректний graph/action —422.

## Перевірка

```powershell
npm run test:labyrinth
npm run build
```

Перший запуск перевіряє модель без бази. Для живого API/міграцій/CAS/restart потрібна **окрема тестова PostgreSQL з pgvector**, не production:

```powershell
$env:CORE_TEST_DATABASE_URL = "<URL окремої тестової PostgreSQL>"
npm run test:labyrinth
Remove-Item Env:CORE_TEST_DATABASE_URL
```

Тест створює свої проєкти й прибирає їх; міграції лишаються в тестовій базі. `test:core-db` окремо видаляє схему `fusion_core`, тому його можна запускати тільки в одноразовій базі. Значення production-секретів у чат або Git не передавати.

Production-приймання після деплою: [Т9.1](../acceptance/T9.1.md). Реальна сесія Firebase, Railway v35 й restart production ще не підтверджені.
