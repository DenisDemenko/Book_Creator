# Secret Vault — Т4.1

The Vault uses AES-256-GCM with a fresh 96-bit nonce for every sealed payload.
The key is exactly 32 random bytes from `SECRET_VAULT_KEY_BASE64`, stored in the
server's protected environment, outside PostgreSQL. The application never creates
or writes a persistent key. Missing, malformed or wrong keys fail closed. Securely
back up the original key with encrypted database backups; changing the environment
variable is not a rotation procedure and makes existing ciphertext unreadable.
No automatic rotation or external KMS is implemented.

Provision the value in Railway's protected variables. Generate 32 random bytes
with a trusted local tool (for example `openssl rand -base64 32`) and enter the
result there. Never put a real value in this repository or chat.

Ciphertext is bound to project, secret ID and version through AEAD associated data.
The commitment hashes the same identity, a random encrypted salt, text, bounds and
reveal policy. Versions are append-only, and used/frozen secrets cannot regenerate.
An append-only hash chain records metadata, not text. PostgreSQL triggers reject
rewritten audit, identity, versions and director plans even through direct SQL;
normal deletion of an entire project remains possible through the FK cascade.
Technical administrators with access to both the key and database can decrypt
secrets. This is stated in the author UI. AI providers used for private steps also
receive that step's private content; their data-retention policy is outside the
application's control. No infrastructure-admin secrecy is claimed.

Personal secrets go only to their character. False beliefs are explicitly marked
`character_belief`, truth `false`, and are never inserted as `world_truth`.
World secrets are not available to characters before story revelation. A dedicated
Mystery Director receives only the requested world secret; its hints/plans remain
encrypted. CausalityService checks earliest scene, canonical evidence chronology
and contradictory claims. Formal checks do not establish semantic consistency of
arbitrary prose or generated secret content with natural-language author bounds.

A private character step gets its own sealed facts and returns only one action
from a finite server allowlist. Private facts are excluded from Jev caches, voice
prompts, the literary writer, scene protocols, index documents and normal API
responses. Free-form output from that private step is discarded. The private AI
mode logs only usage metadata and masks provider error/retry content. A malicious
or mistaken provider cannot return secret-derived prose into the public pipeline.
Observable behavior may still reflect the secret through the chosen action.

The UI is on the scenario branches page, alongside Magic Scene. Create the run
first, then secrets before its first turn. Author-hidden secrets are generated by
the curator; visible secrets may be entered by the author. Freeze and regeneration
use explicit revisions. Emergency Reveal requires confirmation and shows text only
in the current response/UI; it freezes the version but does not reveal it in-story.
All Vault responses use `Cache-Control: no-store`. The reader can hide the displayed
text, and subsequent ordinary GET requests contain only safe metadata.

Confirmed story revelation first checks causality and returns text plus a proposed
`/revelation` tag. It never changes the manuscript. The author may create a separate
T3.3 branch, review its diff and explicitly approve the fragment. Existing scene
knowledge boundaries prevent reading a revelation in an earlier scene. Archiving a
simulation closes its run and archives its unrevealed secrets. Revealed knowledge
is preserved. Branch approval, not hidden generation, creates manuscript content.

Verify with `npm run test:secret-vault` and optionally `-- --browser`. Add the
existing dedicated `CORE_TEST_DATABASE_URL` to exercise PostgreSQL triggers. Tests
use fresh temporary keys and controlled model answers; they do not validate a
Railway deployment, paid model quality or provider retention.
