# Т6.6 — ШІ з урахуванням співпраці

Graph Studio v3.0 §53–54, критерії №43–44. Реалізовано 08.10.2026, журнал #392.

## Контрольовані вузли

COLLAB_QUERY виконує одну з восьми операцій:

| Операція | Результат |
|---|---|
| FIND_PARTICIPANT | Активні учасники без email та приватних профілів |
| FIND_SPECIALIST | Учасники з указаною roleId або спеціалізацією |
| GET_PROJECT_ROLES | Ролі в межах видимого списку учасників |
| GET_ACCESS_SCOPE | Фактична область тільки поточного користувача |
| GET_CONTRIBUTIONS | Внески лише в доступні сцени |
| GET_OPEN_TASKS | Відкриті завдання з доступною ціллю |
| GET_DELIVERABLES | available=false: результати фахівців ще належать етапу 7 |
| GET_AVAILABLE_CONTEXT | Дозволені розділи, сцени й картки героїв |

Власник/учасник із повним доступом може шукати всіх активних учасників;
обмежений користувач бачить тільки власну участь. «Доступний спеціаліст»
означає активного учасника, а не підтверджену зайнятість або фріланс-профіль.

Кожна операція перечитує обліковий запис, права книги, область ресурсу та
поточну серверну копію. Проєкт і користувач беруться з запуску/авторизації,
а не з model args. Людина, що схвалює паузу, не підміняє
ініціатора COLLAB-запитів: повторна авторизація прив’язана до startedBy. QUERY не видає прав, не призначає ролей і не зливає канон.
Колабораційний контекст не містить довільних book metadata/нотаток чи
розшифрованого Vault. Немає system:workflow обходу для COLLAB_QUERY.

Перед LLM, кожним повтором і COLLAB_PROPOSAL контекст перечитується та
порівнюється з прочитаним знімком. Зміна прав або даних зупиняє процес;
потрібно почати новий запуск. Простого збереження старого контексту після
відкликання прав недостатньо для модельного запиту. Трасування містить
операцію та authorized actor; чутливий контекст не дублюється у trace.
Журнал/керування такими запусками та їхніми підпроцесами потребує повного
доступу книги, окрім загального права Graph Studio.

## Пропозиції завдань

COLLAB_PROPOSAL створює pending TaskSuggestion: назва, ціль, необов'язковий
кандидат, причина, автор і час. Це не завдання, нова роль, наданий доступ чи
зобов'язання. Параметри задаються в графі; `from_output=true` читає title,
target/candidateId/reason з перевіреного JSON у state.output після VALIDATOR.
Статична target у графі має пріоритет над model output. Поля користувача,
проєкту, статусу і схвалювача модель не задає.

Власник або адміністратор у «Спільна робота → Пропозиції та внески»
завантажує пропозиції ШІ, читає причину, явно обирає ID виконавця й
підтверджує або відхиляє. Перед підтвердженням повторно перевіряються права
автора та доступ активного виконавця до цілі. Виконавцю не відкривають книгу.

Accepted-пропозиція, завдання й персональне сповіщення записуються в одній
SQLite-транзакції через наявний workspace store. Повторне або одночасне
підтвердження не дублює завдання. Відхилення не створює завдань. Pending-
пропозиції читають їхній автор і власник/адмін, тільки за доступною ціллю.
Завдання після підтвердження діють у наявному просторі співпраці Т3.1.

## API і зберігання

`/api/core/projects/:projectId/collaboration/ai`:

- POST /query — operation, args; тільки читання;
- GET /suggestions — список для автора/власника/адміна;
- POST /suggestions — тільки pending;
- POST /suggestions/:id/accept — явний assigneeId;
- POST /suggestions/:id/reject — без створення завдання.

Відповіді no-store; SQLite proposals належать серверній книзі. Core
залишається Memory/PostgreSQL. Міграція Core не потрібна. Ліміти: до 100
учасників у результаті, 200 завдань, 500 пропозицій; внески — межі Т6.5.
Пропозиція завдання потребує comment або вищого доступу до цілі.

## Перевірка й межі

`test:collaboration-ai` — авторизація, вісім операцій, читання в межах сцени,
незмінність ролей/доступу, pending → explicit accept/reject, відкликання,
реальні COLLAB_QUERY/COLLAB_PROPOSAL, зупинка LLM і захист журналів.
`live:collaboration-ai` після build — справжній UI/API, явне підтвердження,
390 px. PostgreSQL — через CORE_TEST_DATABASE_URL у новій тестовій базі.

Реальні AI/Firebase/production-сесії ще потребують ручного приймання.
Календарі доступності, зовнішній пошук на біржі, deliverables/замовлення та
платіжні зобов'язання — етап 7. Автоматичної видачі прав і призначень немає.
[Сценарій приймання](docs/acceptance/T6.6.md).
