# Етап 10 — Mafia Story Studio

Дата: 09.10.2026. Джерело: [ТЗ власника, 21 розділ](docs/tz/TZ_MAFIA_STORY_STUDIO.md).
**Статус: не почато.** Збереження ТЗ і плану не означає реалізацію ігрового продукту. Нумерація Т10 — загальна дорожня карта; чотири релізні етапи нижче відповідають §19–20 ТЗ.

## 1. Місце у спільній Studio

Story Builder → Game Master Dashboard → Player Experience, зі сценарним Marketplace та SaaS. Спільний Story Engine обслуговує авторські книги, практичні конспекти, інтерактивні історії, лабіринти й сюжетні ігри через окремі адаптери. Не копіювати редактор, користувачів, онтологію, grants або AI-маршрутизацію без перевірки наявної реалізації.

Jev допомагає автору зі структурою, темпом, конфліктами та дозволеними подіями; у грі він рекомендує ведучому або обирає за явно дозволеною політикою. Його модель не підраховує остаточні голоси, не видає доступ і не є джерелом істини ігрового стану. Фізика лабіринту не потрібна «Мафії». Загальнокнижкова інтеграція: [JEV-BOOKS-1](PLAN_JEV_AUTHOR_BOOKS.md), ще не реалізована.

Чернетка сценарію, зафіксована версія сценарію, стан окремої партії та публічна картка товару — різні об’єкти. Партія не переписує сценарій. Оновлення товару не змінює запущені партії. Перетворення зіграної історії на книгу — окремий явний процес з погодженням внесків і співавторства, не автоматична публікація секретів чи повідомлень.

## 3. Дані й межі стану

Базові сутності ТЗ зберігаються. Не створювати дублікати User/Project/World/Character там, де потрібні посилання. Остаточні міграції — Т10.1.

- Scenario / ScenarioVersion: чернетка, immutable version, ruleset, світ/сюжет/персонажі, ролі/команди, секрети/докази, фази, тригери, таймінг, альтернативні фінали.
- RoleDefinition / Faction: **ігрова** роль, команда, дозволені дії, число використань, цілі/перемога; це не роль Platform/User.
- GameSession: project/scenarioVersion, режим live/test, ведучий, статус, раунд/фаза, revision, server timestamps, pause/timer, ruleset version і seed за потреби.
- PlayerSeat / PlayerAssignment: конкретне місце, користувач після claim, персонаж/роль/команда, статус, здібності/завдання. Підготовка списку створює місця, не фіктивні акаунти й не згоди реальних людей.
- SessionKnowledge / Reveal: кому, яку версію доказу/секрету відкрито, за якою подією; client отримує тільки свою проєкцію.
- Action / GameEvent / Receipt / Checkpoint: журнал переходів, actor, expectedRevision, idempotency key, наслідки й приватна аудиторія; точне відновлення після restart без повторних дій.
- VoteRound / Ballot / Tally / Override: правила допуску, відкритості й нічиєї, приватні бюлетені, підсумки, історія та ручна корекція з причиною, без стирання оригіналу.
- Message, GameResult, AIRecommendation, Invitation та MarketplaceItem/Purchase/ScenarioReview — із чіткими owner/session/visibility/version полями.

Таймер визначає сервер (deadline і залишок паузи), UI лише відображає. Restart/reconnect не запускають фазу повторно. Порядок одночасних дій, нічні здібності, смерть/лікування, нічиї та перемога задаються зафіксованими правилами. Мінімальний ruleset «Мафії» і схема авторських здібностей мають бути визначені в Т10.1; довільний JavaScript у правилах/тригерах не допускається.

## 4. Авторизація та секрети

Розділити платформні ролі, проєктні обов’язки, session permissions і приховану ігрову роль. Platform Owner/Administrator не трактувати автоматично як ведучого кожної партії: привілейований доступ до секретів визначається окремою явною політикою та аудитом. Автор купленого сценарію не отримує доступ до приватних повідомлень чужої партії лише через авторство.

| Видимість | Серверна умова |
|---|---|
| PUBLIC | Явно опублікована версія; публічна картка не містить прихованих ролей/відповідей |
| PROJECT | Чинний scoped project grant; участь у грі не дорівнює участі в авторському проєкті |
| ROLE_BASED | Конкретний session assignment і дозволена інформація ролі, не роль із request body |
| PRIVATE | Конкретний одержувач у цій сесії |
| SECRET | Явна аудиторія та умова розкриття; відсутність дозволу = відмова |
| GAME_MASTER_ONLY | Призначений Host або Assistant з конкретним правом; за замовчуванням Assistant без усіх секретів |

QR/link/code — запрошення, а не безстроковий ключ до даних. Непередбачуваний токен з TTL, серверний hash, одноразовий claim, rate limit, прив’язка до session/seat і захищена сесія після входу; роль/персонаж із URL не довірені. QR не містить секретів. Один QR не може привласнити вже зайняте місце. Зміна гравця потребує дії Host та аудиту.

Перевіряти кожне читання, дію, websocket-підписку/подію, файл, експорт, пошук і AI-контекст; відкликання діє на наступній операції та перепідключенні. Не передавати повний сценарій із прихованими полями до браузера. No-store для приватних відповідей; не класти секрети в URL, логи, analytics, service-worker cache чи загальний localStorage. Вихід/зміна seat очищають приватний UI state. DB не публікується гравцям, credentials лише на сервері; ACL API не замінює мережеву ізоляцію й DB privileges. Адміністратор інфраструктури поза довіреною моделлю гравця — не обіцяти захист від власника DB.

### Межі MVP

MVP покриває всі 17 пунктів §19, використовуючи наявну реєстрацію після перевірки, а не створюючи другу систему акаунтів. Вісім стандартних фаз; конфігурація ролей/команд; ручні події та базові детерміновані наслідки. Повні автоматичні тригери, AI-балансування, симулятор, продажі й нові тарифи — наступні релізи; UI не заявляє їх доступними до реалізації. До підтримки механіки валідатор відхиляє її явно, а не мовчки ігнорує.

## 6. Marketplace, ліцензії й тарифи

Публічна картка містить усі поля §15. Після підтвердженої покупки сервер створює entitlement на конкретний товар/версію згідно з ліцензією; ціна/currency/commission не беруться з клієнта. Повтор payment webhook не створює другу покупку, refund/revoke має визначені наслідки для нових запусків і чинних сесій. Підтримка завантаження в ТЗ зберігається: ліцензований пакет може містити секрети для ведучого-покупця, але не є публічним download і не відкривається гравцю.

Публікація сценарію, завершення партії, допис у Marketplace і видання книги — окремі явні дії. Рейтинг/кількість ігор не допускають підміни client body; звіт і рейтинг не розкривають приховані ролі, клієнтські дані чи приватні повідомлення без визначеної політики розкриття після фіналу.

Free/Host/Professional Host — варіанти з ТЗ, не активні тарифи. Конкретні ціни, caps, комісія 20–30% чи інша, license terms, правила відгуків, refunds і payout уточнюються перед Т10.10–Т10.11 на готовій специфікації; приклад ставки не є дозволом на списання коштів. «Необмежені сценарії» не означає безмежні AI-витрати або storage: правила fair use і квоти задаються окремо. Наявні плани Studio не змінювати в межах документації.

## 7. Окремі живі сценарії за кожним пунктом

Нижче — майбутнє приймання, **не пройдені тести**. Локальні тестові principal/моделі й авторизований production-прогін позначаються окремо. Для ізоляції підготувати тестових Author, Co-Author, Editor, Host, Assistant, Player A/B, Observer, Guest та стороннього користувача; дві партії/проєкти. Не використовувати справжні секрети людей. Для кожного прогону зберегти версію сценарію/ruleset, дію/очікування/фактичний результат, revision, часові метрики, pass/fail/unrun.

### Т10.1 — модель і доступ

1. Створити дві сесії одного сценарію: різні assignments/state; дія в першій не змінює другу або сценарій.
2. Player A підміняє project/session/seat/role IDs у GET/POST та websocket: чужий секрет відсутній, сервер відмовляє без зміни revision.
3. Host другого проєкту, Assistant без secret capability, Observer та Administrator без визначеного session права не отримують GM-only інформацію.
4. Два однакові запити із receipt дають один перехід; інший body з тим самим ключем — конфлікт. Перезапуск зберігає стан.

### Т10.2 — конструктор

1. Побудувати сценарій із світом, всіма полями персонажа, мафією/мирним/комісаром/лікарем та авторською роллю, командами, секретом, доказом і фіналом.
2. Зберегти v1, відкрити v2; стара версія незмінна. Конкурентна правка повертає конфлікт, не губить дані.
3. Редактор без secret grant не читає приховане через форму, API, експорт або AI. Непідтримувана здібність явно відхиляється.

### Т10.3 — підготовка й запрошення

1. Створити місця й картки, розподілити ролі; змінити всі параметри підготовки, потім запустити зафіксовану версію. Неповний roster/невірні правила блокують старт.
2. Вхід A через QR, B через link, C через code: кожен claim отримує тільки своє місце. Перевірити TTL, відкликаний/повторний/підібраний код та одночасний claim.
3. QR/URL не містить ролі чи секрету; роль із query ігнорується. Новий account не створюється лише від генерації картки.

### Т10.4 — панель ведучого

1. Пройти вступ → день → обговорення → голосування → ніч → дії ролей → подія → фінал за дозволеними переходами; Player не перемикає фази прямим API.
2. Запустити/поставити на паузу/продовжити таймер, reload і server restart; залишок коректний, завершення не виконується двічі.
3. Виконати комісара/лікаря/мафію за ruleset, перевірити заборонену фазу й повторне використання; ручна зміна Host має причину та попереднє/нове значення в аудиті.

### Т10.5 — гравець і секрети

1. A/B одночасно бачать різні картки. Перевірити response payload, realtime frames, вкладення/кеш/історію й прямий URL, а не тільки DOM.
2. Персональний доказ з’являється лише в A; публічний — у дозволених аудиторій. Після зміни фази чужі дані не відкриваються помилково.
3. На 390px пройти свою дію й повідомлення з клавіатури/екранного читача; disconnect/reconnect не губить стан. Revoke/seat replacement очищає доступ і приватний UI попереднього гравця.

### Т10.6 — голоси й повідомлення

1. Відкриті та таємні раунди: один допустимий бюлетень на seat; повтор мережі не додає голос, зміна дозволена лише до deadline за ruleset.
2. Dead/observer/outsider не голосують; одночасні останній голос/закриття дають детермінований підсумок. Нічия → авторське правило → окремий повторний раунд.
3. У таємному режимі чужий бюлетень не доступний через API/history/realtime; публікується тільки дозволений tally. Видимість бюлетенів Host визначена ruleset.
4. Host override із причиною не стирає сирі голоси. Персональне повідомлення B не бачить A; масова розсилка має правильну аудиторію й один delivery після retry.

### Т10.7 — фінал і звіт

1. Порівняти всі поля §14 з журналом реальної тестової партії, включно з переможцем, rounds/time, голосами, здібностями, завданнями й доказами.
2. Автор бачить дозволені агрегати всіх ігор сценарію, не довільні приватні повідомлення. Гравець отримує дозволений звіт; фінал сам по собі не розкриває всі секрети.
3. Запустити другу партію, перевірити незалежність/restart; повторне завершення не подвоює статистику. Окремо провести весь MVP на production з авторизованими учасниками.

### Т10.8 — AI і баланс

1. Запросити кожну операцію §4, включно з протиріччями та всіма показниками §12; пропозиції не змінюють сценарій до human review.
2. Прийняти рекомендацію в поточну версію; застаріла recommendation/відкликаний доступ відхиляються. Player request не отримує весь авторський контекст.
3. Перевірити помилку, timeout, quota, низьку впевненість й повтор; гра продовжується вручну. Контрольовані моделі та справжній Jev/DeepSeek — окремі прогони, заміряти latency/токени/спроби.

### Т10.9 — тригери й симулятор

1. Окремо перевірити всі сім типів тригерів §10 і всі шість типів наслідків; повтор/restart не виконує подію двічі.
2. Одночасні тригери та циклічний ланцюг мають визначений порядок і ліміт; недопустимий сценарій не зависає.
3. Пройти test mode всіма ролями й кожним фіналом; тест не запрошує людей, не публікує секрети та не збільшує live count/rating.

### Т10.10 — продаж сценарію

1. Опублікувати погоджену картку: усі поля §15, але жодного секретного пакета в public API/page preview.
2. Купити sandbox-платежем, повторити webhook, відкрити library/download за entitlement; outsider/Player прямий файл не завантажує. Підроблена ціна не приймається.
3. Оновити сценарій: бібліотека показує доступні версії, чинна партія лишається pinned. Refund/revoke за визначеною політикою; історія покупок приватна.
4. Рейтинг/відгук і число проведень підтверджуються сервером; модерація/видалення не видають приховані дані.

### Т10.11 — профіль і SaaS

1. Створити професійний профіль з усіма полями §16; права редагування й модерація, календар/бронювання без розкриття приватних клієнтів.
2. Для Free/Host/Professional Host перевірити погоджені ліміти через UI та прямий API, включно зі downgrade/expiry і активною грою.
3. Sandbox payment/refund/payout перевіряє затверджену ставку й ідемпотентність; повтор події не подвоює комісію. Реальні списання — окрема погоджена операція, не автоматичний тест.

### Т10.12 — мобільність і мультимедіа

1. Мобільний Host/Player, повільна мережа/offline/reconnect, клавіатура та доступна текстова альтернатива.
2. Голос/відео/зображення з private signed access: іншому seat URL не видає файл; revoke та TTL перевірені.
3. Файлові типи/розмір/квоти, fallback без відтворення й інтеграція без дублікатів подій; приватні медіа не потрапляють в публічний CDN cache.

## 8. Що ще потребує рішення перед відповідною реалізацією

Правила MVP (нічний порядок/перемога/нічиї/розкриття після смерті й фіналу), гостьова ідентифікація або обов’язковий account для claim, capability matrix Host Assistant і привілейованого адміністрування, ліміти гравців, ліцензія сценарію, ціни/комісія/refunds та календар booking. Це не перешкоджає збереженню ТЗ; рішення фіксуються перед відповідним кодом. Повний продукт, всі Т10.1–Т10.12 та всі наведені живі прогони залишаються невиконаними.
