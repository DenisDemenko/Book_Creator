## 1. Що вже є

- **Реєстр у коді** — `src/utils/coreEntities.ts`: 118 типів (88 базових у
  групах A–I + 30 критичних у J1–J3), 39 зв'язків (21 + 16 + 2 часові),
  характеристики, кольори, аліаси (укр./англ.), формат тега
  `[/slug:значення]`. Джерело істини — документ власника
  `Fusion_Lab_Studio_Entity_Registry…pdf`; файл — його машинна копія.
- **Таблиці `core_entities` / `core_entity_relations`** (SQLite застосунку,
  `server/db.ts`) — засіваються з коду на старті; `GET /api/core/entities`
  віддає їх разом зі статистикою згадок у чаті.
- **Семантичне ядро (PostgreSQL)**: `entities.type`, `entity_aliases.entity_type`,
  `entity_relations.type` — текстові ключі з реєстру; `rules.ts` перевіряє їх
  набором, зібраним із коду при завантаженні модуля.
- **Споживачі реєстру**: панель сутностей, слеш-меню, чат, тултипи й кольори
  тегів у редакторі, Story Graph, профіль героя, AI-1 (згадки), пам'ять
  героя, PDF/експорт (зняття тегів) — близько 30 файлів, усі читають
  масиви й функції `coreEntities.ts` синхронно.

## 3. Задум

**Визначення онтології** (`server/core/ontology/definition.ts`, формат
`fusion-ontology/1`) — один JSON-документ на версію:

- `groups` — 12 доменних груп (`id`, `name.en/uk`, `registry`, порядок);
- `entityTypes` — `id` (= slug, стабільний машинний ключ), `name.en/uk`,
  `groupId`, `family` (null), `status` (`active` / `deprecated`),
  `ui` (колір, порядок), `ai` (опис, підказки), `properties` (характеристики
  з машинним `id` — транслітерація української назви, — назвою, типом,
  переліком), `registry` (`base` / `critic` / `custom`), `aliases`
  (додаткові слова, як «герой» → `character`);
- `relationTypes` — `id` (= key), `name.en/uk`, приклад, `registry`,
  `status`, необов'язкові `from` / `to` (обмеження типів кінців) і
  `inverse` (`follows` ↔ `precedes`);
- `enums`, `validationRules` — переліки значень і декларативні правила
  перевірки (на старті — порожні, формат зафіксовано).

**Імпорт v1.0** — визначення збирається з `coreEntities.ts` (`factoryOntology()`)
і на першому старті ядра записується як активна версія 1 («Fusion Story
Ontology 1.0»). Зворотне перетворення визначення → записи реєстру дає рівно
ті самі 118 / 39 / 12 — це перевіряє тест.

**Реєстр під час роботи.** `coreEntities.ts` отримує `applyOntology(def)`:
масиви й індекси реєстру оновлюються на місці, тож усі ~30 споживачів
бачать активну версію без переписування. Сервер застосовує активну версію на
старті ядра й після публікації; `rules.ts`, AI-1, пам'ять героя читають
реєстр функціями, а не наборами, застиглими при завантаженні модуля.
Застарілий (`deprecated`) тип: наявні дані й теги лишаються дійсними, у
панелі й підказках його немає, AI його не пропонує.

**Життєвий цикл** (`server/core/ontology/lifecycle.ts`, таблиця
`ontology_versions`, міграція `0019`):

| Дія ТЗ | Як | Статус версії |
|---|---|---|
| EDIT → DRAFT | копія активної (або вказаної) версії; правки — операціями | `draft` |
| VALIDATE | структура, унікальність і формат ID, групи, кольори, назви EN/UA, кінці зв'язків, сумісність з активною | `validated` (будь-яка правка — знову `draft`) |
| PREVIEW | різниця з активною: додано / змінено (які поля) / застаріло / вилучено | — |
| MIGRATION IMPACT | скільки сутностей, аліасів, зв'язків і згадок у всіх книгах мають кожен вилучений / застарілий / змінений тип | зберігається з версією |
| PUBLISH → ACTIVE | лише `validated` з актуальним impact без блокерів; попередня активна → `deprecated` | `active` |
| ROLLBACK | нова версія з визначенням обраної минулої, ті самі перевірки й публікація | нова `active` |
| ARCHIVED | ручне архівування неактивної версії; відкинута чернетка | `archived` |

**Заборонено:** вилучити тип сутності чи зв'язку, що має дані хоч у одній
книзі (лише `deprecated`); змінити машинний ID (це вилучення + додавання —
і те саме правило); дві активні версії; правити опубліковану версію.
Кожна дія — у журнал аудиту `ontology_events` (хто, коли, що).

**API** (`server/core/ontology/routes.ts`): `GET /api/core/ontology`
(активна версія, будь-хто з входом — `get_schema`, `get_schema_version`);
решта — лише адміністратор: версії, чернетка, правки, `validate`,
`preview`, `impact`, `publish`, `rollback`, `archive`, аудит.
`GET /api/core/entities` віддає метадані з активної версії; клієнт
підтягує активну версію (і кешує її для офлайну), а без мережі працює з
вбудованою v1.0.

## 5. Порядок і стан

В1 → В2 → В3 → В4.

**Стан на 01.10.2026:** Т5.1 виконано — план #311, В1–В4 #312–#315.

**Критерії ТЗ §39:** №1 (імпорт чинного реєстру) — `bootstrapOntology`,
`live:ontology` (1); №2 (новий тип — як Draft) — чернетка й правки, (3);
№3 (Validate / Preview перед Publish) — публікація без перевірки й впливу —
409; №4 (Version / Rollback) — версії й відкат новою версією; №5 (UI-метадані
з реєстру) — редактор і панелі за активною версією, (4); №28 (розкладка не
змінює семантики) — у визначенні немає координат: розкладка канви Т5.2
житиме окремо від `fusion-ontology/1`, і хеш версії від неї не залежить;
№30 (машинні ID стабільні) — правка назв не змінює ID, зміна ID = вилучення.

**Чого ще немає — і чому.** Екрана редагування (рішення власника — у Т5.2,
разом із канвою); окремого дозволу `PUBLISH_SCHEMA` (Т5.2); `ontology_version`
у прогонах аналізу (§34) — з'явиться разом із прогонами workflow (Т5.4);
сімейства сутностей порожні до маршрутизації Jev (Т5.7). Таблиця SQLite
`core_entities` лишається засіяною вбудованим реєстром — словник для API
береться з активної версії.

## 6. Як користуватись (до канви Т5.2)

Адмін, через API: `POST /api/core/ontology/drafts` → `PATCH …/drafts/:id`
`{ ops: [...] }` → `POST …/validate` → `GET …/preview` → `POST …/impact` →
`POST …/publish`. Відкат — `POST /api/core/ontology/versions/:id/rollback`.
Вилучити тип із даними не можна — `set_entity_status … deprecated`.
