## 0. Підсумок звірки

ТЗ і план v1 збігаються в головному: усе стоїть на спільному індексі сутностей
книги, спершу — ядро, потім сторінки, AI лише пропонує, автор вирішує. Але ТЗ
**суттєво жорсткіший** в п'яти місцях, і кожне з них — архітектурне рішення, а
не деталь:

1. **Стабільні UUID** для абзаців, сутностей, сцен і зв'язків у базі; теги —
   лише псевдоніми. У v1 абзац адресувався хешем тексту, а «сутність» була
   групою тегів з однаковим значенням — для ТЗ цього недостатньо.
2. **PostgreSQL** і таблиці ядра на сервері. Студія працює на `node:sqlite`
   (+ JSON-запасний шлях), а джерело істини книги — IndexedDB браузера з
   дзеркалом на сервері. Без серверного ядра неможливі ні права на окремі
   глави, ні «через API не прочитати закриті глави».
3. **Окремі сторінки з маршрутами** `/projects/:projectId/...`. У Студії немає
   маршрутизації: вкладки перемикаються станом (`currentTab` в `App.tsx`).
4. **Статуси й докази для кожного висновку AI** (suggested / confirmed /
   rejected; у безперервності ще resolved / intentional) і **версії** всього:
   абзаців, сутностей, зв'язків, підтверджень.
5. **AI-наставник не пише абзаци за автора.** Нинішній коуч тренажерів
   повертає `rewrittenExample` і `correctedFullText`, який вставляється в
   книгу (#190, #237), — це пряма суперечність правилу сторінки 9. Власник
   вирішив залишити готову правку за явною дією автора (К4, розділ 2).

Стан коду: ядра немає (є довідник 118 типів і 37 зв'язків, `core_entities`),
сторінок немає; окремі шматки для сторінок існують і будуть перевикористані
(таблиця в розділі 6). Є вади безпеки, які ТЗ прямо забороняє: WebSocket
`/ws` без перевірки сесії; `/api/ai/translate`, `/api/ai/coach-feedback`,
`/api/ai/generate-exercise`, `/api/ai/analyze-emotional-arc` без
`requirePermission('canUseAi')`; запрошений учасник не має доступу до книги
на сервері.

## 3. Семантичне ядро

### 3.1. Таблиці (назви — як у ТЗ 13.1)

Усі таблиці мають `project_id`; кожен запит фільтрується за ним і правами
учасника на сервері. Ключі — UUID; імена й теги — лише псевдоніми.

| Таблиця ТЗ | Поля (основні) | Звідки дані зараз |
|---|---|---|
| `projects` | `id` (= `book.id`), `owner_id`, `title`, `languages` | `books` (payload) |
| `documents` | `id`, `project_id`, `kind` (chapter / section), `parent_id`, `order`, `title`, `version` | `Chapter`, `Section` |
| `paragraphs` | `id`, `document_id`, `order`, `text`, `text_hash`, `version`, `kind` (paragraph / heading / table / divider) + `paragraph_versions` | `Section.content` + нове `Section.paragraphIds` |
| `entities` | `id`, `type` (slug реєстру), `name`, `canonical` (затверджені поля), `status`, `version` + `entity_aliases` (`/character:Serhii`, `/персонаж:Сергій`, ім'я, аліаси) | Теги, `Book.characters` |
| `entity_mentions` | `id`, `entity_id`, `paragraph_id`, `span_start/end`, `source` (tag / ai / author), `status`, `subject_entity_id` | Теги в тексті |
| `entity_relations` | `id`, `type` (37 зв'язків реєстру), `from_id`, `to_id`, `status`, `evidence` (абзаци), `version` | `Character.relationships`, `threshold_scene_links` |
| `media_assets` | наявна таблиця + `license`, `author`, `source`, версії; `asset_entity_links` | `media_assets` |
| `analysis_runs` | `id`, `role` (AI-1/2/3), `module`, `model`, `prompt_version`, `inputs` (id+hash абзаців), `status`, `cost`, `created_at` + `analysis_findings` (результат, докази, статус) | `usage_log`, `diagnostics` (частково) |
| `scenario_branches` | `id`, `branch_point_entity_id`, `name`, `status` (active / archived), `base_version` + `branch_paragraphs` | немає |
| `editorial_tasks` | `id`, `target` (абзац / сцена / сутність / зображення), `kind` (editorial / learning), `assignee`, `due`, `status` | немає |
| `project_members` | `project_id`, `user_id`, `role`, `scopes` (глави, групи сутностей, матеріали) | `book_collab_owners`, `book_collab_invites` |
| `translations` | `paragraph_id`, `lang`, `text`, `status` (draft / approved), `source_hash`, `version` + `glossary_terms` | `Section.contentEn` |

Спеціалізовані таблиці (ТЗ 13.1): `emotion_points`, `story_time_points`,
`continuity_issues`, `appearance_versions`, `comments`, `mastery_exercises`,
`mastery_submissions`, `saved_searches`, `paragraph_embeddings`.

Загальні правила для всього ядра:

- **Статус** кожного запису, що міг створити AI: `suggested` → `confirmed` /
  `rejected` (у безперервності ще `resolved`, `intentional`). Тег, який автор
  поставив сам, — `confirmed`.
- **Затверджене не перезаписується.** AI пише лише `suggested`; зміну
  затвердженого поля AI може тільки запропонувати окремим записом.
- **Версії.** Зміна абзацу, сутності, зв'язку чи статусу пише нову версію з
  автором і часом; відновлення — з історії.
- **Докази.** Висновок без посилання на абзац, сцену чи зображення зберігається
  лише з позначкою «недостатньо даних».

### 3.2. Стабільні ID абзаців

- У редакторі (TipTap) абзацам і заголовкам додається атрибут `pid`. Плагін
  призначає UUID новим блокам і дублікатам після розбиття абзацу (друга
  половина отримує новий id), а при злитті зберігає id першого.
- `tiptapDocToMarkerString` лишається без змін (рукопис чистий); поруч
  зберігається `Section.paragraphIds: string[]` у порядку блоків того самого
  розбору, що в `manuscriptDoc.ts`.
- Сервер, отримавши книгу, розбирає розділ тим самим модулем і зіставляє блоки
  з id. Якщо id бракує або кількість не збігається (імпорт, правка AI поза
  редактором), незмінені блоки впізнаються за `text_hash` і зберігають свій
  id, решта отримує нові.
- `scene_id` = `Section.scene.id` (сцена в Студії прив'язана до розділу).

### 3.3. Синхронізація після редагування (ТЗ 13.4)

Після кожного збереження книги сервер ставить у фонову чергу задачу
`core_sync` (черга — за зразком `server/etsy/publishQueue.ts`: рядок у базі,
повтори, відновлення після перезапуску):

1. Зіставити блоки з `paragraphs` → нові версії лише змінених абзаців.
2. Перерахувати згадки з тегів у змінених абзацах (без AI, одразу).
3. Позначити `needs_review` висновки AI, чиї вхідні абзаци змінились
   (`analysis_runs.inputs` зберігає id і хеш кожного абзацу).
4. Поставити AI-1 на змінені абзаци, якщо автор увімкнув автоаналіз.
5. Записати сповіщення про вплив: ілюстрації сутностей зі зміненими фактами,
   події хронології, переклади змінених абзаців (`source_hash` ≠ хеш),
   гілки, що спираються на змінені абзаци.

Редактор не чекає на це: сторінки показують «синхронізація…» і оновлюються,
коли задача завершилась.

### 3.4. Кому належить тег (суб'єкт)

Теги-атрибути (`/emotion`, `/decision`, `/belief`, `/appearance`,
`/character-state`, `/goal`, `/need`, `/value`, `/relationship`) отримують
`subject_entity_id`: найближчий попередній `/character` в абзаці → єдиний
персонаж абзацу → `/focalization` → учасники сцени → «невизначено» (підказка
автору). Явне уточнення — `@Ім'я` в кінці значення
(`[/emotion:страх — 7 @Сергій]`), якщо власник погодить синтаксис.
Система тегів заморожена до окремого обговорення — `TAGS_ANALYSIS.md` (П1, П2).

### 3.5. Значення тега як поля

Значення ділиться за « — » на поля в порядку характеристик реєстру
(«тип — інтенсивність — причина»); числа, дати й інтервали розбираються
окремо. Звідси — числа для емоцій, час для хронології, «було → стало» для
біографії.

## 4. API

Новий простір `/api/projects/:id/...` (`id` = `book.id`); наявні `/api/books`
лишаються. На кожному маршруті — одна перевірка `requireProjectAccess(role,
scope)` за `project_members`: читання фільтрується за главами й групами
сутностей, до яких учасник має доступ.

Маршрути ТЗ 13.2 (GET: `entities`, `entities/:entityId`, `relations`,
`search`, `story-graph`, `characters/:characterId`, `emotions`, `timeline`,
`visual-library`, `continuity`, `writer-mastery`, `members`, `translations`;
POST: `analysis`, `scenario-branches`, `editorial-tasks`, `translations`) плюс
для кожного ресурсу:

- `PATCH …/:rid` — правка автором (нова версія);
- `POST …/:rid/confirm`, `POST …/:rid/reject` (і `resolve`, `intentional` для
  безперервності) — зміна статусу з версією;
- `GET …/:rid/history`, `POST …/:rid/restore/:version`;
- `DELETE …/:rid` — лише з правом і з м'яким видаленням (історія лишається);
- `GET /api/projects/:id/analysis/:runId` — статус фонової задачі.

`POST /analysis` не чекає результату: повертає `runId` (202), як WriterScan.

## 5. Три ролі AI

| Роль | Що робить | Модулі ядра (`CORE_MODULE_KEYS`) |
|---|---|---|
| AI-1 класифікація | Згадки сутностей в абзацах, зіставлення з наявними `entities`, первинні зв'язки | `entityClassify` |
| AI-2 спеціалізований аналіз | Персонаж, емоції, сценарні гіпотези, безперервність, стиль, вправи, переклад, тлумачення пошукового запиту | `characterProfile`, `emotionAnalysis`, `scenarioHypotheses`, `continuityCheck`, `writerMentor`, `translation`, `searchInterpret` |
| AI-3 візуальний аналіз | Ознаки зовнішності, предмети, локації на зображенні; пропозиції зв'язків; порівняння з описом | `imageEntities` (поруч із наявним `describe-character-from-image`) |

Кожна роль має власну модель в адмінці (`resolveModuleModelId`), тож
замінюється незалежно; на MVP усі три можуть працювати на одній моделі з
різними інструкціями. Кожен виклик — рядок `analysis_runs` з витратою в
`usage_log` (`book_id`), видно в «Тарифах ШІ». Результат без доказу з
вхідних абзаців відкидається на сервері, а не лише в інструкції моделі.

## 6. Одинадцять сторінок

Спільне для всіх: маршрут `/studio/projects/:id/<сторінка>`; денна й нічна
теми; ширини 360 / 768 / 1280 px; мінімум панелей; кожен елемент, що
посилається на текст, відкриває абзац у редакторі
(`handleNavigateToSearchMatch` + `pendingHighlight` за `paragraph_id`); довгі
операції — фоном зі статусом; словник ключів — у `src/i18n/dictionaries`
(українська типово).

### 6.1. Сторінка 1 — Розумний пошук · `/search` · етап 1

**Перевикористовуємо:** `BookSearchModal` (повнотекстовий пошук і перехід),
`collectCharacterMentions`.
**Будуємо:** три рівні, результати зливаються з поясненням джерела збігу:
повнотекстовий (індекс PostgreSQL `tsvector`), векторний
(`paragraph_embeddings` + `pgvector`, ембединги лише змінених абзаців),
графовий (фільтри за `entity_mentions` / `entity_relations`: персонаж +
емоція + сцена, «приховує від дружини» → зв'язок із персонажем-дружиною).
`searchInterpret` (AI-2) лише розкладає запит на фільтри й текст; відповідь —
тільки знайдені абзаци з контекстом і поясненням релевантності. Фільтри ТЗ
(персонаж, сцена, глава, емоція, подія, період, статус), збережені запити
(`saved_searches`), результати обмежені правами.
**Приймання:** запит «герой + емоція» → абзаци з точним `paragraph_id` і
переходом у редактор (тест на тестовій книзі з розміченими й нерозміченими
сценами).

### 6.2. Сторінка 2 — Story Graph · `/story-graph` · етап 1

**Будуємо:** граф з `entities` / `entity_relations` / `entity_mentions`:
вузли всіх типів ТЗ, колір — з реєстру, підписи ребер — типи зв'язків;
масштаб, перетягування, пошук вузла, фільтр типів; картка вузла зі
зв'язками й згадками; ручне створення й підтвердження зв'язків за правами;
поступове довантаження сусідів (`story-graph?focus=<id>&depth=1`).
Бібліотека — React Flow (`@xyflow/react`) з автоматичною розкладкою.
**Приймання:** клік по героєві → підтверджені зв'язки першого рівня з
джерелами.

### 6.3. Сторінка 3 — Профіль персонажа · `/characters/:characterId` · етап 1

**Перевикористовуємо:** картку `Character`, `character-codex` (факти з

AI; появи, події й рішення в хронологічному порядку; арка: початковий,
проміжний, поточний стан; перемикач «стан на главі N» — лише факти до цієї
глави (без спойлерів); портрети з сторінки 7.
**Приймання:** нова глава додає нові підтверджені факти, попередні
лишаються (тест: дві версії книги, профіль до й після).

### 6.4. Сторінка 4 — Emotion Analytics · `/emotions` · етап 2

**Перевикористовуємо:** `emotion_dictionary` (48), `emotion_analysis`,
`emotion_mastery_scores` (майстерність передачі), `EmotionalArcLab`

**Будуємо:** `emotion_points` (персонаж, абзац, емоція, вид: основна /
другорядна / прихована, інтенсивність, майстерність передачі, вплив на сюжет,
джерело: тег / AI / автор, статус, докази). Графіки кількох персонажів за

доказів — «недостатньо даних». Застереження ТЗ: це евристика редагування, не
клінічний вимір; враховується жанр.
**Приймання:** будь-яка точка відкривається й перевіряється за вихідними
абзацами.

### 6.5. Сторінка 5 — Scenario Branches · `/scenario-branches` · етап 3

**Перевикористовуємо:** знімки книги, `bookDiff.ts`, `computeWordDiff`,
AI-чернетки.
**Будуємо:** точка розгалуження — рішення, подія або поріг; гілка —
`branch_paragraphs` поверх основи (основні `paragraphs` і канонічні
`entities` не змінюються); залежні сутності (за `leads_to`, `caused_by`,
`precedes` і спільними учасниками) і потенційні суперечності (перевірка
сторінки 8 у контексті гілки); кілька гілок, перейменування, архів,
історія; візуальне порівняння з основою; `scenarioHypotheses` (AI-2) —
наслідки як гіпотези; перенесення в основу — лише після підтвердження,
новими версіями абзаців.
**Приймання:** створення й правка гілки не змінює ні тексту, ні канонічних
сутностей (тест порівнює хеші основи до й після).

### 6.6. Сторінка 6 — Story Timeline · `/timeline` · етап 2

(флешбек видно як перетин); паралельні лінії; зв'язки `precedes` /
`follows` / `overlaps` (обидва вже в реєстрі коду, К5); перетягування з
підтвердженням; фільтри за героєм, місцем, сюжетною лінією; попередження про
часові суперечності з переходом до сцени.
**Приймання:** флешбек відображається окремо від поточного часу оповіді.

### 6.7. Сторінка 7 — Visual Library · `/visual-library` · етап 2

**Перевикористовуємо:** `media_assets`, `MediaLibraryView`,

**Будуємо:** галерея й завантаження; `asset_entity_links` (герой, локація,

Зміна затвердженого опису позначає прив'язані зображення «перевірити».
**Приймання:** портрет, прив'язаний до героя, видно в його профілі

### 6.8. Сторінка 8 — Continuity Checker · `/continuity` · етап 2

**Перевикористовуємо:** `character-consistency`, `behavior-drift`,
`coach-book-audit` (ідея, без адрес), типи `/continuity-issue`.
**Будуємо:** `continuity_issues` (тип: час, вік, зовнішність, локація,
предмет, знання, стосунки; доказ А і доказ Б — два абзаци; статус
suggested / confirmed / resolved / intentional / rejected); правила без AI на
ядрі (предмет загублено → використано; секрет не розкрито → герой діє з
ним; герой у двох місцях в одному часі) + `continuityCheck` (AI-2) по
розділах у порядку сюжету зі «станом світу» перед розділом; порівняння двох
фрагментів поруч; фільтри; повторна перевірка змінених місць (синхронізація
3.3). Правило ТЗ: відсутність пояснення може бути навмисною загадкою —
модель просять позначати такі місця як `intentional`-кандидати, не помилки.
**Приймання:** кожне попередження має текстові докази й відхиляється
автором без правки рукопису.

### 6.9. Сторінка 9 — Writer Mastery · `/writer-mastery` · етап 3

**Перевикористовуємо:** каталог 18 навичок і 39 вправ із сутностями
(`mastery18.ts`, `masteryEntities.ts`), `BookContextBanner`,
`emotion_mastery_scores`.
**Будуємо:** вправи з прив'язкою до абзацу, сцени чи персонажа
(`mastery_exercises`); особистий план і вільний вибір навичок; короткі й
поглиблені завдання; дві редакції автора поруч (`mastery_submissions` +
`computeWordDiff`); історія й прогрес за навичками; `writerMentor` (AI-2)
ставить запитання й дає критерії; готова виправлена версія — **лише за
явною дією автора** («показати зразок правки»), ніколи автоматично, завжди
з позначкою «AI» і різницею з авторським текстом; у книгу — тільки після
підтвердження, новою версією абзацу (рішення власника К4 — свідомий відступ
від правила ТЗ); відхилення вправи з причиною; оцінки з урахуванням жанру й достатності
вибірки (мало тексту → «недостатньо даних»).
**Приймання:** для обраної сцени — конкретна вправа, і автор порівнює свої
дві редакції.

### 6.10. Сторінка 10 — Collaboration · `/collaboration` · етап 3

**Перевикористовуємо:** запрошення (`collaborationRoutes.ts`), `rbac.ts`,

**Будуємо:** ролі ТЗ (власник, співавтор, редактор, ілюстратор, перекладач,
читач) на рівні проєкту; `scopes` — глави, групи сутностей, матеріали;
коментарі до абзаців, сцен, сутностей і зображень; `editorial_tasks` з
виконавцями, термінами, статусами й сповіщеннями (спершу в застосунку);
історія правок, порівняння, відновлення; **серверна перевірка кожної
операції**: WS з сесією й правом, книга для обмеженої ролі віддається
відфільтрованою, запис — лише патчами дозволених розділів (К2-Б).
**Приймання:** учасник з обмеженим доступом не читає закриті глави й не
змінює заборонене ні через API, ні через WS (негативні тести).

### 6.11. Сторінка 11 — Contextual Translation · `/translation` · етап 3

**Перевикористовуємо:** `/api/ai/translate` (буде переписано), колонки

**Будуємо:** вибір вихідної й цільової мов; `translations` на рівні абзацу
(`paragraph_id` ↔ переклад, статус, версії); наявний `contentEn`
переноситься як мова `en`; паралельний перегляд; `glossary_terms` (імена,
терміни, власні назви, зв'язок із сутністю, затвердження); модель
(`translation`, AI-2) отримує затверджені профілі героїв, їхні мовні
характеристики (`/character-voice`), терміни розділу й стиль автора; теги
зберігаються; зміна оригіналу → переклад «потребує оновлення»
(`source_hash`); експорт перекладеної книги.
**Приймання:** зміна затвердженого імені в глосарії знаходить усі входження
в перекладах і пропонує узгоджене оновлення (пакет `suggested`-правок).

не пройде критеріїв ТЗ про стабільні ID, права й фонові задачі.

| Етап | Зміст | Результат, який можна показати |
|---|---|---|
| **0 — Основа** | Виправлення безпеки (WS із сесією, `requirePermission` на чотирьох маршрутах ШІ); PostgreSQL на Railway для ядра (К1) і шар репозиторіїв; таблиці `projects`, `documents`, `paragraphs` (+версії), `entities` (+псевдоніми), `entity_mentions`, `entity_relations`, `analysis_runs`, `project_members` (поки лише власник); `pid` у редакторі й `Section.paragraphIds`; синхронізація 3.3 (кроки 1–3); фонова черга; каркас маршрутів `/projects/:id/*` і `requireProjectAccess` | Після збереження книги ядро на сервері містить абзаци з UUID і згадки з тегів; `GET /entities` працює з перевіркою прав |

## 8. Критерії готовності ТЗ → як перевіряємо

| Критерій ТЗ (розділ 15) | Перевірка |
|---|---|
| 11 сторінок за маршрутами | Живий прогін відкриває кожну адресу напряму й через меню |
| Спільне ядро й стабільні ID | Тест: правка, розбиття, злиття, переміщення абзацу — `paragraph_id` незмінних блоків той самий; імпорт без id — звірка за хешем |
| Перехід від сутності до абзацу | Живий прогін на кожній сторінці: клік → редактор на тому самому абзаці |
| Джерела, статуси, історія AI | Тест сервера: висновок без доказу не зберігається; зміна статусу пише версію |
| Затверджене не перезаписується | Тест: повторний AI-аналіз після підтвердження не змінює затверджене поле |
| Права на рівні API | Негативні тести: закрита глава недоступна через `/api/projects/*`, `/api/books/*` і `/ws` |
| Мобільний інтерфейс | Живий прогін у 360 / 768 / 1280 px, обидві теми, без горизонтального прокручування |
| Довгі AI-операції не блокують редактор | Тест: `POST /analysis` → 202 і `runId`; редактор зберігає зміни під час задачі |
| Критерії кожної сторінки | Окремий тест на кожен рядок «Приймання» з розділу 6 |

## 9. Ризики

- **Обсяг.** Це найбільша зміна Студії: нова база, нова модель даних,
  11 сторінок. Етап 0 — найризикованіший і має бути закінчений до будь-якої
  сторінки, інакше сторінки доведеться переписувати під ядро.
- **Два сховища на перехідний період** (SQLite Студії й PostgreSQL ядра, К1-А).
  Межа чітка: ядро знає лише `project_id` і `user_id`; користувачі, тарифи,
  медіа поки в SQLite.
- **Книга без тегів.** AI-1 з етапу 1 створює `suggested`-згадки, тож
  сторінки не порожні; лічильник «підтверджено X% згадок» показує автору
  якість даних.
- **Витрати AI.** Аналіз лише змінених абзаців (хеші), оцінка вартості перед
  повним прогоном, облік у `usage_log`, дорогі задачі — за тарифом.
- **Приватність.** Ембединги й аналіз надсилають текст провайдеру — як і
  наявні модулі ШІ; для автоаналізу — окремий перемикач у налаштуваннях
  проєкту.
- **Відступ від ТЗ на сторінці 9** (К4): готова правка AI лишається. Щоб
  вона не стала «непомітним переписуванням», яке ТЗ забороняє в розділі 1, —
  лише за явною дією, з різницею й новою версією абзацу.
- **Дублювання наявних вікон** (К7): рішення про їхню долю — після приймання
  сторінок.
